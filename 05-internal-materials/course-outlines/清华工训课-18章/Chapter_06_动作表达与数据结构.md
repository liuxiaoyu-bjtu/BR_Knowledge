动作学习不是“给机器人一个动作名称，它就自动学会”。而是从动作数据收集到模型训练、模型导出、Sim\-to\-Sim（仿真到仿真验证）和 Sim\-to\-Real（仿真到真实迁移）等过程。其中，数据可以来自动捕、遥操、示教、视频或已有数据集；数据需要被整理成机器人能够表达的关节轨迹；人体动作需要经过重定向；训练前还需要转换为训练程序需要的格式。本章的目标，是让读者理解这条链路中的“数据”。

## 6\.1 动作学习系统全流程

### 6\.1\.1 从动作来源到真机执行

动作学习系统可以先看成一条从“动作来源”到“机器人执行”的全链路：

```Plaintext
动作来源
  ↓
动作数据表达
  ↓
重定向
  ↓
机器人动作数据整理
  ↓
训练数据格式转换
  ↓
BeyondMimic 训练
  ↓
模型评估与导出
  ↓
Sim-to-Sim 验证
  ↓
Sim-to-Real 真机执行
```

这条链路中的每一步都有明确输入和输出。

- **动作来源**解决“动作从哪里来”。它可以是人体动作捕捉数据，也可以是遥操记录、示教轨迹、视频姿态估计结果或已经整理好的动作数据集。

- **动作数据表达**解决“动作如何被表示成数据”。无论动作来源是什么，训练系统最终需要读取的是一帧一帧的数值序列，而不是自然语言描述。

- **重定向**解决“人的动作如何映射到 K1 身体”。人体骨骼和 K1 机器人骨骼不同，关节数量、自由度、比例、坐标系和关节限制都不同，动作需要转换到机器人可表达的关节空间。

- **机器人动作数据整理**解决“数据的标准化，以防止数据不能被训练程序正确读取”。这一步会检查关节顺序、帧率、列数、关节角范围和动作连续性，以防止有数据缺失、冗余、超出正常数据范围等。

- **训练数据格式转换**解决“训练侧需要哪些字段”。CSV（Comma\-Separated Values，逗号分隔值文件）便于直观检查，但由于训练通常**需要直接使用**速度、关节位置、姿态**等高维数组格式**，而 CSV 在表达矩阵/多维数据时效率较低，因此需要进一步整理并压缩转换为 NPZ 文件，以便训练框架高效加载。

- **BeyondMimic 训练**解决“如何根据数据集得到策略模型”。训练时，机器在仿真环境中反复优化策略，让机器人学会如何执行动作，同时满足物理约束。

- **模型评估与导出**解决“训练结果如何变成可部署模型”。训练过程中的 checkpoint（检查点）需要导出为 TorchScript 或 ONNX 等部署侧能加载的模型格式。

- **Sim\-to\-Sim 验证**解决“模型在仿真环境中是否有效、可用”。例如在 Isaac Lab 中训练后，再到 MuJoCo 中执行动作，观察动作是否稳定，通识观察速度、动作保真度等问题，通俗的来说，就是验证模型是否能用。

- **Sim\-to\-Real 真机执行**解决“模型能否迁移到真实 K1”。真实机器人有摩擦、延迟、关节响应、地面条件和安全限制，仿真结果不能直接等同于真机结果。

### 6\.1\.2 为什么先讲数据

动作生成系统中，很多问题表面上看是训练失败，根本原因却在数据层。

如果关节顺序错了，训练程序可能还能运行，但机器人学到的动作会完全错误。因为模型认为第 1 个关节是头部，实际数据却可能对应肩部。

如果帧率错了，动作节奏会改变。一个 30 fps 的动作被当作 50 fps 读取，动作时长和速度都会发生变化。

如果重定向结果不合理，动作可能看起来像人体，但对 K1 来说关节角超限、重心不合理或足底接触不稳定。

如果 CSV 转 NPZ 时字段缺失，训练侧可能无法计算跟踪奖励，也可能无法读取身体部件位置和速度。

因此，在进入 BeyondMimic 训练前，必须具备先检查动作数据的意识。本章的实践案例围绕这一点设计：读取动作文件，打印结构摘要，确认数据是不是符合 K1 动作学习流程。

## 6\.2 动作数据从哪里来

### 6\.2\.1 动捕数据

动捕是 Motion Capture 的简称，通常译为动作捕捉。动捕系统通过光学标记点、惯性传感器或其他设备记录人体运动，得到人体骨骼随时间变化的数据。常见格式包括 BVH、FBX、SMPL 和 SMPL\-X 等。

BVH 是 Biovision Hierarchy 的缩写，常用于保存人体骨骼层级和关节运动序列。SMPL 和 SMPL\-X 是参数化人体模型，能够用参数描述人体姿态和形体。对机器人动作学习来说，动捕数据的优点是动作连续、时序完整、姿态信息丰富；难点是它描述的是人体，不是 K1 机器人。

动捕数据通常不能直接用于机器人训练。人体有自己的骨骼比例和关节自由度，K1 有自己的机械结构和关节限制。要让 K1 学习人体动作，需要先把人体动作重定向到 K1 的关节空间。

### 6\.2\.2 遥操数据

遥操对应英文 Teleoperation。它指操作者通过远程控制设备、动作映射设备或控制界面带动机器人完成动作，同时记录机器人自身的状态数据。

遥操数据的优势是它天然发生在机器人身体上，关节数量、关节顺序和机械限制更接近真实执行条件。它的难点是遥操系统本身需要稳定，操作者动作质量会直接影响记录结果。如果遥操过程中机器人晃动明显、动作断续或控制延迟较大，数据质量也会受到影响。

### 6\.2\.3 示教数据

示教对应 Chapter 5 中的 Teach by Demonstration（通过演示进行示教）。操作者让机器人进入可拖动状态，手动带动机器人完成动作，系统记录关节轨迹。

示教数据适合获取简单动作，尤其适合上半身姿态和展示动作。它的优点是直观、快速，不需要复杂动捕设备。它的边界也很清楚：示教记录的是机器人被人工带动时的轨迹，不等于已经得到了一套可以处理复杂平衡和接触变化的全身控制策略。

### 6\.2\.4 视频数据

视频也可以作为动作来源。通过人体姿态估计模型，可以从视频中提取人体关键点，例如肩、肘、腕、髋、膝、踝的位置变化。再进一步处理后，这些关键点可以转换为人体姿态序列，并参与重定向。

视频来源成本较低，但数据不确定性更高。单目视频可能存在深度估计误差，遮挡会导致关键点丢失，衣物和视角也会影响姿态识别结果。因此，视频数据通常需要更多清洗、补帧和平滑处理。

### 6\.2\.5 现有动作数据集

动作学习也可以使用已经整理好的数据集。例如一些数据集已经完成了人体动作采集、清洗、切分，甚至已经重定向为某类机器人可用的关节数据。本课程使用的 BeyondMimic 示例资源中，就包含 K1 相关动作 CSV 和 NPZ 文件。

使用现有数据集的优势是可以更快进入训练和部署流程。它的限制是动作范围受数据集内容约束，读者仍然需要理解数据格式，否则很难判断数据是否适合某个任务。

## 6\.3 动作数据表达了什么

### 6\.3\.1 动作数据是一组序列数值

对人来说，“跳舞”“挥手”“格斗动作”是可以直接理解的动作名称。但对于机器来说，这些动作对应的是一段时间序列中，每个时刻机器人身体状态的数值。

一段动作可以被简化理解为：

```Plaintext
第 1 帧: 根部位姿 + 关节状态 + 身体部件状态
第 2 帧: 根部位姿 + 关节状态 + 身体部件状态
第 3 帧: 根部位姿 + 关节状态 + 身体部件状态
...
第 N 帧: 根部位姿 + 关节状态 + 身体部件状态
```

每一帧记录“这一瞬间机器人是什么状态”，多帧按照时间顺序排列后，才构成完整动作。

### 6\.3\.2 根部位姿

根部位姿通常用于描述机器人整体在空间中的位置和朝向。在 K1 的 CSV 动作数据中，前 7 列为根部位姿：

```Plaintext
x, y, z, qx, qy, qz, qw
```

其中 `x, y, z` 表示根部在空间中的位置；`qx, qy, qz, qw` 表示四元数姿态。四元数是一种描述三维旋转的方式，常用于机器人和仿真系统中，能够避免欧拉角在某些姿态下出现的奇异问题。

根部位姿的重要性在于，它描述了机器人整体身体的位置和朝向变化。对于走路、转身、舞蹈和格斗动作，只看关节角是不够的，还需要知道身体整体如何移动和旋转。

### 6\.3\.3 关节位置与关节速度

关节位置通常指每个关节在某一帧的角度。对 K1 来说，一帧动作数据中的关节位置可以理解为 22 个关节角组成的向量：

```Plaintext
[joint_1, joint_2, joint_3, ..., joint_22]
```

关节速度描述关节角随时间变化的快慢。两个动作可能经过同样的姿态，但如果速度不同，动作效果会完全不同。慢慢抬手和快速甩手，关节位置序列可能经过相似范围，但关节速度差异很大。

训练时，关节速度不仅用于描述动作节奏，也有助于模型学习更平滑、更稳定的控制行为。

### 6\.3\.4 身体部件位置与姿态

BeyondMimic 训练中，数据通常不只包含关节角。为了让机器人在仿真中跟踪参考动作，训练程序还会使用身体部件的位置、姿态、线速度和角速度。

例如 NPZ 文件中常见字段包括：

|字段|含义|
|---|---|
|`body_pos_w`|世界坐标系下各身体部件的位置|
|`body_quat_w`|世界坐标系下各身体部件的姿态四元数|
|`body_lin_vel_w`|世界坐标系下各身体部件的线速度|
|`body_ang_vel_w`|世界坐标系下各身体部件的角速度|

这些字段让训练系统不仅能比较“关节角像不像”，还能比较“身体部件在空间中的运动像不像”。对于全身动作，这一点非常重要。

## 6\.4 重定向：从人体动作到 K1 动作

### 6\.4\.1 为什么需要重定向

重定向对应英文 Retargeting。它是动作学习流程中的关键步骤，解决的是“一个身体上的动作如何转移到另一个身体上”。

人体动作数据描述的是人的骨骼运动，K1 的动作数据描述的是机器人关节运动。两者不能直接等同，原因包括：

- 关节数量不同；

- 关节自由度不同；

- 骨骼比例不同；

- 坐标系定义不同；

- 关节极限不同；

- 足底接触和身体重心约束不同。

例如，一个人抬手时，肩关节、锁骨、脊柱和手腕可能一起参与；K1 的上肢关节数量和自由度与人体不同，不能逐关节照搬。再比如，人类跳跃或转身时可以依靠脚掌、踝关节和身体柔性自然调整，但 K1 需要在机械关节、接触力和平衡控制约束下执行。

因此，重定向的目标不是把人体动作逐数值复制到机器人上，而是把动作意图转换为机器人可表达、可训练、可能执行的轨迹。

### 6\.4\.2 重定向要解决的约束

重定向至少要处理四类约束。

第一，结构约束。人体骨骼和机器人机构不同，关节名称、关节数量和连接关系不同。

第二，运动学约束。机器人关节有角度范围限制，有些人体姿态在机器人上无法直接达到。

第三，动力学约束。即使某个姿态在几何上可达，也不代表机器人能在真实动力学中稳定执行。

第四，接触约束。涉及下肢动作时，脚底接触地面的状态会影响整个身体的平衡。脚是否离地、支撑脚在哪里、重心是否落在支撑区域内，都会影响动作能否执行。

这些约束说明，重定向不是简单格式转换，而是动作学习系统中的第一道机器人化处理。

### 6\.4\.3 重定向的基本步骤

重定向可以理解为“把来源动作翻译成 K1 能表达的动作”。这里的翻译不是语言层面的翻译，而是身体结构、坐标、关节和运动约束之间的转换。

一个典型重定向流程可以分成五步。

第一步，读取来源动作。来源动作可能是 BVH、SMPL\-X、视频姿态估计结果，也可能是其他人体动作格式。以 BVH 为例，文件中保存了人体骨骼层级和每一帧的关节运动；以 SMPL\-X 为例，文件中保存的是参数化人体模型的姿态参数。

第二步，建立来源身体与 K1 身体之间的映射。人体的肩、肘、髋、膝、踝等部位需要对应到 K1 的相关关节和身体部件。这个映射不是一一复制，因为 K1 和人体的关节自由度不同。例如，人的肩部运动非常复杂，而 K1 的肩部关节只能在机器人设计允许的自由度内运动。

第三步，把来源动作转换到 K1 的关节空间。重定向工具会根据机器人模型、关节名称、关节限制和目标姿态，计算每一帧中 K1 各关节应该处于什么角度。这个过程通常会尽量保持动作外观相似，同时避免明显超出机器人关节范围。

第四步，检查根部位姿和接触关系。对于全身动作，只看四肢姿态不够，还要关注身体根部的位置、朝向，以及脚底是否需要保持支撑。否则，动作看起来像人体动作，但 K1 回放或训练时可能出现重心不合理、脚底滑动或身体姿态突变。

第五步，导出机器人动作数据。重定向完成后，会生成 K1 能够继续处理的动作文件。对本章样例来说，这个产物就是 K1 CSV：每一行是一帧，每一帧包含根部位姿和 22 个 K1 关节角。

如果来源动作是 BVH，典型转换命令可以写成：

```Bash
uv run bvh_to_robot -f assets/bvh/lafan1/walk1.bvh -r k1 --record_video -s2
```

其中 `-f` 指定 BVH 文件，`-r k1` 指定目标机器人为 K1，`-s2` 表示导出 CSV 格式的机器人动作数据。

如果来源动作是 SMPL\-X，典型转换命令可以写成：

```Bash
uv run smplx_to_robot -f motion.npz -r k1 --loop --record_video -s2
```

其中 `-f` 指定 SMPL\-X 动作文件，`-r k1` 指定目标机器人为 K1，`-s2` 表示导出 CSV。不同重定向工具的参数可能不同，但核心目标相同：把来源动作转换成 K1 关节空间中的时间序列。

本章不要求读者重新完成一次上游重定向。这里重点是理解：本章看到的 K1 CSV 并不是原始人体动作文件，而是已经经过重定向后得到的机器人动作数据。

### 6\.4\.4 K1 CSV 和 NPZ 文件是怎么来的

重定向完成后，常见输出是机器人关节空间中的动作序列。对于本章使用的 K1 示例数据，CSV 文件中每一行表示一帧：

```Plaintext
根部位姿 7 列 + K1 关节角 22 列
```

也就是一行共 29 列。

这类 CSV 数据已经不是原始人体数据，而是“人体动作或其他来源动作经过 K1 重定向后的机器人动作”。它表达的是：在第 1 帧、第 2 帧、第 3 帧等每一个时刻，K1 的根部位姿是什么，22 个关节角分别是多少。

可以把本章样例数据的来路理解为：

```Plaintext
人体动作 / 动捕动作 / 参数化人体动作
  ↓
重定向到 K1 机器人模型
  ↓
生成 K1 CSV
  ↓
检查帧率、列数、关节顺序和动作范围
  ↓
通过 csv_to_npz.py 转换
  ↓
生成 K1 NPZ
```

其中，CSV 阶段的重点是“动作已经变成 K1 的关节空间轨迹”。它适合检查：一共有多少帧、每帧有多少列、是否符合 7 列根部位姿加 22 列关节角、帧率是否正确、主要变化发生在哪些关节。

NPZ 阶段的重点是“动作被整理为训练系统需要的多数组结构”。CSV 转 NPZ 时，转换程序会读取 CSV 中的根部位姿和关节角，并进一步处理出训练和回放需要的字段。典型过程包括：

- 读取 CSV 中的根部位置、根部姿态和关节角；

- 将根部姿态四元数转换为仿真环境内部使用的顺序；

- 根据输入帧率和输出帧率进行插值；

- 计算根部线速度、根部角速度和关节速度；

- 在仿真环境中写入根状态和关节状态；

- 记录身体部件的位置、姿态、线速度和角速度；

- 将 `fps`、`joint_pos`、`joint_vel`、`body_pos_w`、`body_quat_w` 等数组打包保存为 NPZ。

典型转换命令可以写成：

```Bash
python scripts/csv_to_npz.py \
  --headless \
  --input_file <K1_MOTION>.csv \
  --input_fps <FPS> \
  --output_name <K1_MOTION>.npz
```

这一步之后得到的 NPZ 才更接近 BeyondMimic 训练所需的 motion file（动作文件）。训练程序读取 NPZ，不只是为了得到关节角，还要得到速度、身体部件位置和姿态等信息，用于后续动作跟踪和奖励计算。

## 6\.5 CSV 动作数据

### 6\.5\.1 CSV 的行和列

CSV 是逗号分隔值文件，适合用文本编辑器、表格工具或 Python 脚本查看。K1 的重定向 CSV 动作数据中，每一行是一帧动作，每一列是一类数值。

本章使用的 K1 CSV 示例具有 29 列：

```Plaintext
第 1-3 列: 根部位置 x, y, z
第 4-7 列: 根部姿态四元数 qx, qy, qz, qw
第 8-29 列: 22 个 K1 关节角
```

如果 CSV 有 1261 行，就表示这段动作包含 1261 帧。如果文件名中标注为 `50fps`，表示每秒 50 帧，那么动作时长约为：

```Plaintext
(1261 - 1) / 50 = 25.20 秒
```

这里使用 `帧数 - 1`，是因为从第 1 帧到第 1261 帧之间有 1260 个时间间隔。

### 6\.5\.2 K1 关节顺序

关节顺序是动作数据中最容易被忽视、但后果最严重的问题之一。

K1 CSV 中，根部位姿之后的 22 列按以下顺序排列：

|序号|关节名|
|---|---|
|1|`AAHead_yaw`|
|2|`Head_pitch`|
|3|`ALeft_Shoulder_Pitch`|
|4|`Left_Shoulder_Roll`|
|5|`Left_Elbow_Pitch`|
|6|`Left_Elbow_Yaw`|
|7|`ARight_Shoulder_Pitch`|
|8|`Right_Shoulder_Roll`|
|9|`Right_Elbow_Pitch`|
|10|`Right_Elbow_Yaw`|
|11|`Left_Hip_Pitch`|
|12|`Left_Hip_Roll`|
|13|`Left_Hip_Yaw`|
|14|`Left_Knee_Pitch`|
|15|`Left_Ankle_Pitch`|
|16|`Left_Ankle_Roll`|
|17|`Right_Hip_Pitch`|
|18|`Right_Hip_Roll`|
|19|`Right_Hip_Yaw`|
|20|`Right_Knee_Pitch`|
|21|`Right_Ankle_Pitch`|
|22|`Right_Ankle_Roll`|

如果关节顺序错了，训练程序仍可能读到一个 22 维向量，但每一维代表的身体部位已经错位。模型可能把头部数据当作肩部，把膝关节数据当作髋关节，最终动作会失真甚至完全不可用。

### 6\.5\.3 帧率与动作节奏

帧率通常写作 fps，表示 frames per second，即每秒帧数。动作数据中的帧率决定时间尺度。

如果一段动作有 300 帧：

- 以 30 fps 播放，时长约 10 秒；

- 以 50 fps 播放，时长约 6 秒。

同样的帧序列，在不同帧率下会产生不同动作速度。训练和回放时必须正确处理帧率，否则动作可能变快、变慢，或者速度估计出现偏差。

### 6\.5\.4 CSV 适合检查，不适合直接承载全部训练信息

CSV 的优点是直观。读者可以打开文件，看到每一行和每一列，也可以用 Python 快速统计列数、帧数和数值范围。

但 CSV 不适合承载全部训练信息。BeyondMimic 训练往往需要关节速度、身体部件位置、身体部件姿态、线速度和角速度等数组。这些数据是多维结构，用 CSV 表达会变得不直观，也不利于训练程序高效读取。

因此，CSV 通常作为动作整理和检查阶段的重要格式；进入训练前，还需要转换为 NPZ。

## 6\.6 NPZ 训练数据

### 6\.6\.1 为什么需要 CSV 转 NPZ

NPZ 是 NumPy 的压缩数组文件。它可以在一个文件中保存多个数组，每个数组都有名称、shape（数组维度）和 dtype（数据类型）。

CSV 转 NPZ 不只是换文件后缀。转换过程中，系统会把动作数据整理成训练程序需要的多组数组。例如，输入 CSV 中主要包含根部位姿和关节角；转换后的 NPZ 中还会包含关节速度、身体部件位置、身体部件姿态、线速度和角速度等字段。

这些字段会在训练中用于计算动作跟踪误差。机器人不仅要关节角接近参考动作，还要让身体部件在空间中的位置和运动趋势接近参考动作。

### 6\.6\.2 NPZ 常见字段

本章使用的 K1 NPZ 示例包含以下字段：

|字段|示例 shape|含义|
|---|---|---|
|`fps`|`(1,)`|帧率|
|`joint_pos`|`(1260, 22)`|每一帧的 22 个关节位置|
|`joint_vel`|`(1260, 22)`|每一帧的 22 个关节速度|
|`body_pos_w`|`(1260, 23, 3)`|世界坐标系下 23 个身体部件的位置|
|`body_quat_w`|`(1260, 23, 4)`|世界坐标系下 23 个身体部件的姿态四元数|
|`body_lin_vel_w`|`(1260, 23, 3)`|世界坐标系下 23 个身体部件的线速度|
|`body_ang_vel_w`|`(1260, 23, 3)`|世界坐标系下 23 个身体部件的角速度|

以 `joint_pos` 的 shape `(1260, 22)` 为例，第一个维度表示帧数，第二个维度表示关节数。`body_pos_w` 的 shape `(1260, 23, 3)` 表示：1260 帧，每帧 23 个身体部件，每个身体部件有 3 个位置坐标。

理解 shape 是读懂训练数据的第一步。读者不需要马上理解每个数组如何参与奖励函数，但需要能判断“这个字段表示什么维度的数据”。

### 6\.6\.3 从 NPZ 进入训练

在 BeyondMimic 训练中，NPZ 文件会作为 motion file（动作文件）被训练任务读取。训练环境加载动作文件后，会按照时间索引读取参考动作帧，并把机器人当前状态与参考动作进行比较。

训练系统会关心的问题包括：

- 当前机器人关节角是否接近参考关节角；

- 当前机器人身体部件位置是否接近参考位置；

- 当前机器人身体姿态是否接近参考姿态；

- 当前机器人速度是否接近参考速度；

- 动作跟踪过程中机器人是否保持稳定。

这些问题会在 Chapter 7 中进一步展开。本章只需要先建立一个判断：NPZ 是训练侧真正需要读取的结构化动作包。

### 6\.7\.3 关键代码含义

`inspect_motion_data.py` 的顶部说明了脚本功能和运行方式：

```Python
"""
动作数据检查工具 (inspect_motion_data.py)

【功能】
  读取 K1 动作学习流程中的 CSV 或 NPZ 动作文件, 打印数据结构摘要。
  - CSV: 查看帧数、列数、根部位姿、关节数量、动作时长和关节变化范围
  - NPZ: 查看内部数组名称、shape、dtype、帧率、帧数和动作时长
"""
```

脚本内置了 K1 的 22 个关节顺序：

```Python
K1_JOINT_NAMES = [
    "AAHead_yaw",
    "Head_pitch",
    "ALeft_Shoulder_Pitch",
    ...
    "Right_Ankle_Roll",
]
```

这组关节名用于解释 CSV 第 8 列之后的数据。如果 CSV 的关节数量为 22，脚本会认为它与 K1 关节顺序匹配，并进一步统计每个关节的变化范围。

CSV 检查逻辑在 `inspect_csv` 中：

```Python
joint_count = columns - 7
duration = (rows - 1) / resolved_fps if resolved_fps and rows > 1 else None
```

这里的 `columns - 7` 对应“总列数减去根部位姿 7 列”。如果总列数为 29，则关节数量为 22。

脚本还会统计变化幅度最大的 5 个关节：

```Python
ranges.append((max_value - min_value, name, min_value, max_value))
```

这个统计结果可以帮助读者快速判断动作主要发生在哪些关节。例如，如果肩关节和肘关节变化最大，说明动作以上肢为主；如果髋、膝、踝变化大，则说明动作包含明显下肢参与。

NPZ 检查逻辑使用 Python 标准库 `zipfile` 读取压缩包，并解析内部 `.npy` 数组头信息：

```Python
with zipfile.ZipFile(path, "r") as archive:
    for member in archive.namelist():
        if member.endswith(".npy"):
            metas[member.removesuffix(".npy")] = parse_npy_member(member, archive.read(member))
```

这种写法不依赖 NumPy，也能读出每个数组的名称、shape 和 dtype。它适合在还没有安装训练环境时先检查数据结构。

### 6\.7\.6 常见问题排查

问题 1：运行脚本后提示没有找到默认样例数据。

确认当前是否在项目根目录 `/Users/zoe/Documents/CodeX/Book` 下运行。如果脚本无法从当前位置找到 `Resources/`，可以手动指定 CSV 或 NPZ 文件路径。

问题 2：CSV 列数不是 29。

先确认文件是否为 K1 重定向动作数据。K1 示例 CSV 预期为 7 列根部位姿加 22 列关节角。如果列数不同，可能是其他机器人型号、带表头的中间文件，或上游转换结果尚未整理。

问题 3：脚本提示某一行 CSV 列数不一致。

说明 CSV 文件中存在格式异常。有些行可能缺少字段，或包含额外逗号。需要先清理 CSV，再进入训练数据转换。

问题 4：CSV 帧率显示为未知。

脚本会从文件名中的 `30fps`、`50fps` 推断帧率。如果文件名没有包含帧率，可以使用 `--fps` 手动指定。

问题 5：NPZ 中缺少 `joint_pos` 或 `fps`。

说明该 NPZ 可能不是 BeyondMimic 动作训练所需格式，或者生成流程不完整。训练前应确认 NPZ 至少包含帧率、关节位置，以及训练配置需要读取的身体状态字段。

## 6\.8 本章小结

### 6\.8\.1 本章建立的数据视角

本章从整体流程出发，说明了动作学习不是单个训练脚本，而是一条从动作来源到真机执行的工程链路。动作可以来自动捕、遥操、示教、视频或已有数据集，但进入训练系统前，都需要被表达为结构化的时间序列数据。

本章重点讲解了动作数据中的几个核心概念：帧、帧率、根部位姿、关节位置、关节速度、身体部件位置和姿态。读者应能够理解：动作不是标签，而是一段机器人身体状态随时间变化的记录。

### 6\.8\.2 与后续章节的关系

本章还说明了重定向的作用。人体动作不能直接交给 K1 执行，必须先转换到 K1 可表达的关节空间，并进一步整理为训练程序能够读取的数据格式。

CSV 适合检查动作结构，NPZ 更接近训练输入。通过 `inspect_motion_data.py`，读者已经能够查看动作文件的帧数、列数、关节数量、shape 和字段含义。
