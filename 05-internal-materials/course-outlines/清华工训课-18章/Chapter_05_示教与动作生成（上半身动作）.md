## 5\.1 从控制指令到动作数据

在 Chapter 3 和 Chapter 4 中机器人通过“控制指令”完成相应动作，比如：调用 `Move`，机器人向前移动；调用 Service，机器人执行准备、行走、半身动作或全身舞蹈。这类程序的重点是“如何正确编写控制指令的顺序结构”，它们适合建立机器人可被程序控制的基本认识。

示教关注的是另一件事：如何得到一段新的动作数据。

以“挥手”为例，从控制指令角度入手，程序可能会写成“调用一个挥手 API”。但如果从动作数据角度理解挥手，问题会变成：肩关节抬起多大角度，肘关节如何弯曲，手臂怎样往复摆动，每个关节的变化持续多长时间，关节之间如何保持协调。在这里，动作是一段随时间展开的身体状态序列。

这种认识对后续动作生成非常关键。动作生成系统要处理一系列的真实数据：每一时刻机器人各个关节处于什么状态，下一时刻如何变化，整段动作是否连续、是否稳定、是否能被真实机器人执行。示教模式是一种通过人工演示得到动作序列数据的方法，它不需要编写程序。

本章的任务：完成一次上半身动作的录制与回放。读者需要理解机器人为什么能被拖动，程序记录了什么，为什么回放时机器人能够复现刚才的动作，以及这段轨迹数据如何成为后续动作数据处理和动作生成的基础。

## 5\.2 示教模式

### 5\.2\.1 什么是示教

示教通常对应英文 Teach by Demonstration，也可以理解为“通过演示教机器执行动作”。它不需要通过代码约束每一个关节的角度，而是通过操作者手动转动关节引导机器人完成一系列目标动作，然后示教系统会记录这个过程中的关节的变化，生成后续可以回放的动作轨迹。

对人形机器人来说，示教是一种很直观的动作采集方式。假设希望机器人完成一个简单的上半身展示动作，可以先让机器人进入可拖动状态，然后用手带动机器人的手臂、肩部或上身完成动作。录制程序会在这个过程中持续记录关节状态。录制结束后，机器人可以读取刚才保存的轨迹文件，并按时间顺序复现这段动作。

示教的优势在于快速获得可用动作样本。对于挥手、摆臂、简单展示动作这类上半身动作，人工拖动往往比从零开始不断通过调试确定每个关节角度更直接。后续如果需要把动作整理为数据集、转换成训练格式，或用于动作生成模型，示教得到的轨迹就可以作为原始数据。

示教也有缺点，比如：人工拖动得到的动作不一定平滑，动作幅度过大可能导致动作“回放”时不稳定，录制时节奏不均匀也会影响效果。因此，本章只要求完成一段简单、缓慢、连续的上半身动作，不追求复杂的全身舞蹈。

### 5\.2\.2 零力矩拖拽

零力矩拖拽对应英文 ZeroTorqueDrag。这里的“零力矩”不是说机器人完全没有任何物理约束，而是指关节电机不再像正常运动控制时那样主动保持刚性输出，关节进入更容易被外力带动的状态。进入该状态后，操作者可以用手带动机器人的上半身关节完成动作。

普通控制状态下，机器人会努力维持当前姿态或执行控制器给出的目标，手动掰动关节会遇到明显阻力，也可能与控制器输出发生冲突。零力矩拖拽则是为人工摆动准备的状态：关节更顺从，操作者可以较轻地改变关节姿态，录制程序也可以在这个过程中记录关节变化。

零力矩拖拽也是本章最需要注意安全的环节。进入零力矩后，机器人关节刚性降低，身体可能因为外力或重心变化产生晃动。输入 `zt` 前应先扶稳机器人，或将机器人放在合适支架上。拖动上半身动作时，应避免突然用力、避免大幅度扭转躯干，也不要强行拉到机械极限位置。如果出现异常，应立即按下背部 `STAND` 按钮，让机器人回到可控状态。

从程序角度看，零力矩拖拽由 SDK 接口 `ZeroTorqueDrag(True)` 打开，由 `ZeroTorqueDrag(False)` 关闭。本章代码在结束录制和程序退出时都会尝试关闭零力矩拖拽，避免机器人停留在不期望的柔顺状态。

### 5\.2\.3 示教的基本流程

基础示教流程可以分成六步。

第一步，机器人进入站立准备状态。程序启动后会自动切换到 `Walking`，让机器人处在可操作的站立状态。

第二步，进入零力矩拖拽。程序调用 `ZeroTorqueDrag(True)`，机器人关节进入可被人工带动的状态。

第三步，开始录制。程序调用 `RecordTrajectory(True)`，系统开始记录关节随时间变化的轨迹。

第四步，人工拖动上半身完成动作。此时动作要尽量缓慢、连续、幅度适中。拖动的过程就是动作数据产生的过程。

第五步，结束录制。程序调用 `RecordTrajectory(False)` 停止记录，同时关闭零力矩拖拽，并让机器人回到 `Walking`。

第六步，回放轨迹。程序调用 `ReplayTrajectory` 读取系统保存的轨迹文件，机器人按刚才记录的时间顺序复现动作。



## 5\.3 关节空间与动作轨迹

### 5\.3\.1 关节空间

关节空间对应英文 Joint Space。人形机器人是一个由多个可转动关节组成的身体，手臂可以抬起、摆动、弯曲，肩、肘、腕等关节在不同时间处于不同角度，这些共同组成关节空间。

机器人手臂从低处抬到高处的行为，从关节空间看，会看到多个关节角度同时变化。每个时刻，机器人都可以用一组关节状态描述。例如，上半身动作涉及肩部、肘部、腕部和躯干等相关关节，这些关节的当前状态就构成了该时刻机器人上半身的一帧姿态。

关节空间直接对应机器人动作的客观数据。后续无论是保存动作、分析动作，还是训练动作生成模型，本质上都是“每个关节在每个时刻是什么状态”这一层数据。

### 5\.3\.2 姿态与轨迹

单个时刻的关节状态可以称为一帧姿态。它描述的是某一瞬间机器人身体的样子。例如，左肩抬高、右肘弯曲、躯干略微前倾，这些共同构成一帧姿态。

轨迹对应英文 Trajectory。轨迹是一组姿态按照时间顺序排列形成的序列。一个动作的本质，就是机器人从第一帧姿态开始，经过一系列中间姿态，最终到达结束姿态。

可以用下面的简化形式理解动作轨迹：

```Plaintext
第 1 帧: [肩关节角度, 肘关节角度, 腕关节角度, ...]
第 2 帧: [肩关节角度, 肘关节角度, 腕关节角度, ...]
第 3 帧: [肩关节角度, 肘关节角度, 腕关节角度, ...]
...
第 N 帧: [肩关节角度, 肘关节角度, 腕关节角度, ...]
```

如果只保存第一帧和最后一帧，机器人只能知道起点和终点，却不知道中间如何过渡。示教录制记录了从起点到终点之间连续变化的过程。回放时，机器人不是瞬间跳到某个姿势，而是按照轨迹中的顺序逐步复现动作。

### 5\.3\.3 上半身动作的轨迹特点

为什么围绕“上半身动作”进行内容设计呢？这是因为人形机器人的身体控制本身存在明显的分层。对于 K1 这样的双足人形机器人，下半身承担站立、重心保持、支撑切换和步态稳定等任务；上半身则更多负责手臂姿态、展示动作、交互动作和部分躯干协同动作。

从控制系统角度看，下半身不是普通的“几个关节角度一起变化”。只要动作涉及腿部、脚底接触或身体重心移动，控制器就需要持续处理重心位置、支撑面、足底接触力、姿态扰动和关节力矩限制。机器人从双脚站立到迈步、转身或全身舞蹈，中间不仅是轨迹变化，还包含平衡状态和接触状态的变化。这个过程更复杂，通常需要全身运动控制、步态控制或模型预测控制等机制支持，不能简单理解为“人工拖动腿部并记录下来，再原样回放”。

本章的示教程序采用的是下半身保持站立和平衡控制，上半身关节进入适合人工拖动和轨迹记录的状态。也就是说，示教模式并不是把整台机器人完全放开，而是在保持底层稳定控制的前提下，开放上半身动作给操作者演示。这样得到的轨迹主要描述上半身关节如何随时间变化，而不是重新生成一套完整的双足平衡控制策略。

上半身动作通常具有三个特点。

第一，多个关节协同变化。一个挥手动作不只是手腕在动，肩部、肘部和躯干姿态都会影响最终效果。

第二，动作节奏很重要。同样的抬手动作，慢慢抬起和快速甩起会产生完全不同的观感，也会对机器人稳定性产生不同影响。

第三，轨迹连续性很重要。示教时如果突然用力、停顿过多或反复拉回，录制出来的轨迹也会包含这些不连续变化。回放时，机器人会尽量复现记录到的轨迹，因此录制动作本身越平顺，回放效果通常越自然。

本章实践时，建议录制一段简单动作，例如单臂抬起再放下、双臂缓慢张开再收回，或一只手臂做小幅摆动。动作幅度不需要大，关键是让读者看清“人工拖动动作”如何变成“可回放轨迹”。

## 5\.4 动作数据与时间序列

### 5\.4\.1 连续动作与离散采样

人工拖动机器人时，动作在物理世界中是连续发生的。手臂从低处移动到高处，中间会经过无数个细微状态。但计算机保存数据时，不可能保存无限多个瞬间，只能按照一定频率进行采样。

采样可以理解为“每隔一小段时间记录一次机器人关节状态”。如果采样足够密集，连续动作就会被近似表示为很多帧离散数据。每一帧记录一个时刻的关节状态，多帧连起来就形成了动作轨迹。

示教程序中的 `RecordTrajectory(True)` 开始记录轨迹，`RecordTrajectory(False)` 停止记录轨迹。中间这段时间内，系统会持续采集关节状态，并写入用于回放的轨迹文件。

### 5\.4\.2 时间序列

时间序列对应英文 Time Series。动作数据是一种典型时间序列，因为它不仅包含每一帧的数值，还依赖这些数值的先后顺序。

如果把同样的关节姿态打乱顺序，动作就会完全改变。如果把每帧之间的时间间隔拉长，动作会变慢；如果把间隔缩短，动作会变快。也就是说，动作数据包含两个层面的信息：

第一，空间层面的关节状态。它说明机器人每一帧是什么姿态。

第二，时间层面的顺序和节奏。它说明这些姿态以什么顺序、什么速度发生。

这也是为什么动作生成不能只生成一组关节角。真正可执行的动作需要生成一段有时间顺序的关节状态序列。

### 5\.4\.3 录制时长与回放节奏

本章代码会记录一次录制持续了多少秒。这个时长不是动作数据本身，但它对回放控制有实际意义。

在 `teach.py` 中，输入 `rec` 时记录开始时间，输入 `f` 时计算当前时间与开始时间的差值：

```Python
recording = True
rec_start = time.time()
```

```Python
last_record_seconds = time.time() - rec_start
```

回放时，程序根据上一次录制时长再增加几秒缓冲时间：

```Python
wait = (last_record_seconds + REPLAY_BUFFER) if last_record_seconds else DEFAULT_REPLAY_WAIT
client.ReplayTrajectory(_TRAJ)
time.sleep(wait)
client.ChangeMode(b1.RobotMode.kWalking)
```

这样做的原因是：`ReplayTrajectory` 发出回放请求后，机器人需要一段时间完成动作。如果程序刚发出回放请求就立即切换回其他状态，动作可能还没有执行完就被打断。录制时长可以作为估算回放等待时间的依据，`REPLAY_BUFFER` 则用于给动作末尾留出余量。

### 5\.4\.4 动作数据与后续动作生成

本章示教生成的轨迹文件路径为：

```Plaintext
/opt/booster/Gait/bin/joint_position.txt
```

在本章中，读者只需要知道这是系统用于保存和回放示教轨迹的文件。程序调用 `ReplayTrajectory(_TRAJ)` 时，机器人会从这个路径读取刚才录制的轨迹并执行回放。

后续动作生成章节会进一步讨论动作数据的组织方式，例如如何把轨迹转换为更适合分析和训练的数据格式，如何理解每一帧中的关节字段，如何处理 CSV、NPZ 等数据文件。CSV 是逗号分隔值文件，适合表格化查看；NPZ 是 NumPy 的压缩数组格式，适合保存训练程序读取的多维数组。

因此，本章的示教不是孤立功能。它是动作生成主线的起点之一：先得到一段真实轨迹，再进一步理解轨迹如何被表达、处理和用于模型训练。

## 5\.5 SDK 示教接口与实践案例：录制并回放上半身动作

K1 的 SDK 提供了示教相关接口，使 Python 程序可以完成零力矩拖拽、轨迹录制和轨迹回放。本节先说明本章用到的接口含义，然后进入 `teach.py` 实践案例。

### 5\.5\.1 SDK 中的示教相关能力

本章程序主要使用四类 SDK 能力。

|接口|作用|
|---|---|
|`ChangeMode`|切换机器人运动模式|
|`ZeroTorqueDrag`|打开或关闭零力矩拖拽|
|`RecordTrajectory`|开始或结束轨迹录制|
|`ReplayTrajectory`|回放已录制的轨迹文件|

`ChangeMode` 用于让机器人在示教前后回到合适状态。程序启动后调用 `ChangeMode(b1.RobotMode.kWalking)`，让机器人进入站立就绪状态。程序退出时尝试调用 `ChangeMode(b1.RobotMode.kPrepare)`，让机器人回到准备状态。

`ZeroTorqueDrag(True)` 用于进入零力矩拖拽，`ZeroTorqueDrag(False)` 用于退出零力矩拖拽。示教动作只应在拖拽状态下人工摆动，录制结束后需要及时关闭。

`RecordTrajectory(True)` 用于开始录制，`RecordTrajectory(False)` 用于停止录制。录制期间，系统会记录机器人关节随时间变化的轨迹。

`ReplayTrajectory(_TRAJ)` 用于回放指定路径中的轨迹文件。本章使用系统固定轨迹文件 `_TRAJ`：

```Python
_TRAJ = "/opt/booster/Gait/bin/joint_position.txt"
```

从接口关系看，`teach.py` 并不是复杂程序。它做的事情是把几个示教接口按安全顺序组织起来，并提供一个命令行交互入口，让读者能够手动控制录制和回放过程。

### 5\.5\.2 实践目标

本实践完成一次上半身动作的录制与回放。完成后，读者应能理解以下问题：

1. 机器人如何进入可拖动状态；

2. 程序如何开始和结束轨迹录制；

3. 录制时长为什么会影响回放等待；

4. `replay` 为什么能够让机器人复现刚才的动作；

5. 程序退出时为什么要关闭录制和零力矩拖拽。

本案例只要求录制一段简单动作，例如手臂抬起后放下，或双臂缓慢展开后收回。动作应保持缓慢、连续、幅度适中。

### 5\.5\.4 关键代码含义

`teach.py` 的开头使用说明块描述功能、运行方式和操作流程。

```Python
"""
动作示教 · 录制 + 回放 (teach.py)

【功能】
  使用"零力矩拖拽"的方式手动带动机器人完成一段上半身动作并录制,
  再通过轨迹回放接口让机器人复现刚才录制的动作。

【运行】
  python3 teach.py

【操作流程】
  录制:  zt -> rec -> 手动拖动上半身动作 -> f
  回放:  replay
"""
```

程序随后定义轨迹文件路径和回放等待参数：

```Python
_TRAJ = "/opt/booster/Gait/bin/joint_position.txt"
DEFAULT_REPLAY_WAIT = 30
REPLAY_BUFFER = 3
```

`_TRAJ` 是系统保存和回放示教轨迹的固定路径。`DEFAULT_REPLAY_WAIT` 是没有本次录制时长可参考时的默认等待时间。`REPLAY_BUFFER` 用于在录制时长基础上多等待几秒，避免动作末尾被提前打断。

程序初始化通信时，先读取命令行参数：

```Python
argv = sys.argv[1:]
net_if = argv[0] if argv else "127.0.0.1"
robot_name = argv[1] if len(argv) >= 2 else None
```

默认情况下，直接运行 `python3 teach.py` 即可。只有在需要指定通信网卡或机器人名称时，才在命令后追加参数。这里的参数是普通 Python 程序参数，不是 ROS2 参数。

接着，程序初始化 SDK 通信通道和运动控制客户端：

```Python
b1.ChannelFactory.Instance().Init(0, net_if)
client = b1.B1LocoClient()
if robot_name:
    client.InitWithName(robot_name)
else:
    client.Init()
```

`B1LocoClient` 是本章与机器人运动控制接口交互的客户端对象。后续切换模式、进入零力矩拖拽、录制轨迹和回放轨迹，都通过这个对象完成。

程序启动后先进入 `Walking`：

```Python
client.ChangeMode(b1.RobotMode.kWalking)
```

这里的 `Walking` 可以理解为机器人站立就绪并具备运动控制能力的状态。示教前先让机器人进入稳定状态，有利于后续进入拖拽和录制流程。

`teach.py` 的主体是一个命令行循环：

```Python
while True:
    raw = input("teach> ").strip()
    cmd = raw.lower()
```

每次输入一条命令，程序根据命令执行不同接口。`zt` 对应进入零力矩拖拽：

```Python
client.ZeroTorqueDrag(True)
```

`rec` 对应开始录制：

```Python
client.RecordTrajectory(True)
recording = True
rec_start = time.time()
```

这里的 `recording` 用于标记当前是否处于录制状态，`rec_start` 用于记录录制开始时间。

`f` 对应结束录制、关闭零力矩拖拽并恢复站立：

```Python
client.RecordTrajectory(False)
client.ZeroTorqueDrag(False)
client.ChangeMode(b1.RobotMode.kWalking)
```

如果程序确认刚才处于录制状态，还会计算录制持续时间：

```Python
last_record_seconds = time.time() - rec_start
recording = False
```

`replay` 对应轨迹回放：

```Python
wait = (last_record_seconds + REPLAY_BUFFER) if last_record_seconds else DEFAULT_REPLAY_WAIT
client.ReplayTrajectory(_TRAJ)
time.sleep(wait)
client.ChangeMode(b1.RobotMode.kWalking)
```

这段逻辑的重点不是 `sleep` 本身，而是“回放是一个需要持续时间的动作”。程序发出回放请求后，需要给机器人足够时间完成轨迹执行，然后再切换状态。

最后，程序在退出时做兜底处理：

```Python
if recording:
    client.RecordTrajectory(False)
client.ZeroTorqueDrag(False)
client.ChangeMode(b1.RobotMode.kPrepare)
```

这段逻辑用于处理用户按下 `Ctrl+C` 或输入 `quit` 的情况。即使程序不是按完整流程退出，也尽量关闭录制、退出零力矩拖拽，并让机器人回到准备状态。

### 5\.5\.6 常见问题排查

问题 1：输入 `zt` 后机器人无法拖动。

先确认程序是否已经成功初始化并进入 `Walking`。如果 SDK 通信没有建立，`ZeroTorqueDrag(True)` 可能不会生效。还要确认输入的是完整命令 `zt`，而不是在程序启动前直接在 shell 中输入。

问题 2：进入零力矩拖拽后机器人晃动明显。

立即扶稳机器人，停止继续拖动。如果状态不可控，按下背部 `STAND` 按钮让机器人回到可控状态。后续重新录制时，应缩小动作幅度，避免突然拉动上半身或让机器人重心明显偏移。

问题 3：输入 `rec` 后不确定是否正在录制。

`teach.py` 会在执行 `rec` 后打印开始录制提示。只有在输入 `rec` 之后、输入 `f` 之前的动作才会被记录。输入 `zt` 只是进入可拖动状态，并不等于开始录制。

问题 4：输入 `f` 后没有得到想要的动作。

`f` 只负责停止录制和恢复状态，不会立即回放。需要继续输入 `replay` 才会看到机器人复现刚才的动作。

问题 5：输入 `replay` 后机器人没有明显动作。

常见原因是录制阶段没有真正移动关节，或者录制时间太短。重新执行 `zt -> rec -> 拖动上半身动作 -> f -> replay`，并确保 `rec` 之后再开始完成动作。

问题 6：回放动作不完整。

如果录制动作较长，而程序等待时间不足，可能出现回放末尾被状态切换打断的情况。可以适当增大代码中的 `REPLAY_BUFFER`，让回放后多等待几秒再切回 `Walking`。

问题 7：程序退出后机器人仍处于不期望状态。

`teach.py` 在退出时会尝试关闭录制、关闭零力矩拖拽并进入 `Prepare`，但异常中断或通信失败时仍可能需要人工处理。此时应按下背部 `STAND` 按钮，使机器人回到可控状态，再重新运行程序。

问题 8：运行时提示找不到 SDK 模块。

如果终端提示无法导入 `booster_robotics_sdk_python`，说明当前 Python 环境没有找到 K1 SDK。应确认程序在 K1 机器人环境中运行，并确认 SDK 已按机器人系统环境正确安装。

问题 9：指定通信参数后仍无法连接机器人。

`teach.py` 支持在命令后追加普通 Python 参数：

```Bash
python3 teach.py <net_if> <robot_name>
```

`net_if` 对应通信接口参数，`robot_name` 对应需要按名称初始化的机器人。普通情况下不需要追加参数，直接运行 `python3 teach.py` 即可。

## 5\.6 本章小结

### 5\.6\.1 示教的本质

本章完成了从控制指令到动作数据的过渡。通过 SDK 或 ROS2 调用已有动作，重点是让机器人执行某个已经存在的能力；通过示教录制动作，重点是产生一段新的轨迹数据。

示教的核心过程是：进入零力矩拖拽，让机器人可以被人工带动；开始轨迹录制，让系统记录关节状态随时间的变化；结束录制并回放，让机器人按记录到的轨迹复现动作。

在这个过程中，动作不再被看作一个命令，而是被看作一段时间序列。每一帧记录一组关节状态，多帧按时间顺序排列后形成轨迹，轨迹再被机器人执行为可观察的动作。

### 5\.6\.2 与后续章节的关系

本章建立了动作生成主线的几个基础概念：示教、零力矩拖拽、关节空间、动作轨迹和时间序列。它们会在后续动作数据表达、动作数据转换、模型训练和真机部署中反复出现。

后续章节会进一步讨论动作数据如何被组织为更明确的数据结构，如何从轨迹文件进入训练数据，如何在仿真环境中查看动作效果，以及如何把动作生成结果迁移到真实机器人上执行。理解本章的录制和回放闭环，是进入后续动作生成系统的前提。
