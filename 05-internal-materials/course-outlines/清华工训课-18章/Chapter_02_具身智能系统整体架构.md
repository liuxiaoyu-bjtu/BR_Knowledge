# Chapter\_02\_具身智能系统整体架构

# Chapter 02｜具身智能系统整体架构

## 2\.1 具身智能系统

具身智能强调智能体通过身体与环境交互来完成任务。从工程实现来看，人形机器人并非单一的软件程序或独立的 AI 算法模型，而是由物理本体、传感器、控制器、计算平台、软件通信网络与物理环境共同组成的具身智能系统（Embodied Intelligence）。

传统 AI 的处理对象多为静态的数字化数据（如文本、图像或结构化表格），而具身智能系统直接面向带有物理约束的真实物理环境，强调智能体通过身体与环境交互来完成任务。与传统 AI 相比，具身智能系统的开发面临以下工程挑战：

1. **传感器输入的不确定性**：真实环境中的光照剧变、遮挡、反射以及相机运动导致的画面模糊，会导致感知数据持续存在噪声与偏差。

2. **物理控制的连续性与时延**：指令下发到关节电机执行存在物理通信延迟，电机输出扭矩受非线性动力学、地面摩擦力及姿态失稳的制约。

3. **环境反馈的动态耦合**：机器人的物理动作会即时改变自身的传感器视角与环境状态，形成“动作 ➔ 环境改变 ➔ 姿态变化 ➔ 新感知”的强耦合闭环。

4. **安全边界与可恢复性**：系统的输出并非单纯的数值判断，而是具体的**物理动作**。算法故障不仅会导致任务失败，还可能引发机器跌落、硬件过载或碰撞等安全风险。

因此，具身智能开发的核心要求在于：构建能够在不确定性环境中，持续输出可安全执行、可状态恢复、可离线/在线验证的物理行为系统。这要求开发者超越孤立的“算法开发”视角，从硬件接口、数据通信、控制响应到决策逻辑构建完整的闭环系统架构。

可以用下面的方式理解两类系统的差异：

```Plaintext
传统 AI 系统：
输入数据 → 模型计算 → 输出结果

具身智能系统：
感知环境 → 理解状态 → 控制身体 → 执行动作 → 接收反馈
```

对于 Booster K1 这样的人形机器人来说，具身智能系统至少包含四个关键特征。

第一，机器人有可执行动作的身体结构。K1 不是只有摄像头和计算程序，它有头部、躯干、手臂、腿部和足部。动作最终要通过关节、电机和身体结构表现出来。

第二，机器人需要感知自身和环境。相机可以获取外部图像，IMU 可以反映姿态变化，关节状态可以反映机器人身体当前处于什么位置。这些信息共同构成机器人理解环境和自身状态的基础。

第三，机器人需要把上层任务转化为身体动作。程序里的一条“向前移动”指令，最终会变成步态控制、关节协调和身体平衡问题。越接近真实机器人，越不能把控制理解成简单的数值输出。

第四，机器人需要在任务中持续反馈和调整。足球任务中，足球可能滚动，机器人可能偏离目标，相机可能短时间丢失目标，动作执行后身体姿态也可能发生变化。系统必须根据新的状态继续调整，而不是只执行一次固定流程。

因此，学习 K1 不能只从“调用某个接口”开始理解。接口是入口，系统才是本体。后续每一章的代码、模型和实验都应该放回系统中理解：它接收什么输入，输出什么数据，控制哪个模块，又如何服务最终任务。

本课程中的两个核心任务主线都体现了具身智能系统的特点。动作生成主线关注动作如何从数据和模型进入机器人身体；足球任务主线关注机器人如何从视觉输入出发，经过位置理解和行为组织，完成追球与踢球。这两条主线都不是单点技术，而是系统链路。

## 2\.2 K1 系统分层

为了理解 Booster K1 的系统结构，可以先把它分成五个层级：

```Plaintext
硬件层 → 控制层 → 计算层 → 软件层 → 行为层
```

|层级|主要内容|作用|
|---|---|---|
|硬件层|机器人本体、关节、电机、相机、IMU、电源|提供身体结构、感知入口和动作执行能力|
|控制层|底层控制器、步态控制、模式切换、关节控制|把上层运动意图转化为可执行运动|
|计算层|板载计算平台、系统环境、运行进程|承载视觉、行为、训练部署和应用程序|
|软件层|SDK、ROS2、Python 程序、模型推理节点|组织程序模块和数据通信|
|行为层|状态机、行为树、任务逻辑、动作触发|决定机器人在任务中什么时候做什么|

硬件层提供身体基础。没有相机，机器人无法获得足球图像；没有腿部关节和足部结构，机器人无法完成追球、停稳和踢球；没有电源和控制器，机器人无法持续执行任务。

控制层负责让身体可控。人形机器人控制的难点在于，运动不是简单移动一个点，而是全身多关节协调。读者在课程中直接接触的多是上层控制接口，但这些接口背后依赖底层控制层来维持姿态、执行步态和保护机器人。

计算层负责运行上层程序。相机图像读取、YOLO 目标检测、动作数据处理、行为逻辑判断、日志记录等任务，都需要计算平台承载。对于教育版或专业版 K1，板载计算平台可以支持更复杂的视觉和模型推理任务。

软件层是课程中最常接触的开发层。SDK 提供机器人能力调用入口，ROS2 提供模块通信机制，Python 程序把感知、控制、动作和行为组织为可运行节点。

行为层把单个能力组织为完整任务。机器人会走路、会转头、会识别足球、会执行动作，但这些能力本身还不是“自主追球”或“视觉踢球”。行为层负责根据当前状态安排执行顺序，例如搜索足球、对准目标、靠近足球、停稳、触发踢球。

在 Booster K1 系统架构中，板载计算平台是承载上层软件与算法运行的算力核心。与常规通用计算机不同，该计算平台通过硬件总线与板载网络，直接与机器人的深度相机、IMU 及底盘控制器相连，构建了低延迟的数据交互链路。计算平台集中承载了以下核心系统任务：

1. **操作系统与中间件运行**：运行 Linux 机器人操作系统及 ROS2 通信底座，管理多节点进程与消息调度； 

2. **感知算法实时推理**：接收深度相机数据流，实时解算 YOLO 目标检测模型与 3D 空间坐标变换； 

3. **策略部署与行为控制**：加载足球检测等视觉模型与行为树逻辑，完成实时控制指令的计算与下发； 

4. **系统数据流监控**：处理运行日志、话题数据转发及安全状态监听。

可以把硬件与计算基础理解为两类支撑：

```Plaintext
硬件身体：相机、关节、电机、躯干、腿部、足部
计算平台：系统环境、ROS2、模型推理、应用程序、日志与调试
```

硬件身体决定机器人能否完成动作，计算平台决定上层程序能否实时读取数据、做出判断并发送指令。两者之间互相约束。例如：

- 相机安装位置会影响足球在图像中的位置和可见范围；

- 计算平台性能会影响 YOLO 模型的推理速度；

- 腿部结构和控制能力会影响追球速度和停稳效果；

- 机器人当前模式会影响控制指令是否能执行；

- 地面材质和周围空间会影响动作执行安全。

因此，后续写代码时不能只问“程序有没有运行”，还要观察机器人是否处于合适模式，传感器数据是否正常，动作是否安全，计算负载是否影响实时性。

### 2\.2\.2  控制与软件接口

硬件和计算平台提供了基础保障，在实际开发时，还需要控制接口和软件模块。

控制层负责把上层程序的运动意图转化为机器人可以执行的动作。例如，程序希望机器人前进、转向、停止、抬头等动作，这些意图都需要经过控制系统才能作用到机器人身体上。

人形机器人在行走时需要协调多条腿部关节，保持身体平衡，处理姿态变化，并在异常情况下进入保护状态。K1 具备的阻尼模式、准备模式、行走模式和保护模式，体现了机器人控制系统对安全和状态切换的要求。

在课程开发中，读者不会直接从底层电机控制开始，而是通过已经封装好的软件接口进入上层应用开发。主要入口包括 SDK 和 ROS2。

SDK 提供了较直接的能力调用方式。通过 SDK，可以调用机器人已有能力，例如切换模式、执行动作、控制运动等。对于入门阶段来说，SDK 适合建立“程序可以控制机器人”的第一层认识。

ROS2 则更适合组织多模块系统。ROS2 中的不同节点可以分别负责图像获取、目标检测、位置计算、控制输出和行为判断。节点之间通过标准通信机制交换数据。这样，一个复杂任务就可以拆成多个相对清晰的模块，而不是全部写在一个程序里。

在本课程中，SDK 和 ROS2 不是二选一的关系。它们承担不同角色：

|工具|更适合解决的问题|在课程中的作用|
|---|---|---|
|SDK|调用机器人已有能力|快速完成基础控制、动作调用和模式相关操作|
|ROS2|组织多个程序模块协作|建立视觉、控制、行为之间的数据通信|

后续 Chapter 3 会从机器人控制基础和 SDK 入手，让读者掌握最基本的运动控制能力。Chapter 4 会进一步引入 ROS2 通信与控制接口，让读者理解如何把单个控制能力放进机器人系统中。

本节只需知道：K1 的上层应用开发不是直接操作所有底层硬件，而是通过控制接口和软件通信机制，把感知结果、控制指令、动作调用和行为逻辑连接起来。

## 2\.3 感知、动作与行为

在 Booster K1 开发体系中，感知、控制、动作与行为是四个核心概念。虽然它们在项目中高度协同，但在工程架构上具备明确的边界与解耦契约。明确这四者的区别，有助于在后续开发与故障排查时快速定位模块层级。

1. 感知

感知的工程职责是“从传感器原始数据中提取机器人与环境的状态信息”。

- 物理输入：相机图像流、IMU 姿态数据、关节编码器反馈。 

- 信息输出：目标物体识别框、三维空间坐标 \(x, y, z\)、机器人自身姿态角等。 

- 模块特性：感知模块只进行数据的采集、处理与坐标变换，不直接产生物理运动指令。比如，在足球任务中，感知系统从相机采集的图像中识别足球，并输出足球的位置（检测框）和置信度等信息。感知模块本身并不驱动机器人做任何位移。

2. 控制

控制的工程职责是“驱动电机执行运动并维持身体物理稳定”。

- 物理输入：上层下发的期望运动速度或目标姿态指令。 

- 信息输出：下发至各个关节伺服电机的驱动信号（脉冲/扭矩/角度）。 

- 模块特性：控制层屏蔽了复杂的关节动力学细节，负责步态解算、双足平衡调节与防跌倒保护，确保机器人按照指令安全平稳地移动。  比如，当系统知道足球在左前方时，控制模块需要把这些信息转化为运动指令，具体表现为调整朝向、向前靠近、降低速度或停稳。

3. 动作

动作的工程职责是“表达、生成与执行特定的高维肢体姿态序列”，**动作**比**控制**指令更强调身体姿态随时间的变化。

- 物理输入：离线采集的示教轨迹数据，或基于强化学习训练导出的策略模型。 

- 信息输出：随时间演化的全身关节角度与姿态变化序列。 

- 模块特性：动作可以是定型的开环轨迹（如打招呼、固定踢球动作），也可以是基于模型解算的动态策略。它解决的是身体“如何协调做出特定复杂姿势”的问题。 

4. 行为

动作的工程职责是“调度多模块协同，将单个能力组织为闭环任务”

- 物理输入：感知模块输出的目标位置、系统当前运行状态及逻辑判定条件。

- 信息输出：向控制层或动作模块下发的执行状态切换指令。

- 模块特性：行为层本身不处理图像，也不直接算步态，而是作为系统“脑中枢”安排执行顺序。例如在足球任务中，行为层依据感知数据，依次调度系统进入“寻找足球 ➔ 靠近对准 ➔ 减速停稳 ➔ 触发踢球”的动态逻辑切换。

```Plaintext
没有看到足球 → 搜索
看到足球但位置偏左 → 调整朝向
足球距离较远 → 向前靠近
足球进入踢球区域 → 停稳
满足触发条件 → 踢球
```

可以把四者关系理解为：

```Plaintext
感知提供环境信息
控制改变机器人位置和姿态
动作表现具体身体能力
行为决定任务执行顺序
```

在自主追球任务中，感知模块识别足球，控制模块让机器人靠近足球，行为逻辑决定搜索、跟踪和停稳的切换。在视觉踢球任务中，动作能力和行为逻辑进一步结合，系统需要在合适位置触发踢球动作或策略。

在动作生成主线中，“动作”的含义会进一步展开。后续章节会把动作看作数据、轨迹、模型和部署结果。

## 2\.4 K1 系统数据流

系统架构不是模块名称的堆叠，而是数据和指令如何在模块之间流动。理解数据流，才能理解后续代码为什么要拆成不同节点、为什么要定义消息格式、为什么要观察话题输出。

相机图像是视觉系统的输入，它是由来自 K1 头部的相机采集的，通过 ROS2 图像话题进入程序。

目标检测负责从图像中找到足球。经 YOLO 模型处理会输出检测框、类别、置信度和中心点等信息。目标检测主要解决“图像中哪里有足球”的问题。

位置理解负责把 YOLO 检测结果转换成更适合控制使用的信息。例如，足球在图像左侧还是右侧，离机器人近还是远，是否已经进入可踢区域。这个阶段是从视觉结果走向控制的关键桥梁。

追球控制根据足球位置计算机器人运动。机器人可能需要转向、前进、减速或停止。控制输出必须考虑安全和稳定，不能简单地把误差直接变成很大的速度指令。

停稳与踢球判断属于行为层。机器人接近足球后，系统还需要判断是否满足踢球条件。过早可能踢不到球，过晚可能错过位置，机器人未停稳时触发动作也可能影响执行效果。

动作或策略执行是任务链路的最后阶段。机器人会执行踢球动作或进入视觉踢球策略。执行完成后，系统还需要观察结果，例如足球是否被踢出、机器人是否保持稳定、是否需要重新搜索目标。

## 2\.5 本章小结

本章从系统角度介绍了 Booster K1 人形机器人应用实践课程的基础框架。

首先，K1 应被理解为一个具身智能系统，而不是一台只靠单个程序控制的设备。机器人任务会同时涉及身体结构、传感器、控制器、计算平台、软件模块和真实环境反馈。

其次，K1 可以从硬件层、控制层、计算层、软件层和行为层五个层级理解。硬件层提供身体和传感器基础，控制层让身体可控，计算层承载上层程序，软件层组织模块通信，行为层把多个能力组合成完整任务。

再次，本章区分了感知、控制、动作和行为。感知让机器人获得环境信息，控制让机器人移动身体，动作体现具体身体能力，行为决定任务执行顺序。后续章节中的相机数据、YOLO 检测、追球控制、动作训练、行为树和视觉踢球，都可以放回这几个概念中理解。

最后，本章建立了两条系统数据流。足球任务数据流从相机图像出发，经过目标检测、位置理解、追球控制和踢球判断，最终进入动作或策略执行。动作生成数据流从动作数据出发，经过训练、仿真验证、模型导出和真机执行，最终形成动作能力。

进入下一章后，课程将从整体架构转入具体控制开发。读者将开始理解 K1 的控制链路，学习如何通过 SDK 调用基础运动能力，并把系统架构中的“控制层”落到实际程序和机器人运行现象中。
