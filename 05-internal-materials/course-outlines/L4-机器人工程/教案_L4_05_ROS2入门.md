# 教案\_L4\_05\_ROS2入门

|**基本信息**|||
|---|---|---|
|**课  题**|**ROS2 入门：机器人系统的通信语言**||
|**适用学段**|高中\(机器人特色校\) / 大学入门||

|**教学目标**|||
|**知识与技能**|1\. 区分 Ubuntu 与 ROS2：Ubuntu 是真正的操作系统（管理硬件与基础进程），ROS2 是跑在操作系统之上的「机器人软件框架 / 中间件」。<br>2\. 理解机器人系统天然是多模块组成的——感知 / 决策 / 行动 不能挤在一个程序里，需要统一的通信规则。<br>3\. 掌握 ROS2 三个核心概念：Node（独立功能模块）、Topic（持续广播的数据通道，Publish / Subscribe）、Service（一次请求一次应答，Request / Response）。<br>4\. 能区分 Topic 与 Service 各自的适用场景：图像 / IMU / 检测结果用 Topic；切模式 / 查询状态 / 触发动作用 Service。<br>5\. 掌握三条基础 ROS2 CLI 命令：ros2 node list / ros2 topic list / ros2 service list，以及 ros2 topic info 深入观察。<br>6\. 能在 K1 上完成 /greeting 三终端最小通信实验：ros2 topic pub 发布 \+ ros2 topic echo 订阅 \+ ros2 topic info 验证 Pub / Sub 数。<br>7\. 理解话题通信的「解耦」本质——发布者和订阅者不需要互相知道对方是谁，只需约定同名话题与同型消息。||
|**过程与方法**|1\. 通过「单程序 vs 多模块」「乱线 vs 通信总线」两组直观对比，建立「为什么需要 ROS2」的认知动机。<br>2\. 通过校园场景类比（节点 = 部门、话题 = 校园广播、服务 = 去办公室提问），把抽象通信机制落到学生熟悉的生活情境中。<br>3\. 通过 4 个实践（list 三件套 \+ /greeting 实验），让学生第一次看到机器人系统内部，建立「实操观察」的工程习惯。<br>4\. 通过填空题 \+ 判断题 \+ 分类题三种形成性评估，及时检查概念到位情况。<br>5\. 通过故障排查环节，培养「按层定位、不凭直觉乱改」的工程思维。||
|**情感态度与价值观**|1\. 体会「机器人是协作系统」而不是「一个大程序」——理解工程系统的复杂性与模块化的优雅。<br>2\. 通过看到 K1 上正在运行的真实节点 / 话题 / 服务，建立「我面对的不是黑盒」的工程自信。<br>3\. 在三终端实验中体会「发布者与订阅者不直接相连」的解耦之美，理解为什么大型机器人系统能「越长越大」。<br>4\. 通过下节课预告，建立「同一件事可以有多种实现方式」的开放认知——L4 的 SDK 直接调用与 L6 的 ROS2 服务调用是两种工程选择。||
|**教学重点**|1\. ROS2 与 Ubuntu 的关系——ROS2 不是操作系统，是跑在操作系统之上的机器人通信框架（中间件）。<br>2\. Node / Topic / Service 三个概念的直观含义与适用场景。<br>3\. ros2 node list / topic list / service list 三条命令的实操，以及 topic info 读懂 Pub/Sub 数量。<br>4\. /greeting 三终端实验完整跑通，并理解通信背后的「按名字解耦」原理。||
|**教学难点**|1\. 理解「ROS2 不是 Windows 那样的操作系统」——名字里有 OS 容易误导，要反复强调它是「中间件 / 框架」。<br>2\. 区分 Topic 与 Service 的适用场景——学生常会把「触发挥手」也归为 Topic，需要用「广播 vs 提问」的类比反复强化。<br>3\. /greeting 实验需要同时开 3 个 K1 终端（pub / echo / info），SSH 多窗口操作对从未接触过 Linux 的学生有门槛，需教师演示。<br>4\. 「ros2: command not found」需要 source 环境的根因——非 IT 背景学生很难理解，教师备课时要先把这个流程练熟。||
|**教学准备**|||

|**环节一  导入  ·  为什么机器人需要 ROS2   【时长：8 分钟  ·  对应 PPT P1 – P6】**<br>**1\. 课程开场（约 1 分钟）：**<br>打开 PPT 第 1 页（封面三角节点图）。一句话引入：「前面几节课，我们让 K1 跑了第一段 Python，让 K1 点了头、说了话、做了动作。今天我们要打开机器人的『内部视角』——看看机器人系统里其实有很多模块在同时工作，它们靠 ROS2 这个『通信语言』协作起来。」<br>**2\. 内容架构预告（约 1 分钟）：**<br>翻到 PPT 第 2 页，介绍课程坐标 \(第 4 课 → 第 5 课 → 第 6 课\) 与本课五段安排。重点一句话定位：**「上节课用 SDK API 直接调用让 K1 做事，今天看 ROS2 系统全貌，下节课用 ROS2 服务再重写一遍——同一件事可以有两种做法。」**<br>**3\. 最终任务说明（约 0\.5 分钟）：**<br>告知学生本课最终任务：① 用 list 三件套查到 K1 当前的节点 / 话题 / 服务；② 三终端完成 /greeting 通信实验。强调本课「几乎不写程序，重在看见 \+ 理解」。<br>**4\. 单程序 vs 多模块对比（约 1\.5 分钟）：**<br>翻到 PPT 第 3 页，对照左侧「单程序模式」与右侧「多模块系统」：<br>· 单程序：所有功能写在一个 main\(\)，循环顺序执行——第 4 课的 Notebook 就是这种风格。<br>· 多模块：每个功能是一个独立模块（相机 / 视觉 / 决策 / 动作），同时运行，通过消息沟通——K1 真实工作方式。<br>抛出关键句：**「机器人天然需要多模块——『说话时不能同时看人脸』就是单程序的硬伤。」**<br>**5\. Ubuntu vs ROS2（约 2 分钟）：**<br>翻到 PPT 第 4 页，对照左侧 K1 软件栈四层图与右侧 OS logos 拼图：<br>· 让学生说一说自己用过哪些操作系统（Windows / macOS / Android / iOS / Ubuntu）。<br>· 强调一句话区分：**Ubuntu = 底座（管硬件）  ·  ROS2 = 通信框架（管多模块对话）。**<br>· 反复强调：**「ROS2 名字里有 OS，但它不是 Windows 那样的完整操作系统——它是跑在操作系统之上的中间件。」**<br>**6\. 没有 ROS2 vs 有 ROS2 视觉对比（约 1\.5 分钟）：**<br>翻到 PPT 第 5 页，对照「乱线图」与「ROS2 总线图」。让学生数一数左图有几条线（5 个模块两两相连 = 10 条线），引出 ROS2 把通信收敛到一条总线的工程价值。<br>**7\. 三个关键词预告（约 0\.5 分钟）：**<br>翻到 PPT 第 6 页，亮出三张概念卡：Node（节点）/ Topic（话题）/ Service（服务）。强调一句：「这三个名词是 ROS2 的 80/20，本课只建立直观印象，不要求记完整定义。」||**活动一**<br>1\. 听讲并接收本课主题——「打开机器人内部视角」。<br>2\. 在心里复述 L4 / L5 / L6 三课的衔接关系。<br>3\. 参与「我用过哪些操作系统」的口头讨论。<br>4\. 数一数 PPT 第 5 页乱线图中的连线数量，感受多模块通信的复杂性。<br>5\. 跟读 Ubuntu / ROS2 / Node / Topic / Service 五个关键词。<br><br>**学生产出**<br>·  在学习单上写出一句区分：<br>**Ubuntu = 底座  ·  ROS2 = 通信框架（中间件）**|
|**设计意图  **<br>本环节是认知动机阶段。学生只接触过「一个 Python 文件跑到底」的视角，没有「多模块系统」的概念。如果直接讲三个 ROS2 概念，他们会觉得「为什么要学这个」。所以本环节先用「乱线 vs 总线」「单程序 vs 多模块」两组视觉对比把动机建立起来。<br>特别强调「同一件事可以有两种做法」（L4 SDK 直接调用 / L6 ROS2 服务调用），是为了让学生理解本课的位置——L5 不是孤立的「概念课」，是 L4 与 L6 之间的认知桥梁。<br>反复强调「ROS2 不是操作系统」是因为这是非 IT 背景学生最容易踩的认知坑——名字里的 OS 字母会强化他们错误的初印象。课堂上用 3 次以上重复 \+ 课末填空 Q4 检查认知。|||
|**环节二  ROS2 三个核心概念  ·  Node / Topic / Service   【时长：12 分钟  ·  对应 PPT P7 – P12】**<br>**1\. Node 节点（约 2\.5 分钟）：**<br>翻到 PPT 第 7 页。先用「机器人 = 一个身体，节点 = 一个个器官」的类比建立直观印象：<br>· 相机节点 = 眼睛  ·  麦克风节点 = 耳朵  ·  语音节点 = 嘴巴  ·  运动节点 = 腿  ·  决策节点 = 大脑的一部分<br>然后给出严谨定义：**Node = ROS2 中的最小运行单元（一个独立进程），负责一件事。**<br>强调「为什么要拆」三点理由：每个节点只做一件事 / 一个节点坏了不影响整体 / 便于复用与调试。引导学生看右侧节点关系图（旧版插图），把视觉感受与文字定义对应起来。<br>**2\. Topic 话题（约 3 分钟）：**<br>翻到 PPT 第 8 页。用「微信群」类比：发布者在群里发消息，订阅者在群里看消息，群里没有「应答」机制——发了之后谁看谁知道。<br>给出严谨定义：**Topic = 一条命名好的数据通道，采用 Publish / Subscribe 模式。**<br>指着左下角 Pub/Sub 简图说明：「一个 Publisher 可以发给多个 Subscriber，订阅者越多发布者不感知。」<br>最后给出适用场景：适合「持续不断的数据」 —— 图像、IMU、机器人状态、视觉检测结果。<br>用右侧机器人例子收尾：/boostercamera/head/raw/rgb（相机持续发图像）  ·  /vision/face\_detected（视觉持续发检测结果）。<br>**3\. Service 服务（约 2\.5 分钟）：**<br>翻到 PPT 第 9 页。用「学生举手提问，老师回答」的类比建立直观印象——一次请求，一次应答，问的人会等到回答才继续。<br>给出严谨定义：**Service = 一次性的「请求 → 应答」通信。Client 发 Request → Server 处理 → 返回 Response。**<br>展示左下角 Client → Server 双向箭头图，强调 **「同步阻塞」**——请求方会等到结果才继续。<br>用右侧 Topic vs Service 对比表过一遍 6 个维度（通信模式 / 方向 / 数量关系 / 阻塞 / 类比 / 适合场景），让学生把两个概念对应起来。<br>**4\. 三概念整合 \+ 校园类比（约 1\.5 分钟）：**<br>翻到 PPT 第 10 页。上半区是校园场景类比（复用旧版图）——<br>· 节点 \(Node\) = 校园里的部门  ·  话题 \(Topic\) = 校园广播  ·  服务 \(Service\) = 学生去办公室问问题<br>下半区是 K1 真实拓扑示例——camera\_node / vision\_node / decision\_node / motion\_node 四个节点，3 条 Topic 链路 \+ 1 个 Service 链路。让学生指着图说出哪里是 Node、哪里是 Topic、哪里是 Service。<br>**5\. 阶段小测填空（约 1\.5 分钟）：**<br>翻到 PPT 第 11 页。让学生独立做 4 个填空（Node / Topic / Service / Ubuntu vs ROS2），与同桌互核。教师走动观察哪一题错的人多，公布答案时重点解释错率最高的那一题。<br>**6\. 阶段小测判断 \+ 分类（约 1 分钟）：**<br>翻到 PPT 第 12 页。8 道判断题（来自 ipynb 第 23 节）\+ 7 道 Topic/Service 分类题。教师点名学生口头回答，对错误较多的项口头解释。<br>特别强调判断题第 7 项「发布者和订阅者必须直接互相调用 → 错」——这是 P19 解耦原理的伏笔。||**活动二**<br>1\. 听讲三个核心概念，对应「器官 / 微信群 / 提问应答」三个类比。<br>2\. 跟随教师指 PPT 第 10 页的 K1 拓扑图，找出 Node、Topic、Service 各在哪里。<br>3\. 独立完成 4 题填空，与同桌互核。<br>4\. 跟随教师过 8 道判断题 \+ 7 道分类题。<br><br>**学生产出**<br>·  在学习单上写出三个概念的「一句话定义」：<br>**Node = 独立功能模块**<br>**Topic = 持续广播通道（发布/订阅）**<br>**Service = 一次请求一次应答（请求/应答）**|
|**设计意图  **<br>本环节是认知建立阶段。三个抽象概念对学生而言一上来很陌生，所以采用「类比 \+ 定义 \+ 示例 \+ 整合」四步走：先用生活类比（器官 / 微信群 / 提问应答）让学生有直观印象，再给严谨定义，再用 K1 真实例子（相机话题 / booster\_rpc\_service）落地，最后整合到一张系统图里。<br>Topic vs Service 对比表是本环节的关键认知工具。学生最容易混淆「触发挥手用 Topic 还是 Service」——通过对比表的 6 个维度（特别是「阻塞」与「方向」），他们能自己推理出「需要确认结果的用 Service」。<br>两道小测的设计是「填空检查概念名词、判断检查反例、分类检查应用」三层递进。错率最高的几道题（特别是判断 1 / 6 / 7）反映学生最容易踩的坑，是教师调整后续讲解节奏的依据。|||
|**环节三  用 ROS2 命令观察 K1 系统  ·  实践 1 – 3   【时长：9 分钟  ·  对应 PPT P13 – P16】**<br>**1\. ROS2 CLI 引入（约 0\.5 分钟）：**<br>翻到 PPT 第 13 页。一句话引入：「ROS2 命令行工具能查到当前 K1 系统里有哪些节点 / 话题 / 服务——这是机器人开发者的 X 光机。」<br>**2\. 实践 1  ·  ros2 node list（约 2\.5 分钟）：**<br>在教师端电脑上演示：打开 K1 SSH 终端，执行 **ros2 node list**。预期会看到若干 booster\_\* / camera/camera / joy\_node / rpc\_service\_node 等节点。<br>课堂提示：**「如果第一次执行报 command not found，需要先 source /opt/ros/humble/setup\.bash。」**<br>让学生分组在自己 K1 上跑，把节点名抄到学习单的「节点观察表」里，每个节点猜一下作用。<br>教师巡视 4 个组，重点关注：<br>· 是否 source 了环境？  ·  是否成功执行？  ·  能否说出 3 个节点的猜测作用？<br>**3\. 实践 2  ·  ros2 topic list \+ topic info（约 3 分钟）：**<br>翻到 PPT 第 14 页。三步：<br>Step 1：**ros2 topic list**  列出所有话题。<br>Step 2：**ros2 topic info /boostercamera/head/raw/rgb**  深入观察一个话题，看 Type / Publisher count / Subscription count 三项。<br>Step 3：按相机 / 状态 / 输入三类把话题分类，记到学习单上。<br>讲解 info 输出的解读逻辑——「Pub=1, Sub=0」表示有人发但没人看；「Pub=1, Sub=1」表示正常通信；「Pub=0, Sub=1」表示有人等但没人发。这是判断系统通信是否在跑的最快办法。<br>**4\. 实践 3  ·  ros2 service list（约 2 分钟）：**<br>翻到 PPT 第 15 页。让学生执行 **ros2 service list**，把 booster 相关的服务名抄下来——重点是 **/booster\_rpc\_service**。<br>强调：**「这个服务就是 SDK 的『能力总入口』。下节课会用 ros2 service call 真正调用它让 K1 切模式、做动作。今天只是先『看见』它的存在。」**<br>解释另一类服务——每个节点自带的参数服务（/camera/\.\.\./get\_parameters），本课不展开。<br>**5\. 三步法总结（约 1 分钟）：**<br>翻到 PPT 第 16 页。把刚才三个实践收敛成一套通用方法论：**「先 node list 看有谁 → 再 topic list/info 看有什么通道 → 最后 service list 看有什么接口。」**<br>强调这套方法在后续所有 ROS2 课程做实机调试时都会反复用到。||**活动三**<br>1\. 三人一组分工：操作员（敲键盘）、记录员（抄到学习单）、解读员（猜节点 / 话题作用）。<br>2\. 执行实践 1：ros2 node list  →  抄 5 个节点名到学习单。<br>3\. 执行实践 2：ros2 topic list \+ ros2 topic info \<一个话题\>  →  抄 3 个话题，并记下 Type 与 Pub/Sub 数。<br>4\. 执行实践 3：ros2 service list  →  找到 /booster\_rpc\_service 并标记。<br>5\. 跟着教师过一遍三步法总结。<br><br>**学生产出**<br>·  学习单上「节点 / 话题 / 服务」三张观察表填好。<br>·  截图保存 3 次命令的输出。|

|**环节四  /greeting 通信实验  ·  三终端实操   【时长：10 分钟  ·  对应 PPT P17 – P19】**<br>**1\. 实验背景与多终端演示（约 1 分钟）：**<br>翻到 PPT 第 17 页上半区。说明实验意义：「这个实验不控制机器人，但能最清楚地看到发布者和订阅者如何通信——这是后面 7、8 课视觉检测发布结果的最小原型。」<br>教师在大屏上演示「同时开 3 个 K1 终端」的操作方式（Booster Studio Terminal 拆分 / Windows Terminal 多窗格 / 多开 SSH 窗口）。这一步必演——非 IT 背景学生不熟悉。<br>宣布话题命名约定：**「每组使用 /greeting\_groupN（N 为组号），不要混用同一话题名。」**<br>**2\. 实验 4\-A  ·  发布端 ros2 topic pub（约 3 分钟）：**<br>翻到 PPT 第 17 页下半区。讲解发布命令：<br>**ros2 topic pub /greeting\_group1 std\_msgs/String "data: Hello K1"**<br>逐段拆解：**ros2 topic pub** = 发布命令；**/greeting\_group1** = 话题名；**std\_msgs/String** = 消息类型；**"data: Hello K1"** = 内容（YAML 格式）。<br>让学生在第 1 个终端跑这条命令，看到「publishing \#1 \#2 \#3 \.\.\.」持续输出。<br>**3\. 实验 4\-B  ·  订阅端 ros2 topic echo（约 2\.5 分钟）：**<br>翻到 PPT 第 18 页。在第 2 个终端跑：<br>**ros2 topic echo /greeting\_group1**<br>看到与发布端同步的「data: Hello K1」实时输出。<br>回到第 1 个终端，Ctrl\+C 停止后改消息内容重新发，例如：data: 我是第 1 组的 K1 学习者。观察第 2 个终端同步变化——这就是「话题是实时数据流」。<br>**4\. 实验 4\-C  ·  topic info 验证 \+ 解耦原理（约 3 分钟）：**<br>翻到 PPT 第 19 页。在第 3 个终端跑：<br>**ros2 topic info /greeting\_group1**<br>观察 Publisher count = 1 / Subscription count = 1。然后让学生再多开一个 echo 终端，回来重跑 info，观察 Subscription count 从 1 → 2 的变化。<br>讲透「解耦原理」：**「发布者和订阅者不需要互相知道对方是谁、不需要直接连接、甚至不需要在同一台机器上——它们只需要约定同一话题名 \+ 同一消息类型。」**<br>强调这是 ROS2 系统能「越长越大」的根本机制——后续课程加新节点时，旧节点完全无感。<br>**5\. 小组验收（约 0\.5 分钟）：**<br>教师巡视确认每组都跑通了 pub \+ echo \+ info 三件套，所有 K1 都能看到「我是第 N 组」的消息流。||**活动四**<br>1\. 跟随教师演示在自己电脑上同时开 3 个 K1 终端。<br>2\. 终端 1 跑 pub 命令，看到持续发布输出。<br>3\. 终端 2 跑 echo 命令，看到与发布端同步的数据。<br>4\. 改 pub 的 data 内容（换成本组名字），观察终端 2 的同步变化。<br>5\. 终端 3 跑 info，记下 Publisher count / Subscription count。<br>6\. 多开一个 echo，回来重跑 info，观察 Sub count 是否变成 2。<br><br>**学生产出**<br>·  截图保存 3 个终端的输出。<br>·  在学习单上写出一句话回答：<br>**「为什么 pub 和 echo 不需要互相知道对方？」**|
|**设计意图  **<br>本环节是本课的实操高潮。/greeting 实验是 ROS2 最小可工作单元——通过它，学生能用最少的命令亲眼看到「两个独立终端通过话题名沟通」的完整过程。这种「看得见的解耦」是 ROS2 工程美感的浓缩。<br>三个终端的设计（pub / echo / info）让学生第一次理解「同一系统里多个进程并行」是什么意思——这是后续所有多节点协作的认知基础。<br>从「改 pub 内容看 echo 同步」到「多开一个 echo 看 Sub count 增加」是两层递进的体验：前者让学生感受「实时数据流」，后者让学生感受「Pub/Sub 多对多」。<br>解耦原理的强调是为了让学生在 P19 之后能自己回答课末作业题——「为什么 say\('你好'\) 这样的代码能让 K1 动起来？」其本质和 /greeting 实验一样，都是按名字解耦的通信。|||
