# 足球SDK能力与定位方案：分级测试计划

版本：2026-10-30 v1。使用者：课程开发者、教师和SDK支持人员。用途：先确认实际SDK能力，再决定U7-L2及后续足球课程采用什么定位方案。**以下全部待执行**；既有离线检查不自动填作真机通过。

审核结论见[SDK能力与教学边界](足球方案联合审核_SDK能力与教学边界.md)。现有[U7逐格指导](U7_逐课真机测试指导.md)、[U8实施指导](U8_逐课实施与真机测试指导.md)用于课程联调，本计划补充它们前面的能力调查、误差覆盖与方案选择。

## 1. 顺序与进入条件

```text
A：SDK能力探查（不发运动指令）
   ├─已有可靠机身球位 → 独立测量与动态核查 → C
   ├─有深度/内参/变换 → 教师验证定位实现与独立误差 → C
   ├─以上不满足、拟保留固定映射 → B → 动态核查 → C
   └─没有可验证的定位来源 → 停留静态内容，调整课程方案
C：教师验证管理器启停与控制 → D：课程片段和项目整合
```

世界/场地坐标不是管理器必需输入。已有世界坐标也要核实来源、机器人当前位姿和转换，不可直接填入`update_ball`。两条路线若都可用，比较误差、失效方式、准备时间和学生操作复杂度，再选课堂方案。

本计划不安排开发者远程运行机器人。A由现场人员运行[只读能力探查Notebook](足球SDK能力探查_只读.ipynb)；它不导入课程`x_lab`，不发运动或模式指令，也不调用管理器start。C需另外使用经审阅的教师测试程序与现场保护，不按未核实坐标直接运动。

## 3. A：先探SDK实际能力，不运行足球控制

先完成A01～A04，再按发现选择A05～A09。没有数据、导入失败、字段为空均原样记录，不通过安装未知同名包、修改属性或伪造坐标补齐结果。

| ID | 条件与操作 | 记录证据 | 本项判定/下一步 | 初始状态 |
| --- | --- | --- | --- | --- |
| A01版本和符号 | 在实际教学运行环境，打印Python/SDK版本、安装路径；仅导入当前文档的BoosterRobot、Detection、SoccerKickManager | 版本、符号与导入异常；不启动/实例化管理器 | 环境匹配才继续；错误先定位版本 | 未执行 |
| A02静态元数据 | 旧任务退出、机器人固定；只连接读取机型、模式、传感器、坐标系列表与相机参数 | 原始列表、内参、frame_id、时间戳 | 对象齐备仅说明能读取，不是球位可用 | 未执行 |
| A03单帧检测全字段 | 画面只放一只球，取RGB并检测；打印结果实际类型、基础与扩展字段、公开属性名 | 原图、框、raw结果、distance_m、mask/keypoints及可能位置字段；不可只看to_dict | 发现候选位置字段时查含义/单位/参考系，不直接发控制 | 未执行 |
| A04重复与无球 | 同一球位采20个不同源时间戳记录；机器人静止时移走球再采20条；重复源戳单独计 | 检出率、错检、字段是否变化/为空、调用耗时、旧帧重复 | 有球/无球输出与实际对应，记录准确不足或待查项 | 未执行 |
| A05已有球位核对 | 若发现SDK或已部署服务直接给球位，核实原点/轴/单位、球中心或落地点定义，再在近中远×左中右9点核对；每点20个独立帧 | x/y、地面实测值、误差/偏差/抖动/可用率、源时间 | 达到已填门槛才作为候选；world坐标先明确转换 | 未执行/按发现选用 |
| A06深度原始能力 | 无管理器，分别取RGB和depth、CameraInfo，记录元数据与原数组；用几个已知距离点核实比例、Z/视线距离和无效值定义 | encoding/dtype/原值/单位依据、分辨率/frame_id及源戳；近距足球有效深度比例 | 不能只按uint16/float猜单位；没有单位和深度定义不反投影 | 未执行/按发现选用 |
| A07配准与内参 | 查RGB/depth是否已对齐、对应内参和去畸变方式；用场景边缘和目标作覆盖检查 | 配准依据、图像/参数对应、不同区域和距离的对照 | 同分辨率或缩放框不足以证明配准；不满足则暂停此路线 | 未执行/按发现选用 |
| A08坐标变换 | 从实际list_frames选相机源与机身目标；查询TF，核对返回字段、矩阵方向、轴向、时间 | 原始TF与参数；用已知方向/位置做正反向检查 | 目标原点须是管理器定义；TF存在不代表它包含球；动态还需时序核对 | 未执行/按发现选用 |
| A09产品能力问答 | 将A证据和问题交SDK支持人员核实；没有得到回复的项目记待核 | 正式文档/版本说明或技术回复位置 | 确定路线，列缺口；不把公开文档未列出推成系统无能力 | 未执行 |

需要核实的产品问题：是否已有机身或世界球位读取接口/服务；支持哪版和机型；`distance_m`是否由soccer模型填充且代表什么；深度配准和frame定义；管理器的机身原点及球位参考点；管理器是否自行感知、或必须持续外部更新；最低更新率/球位失效时间；start到首个球位之间做什么；丢球、旧球位、stop后的状态如何；如何保证SDK阻塞时现场仍可停止。

**A阶段小结**：选择路线______；依据______；还缺______。若A05或其他路线没有球位可用性证据，不进入实际试踢。SDK组合定位的反投影由教师验证，先完成与A05相同的独立点误差，再进入C；不因为使用官方数据就免除实测。

## 4. B：只有决定保留固定映射时才执行

这是教师验证候选方案，不默认成为学生45分钟内必须从零完成的活动。拟合与核对点分别编号，核对点不能拿回去边调模型边宣称仍为独立验收；模型调整后重新采验收集。

| ID | 操作与覆盖 | 记录/判据 | 初始状态 |
| --- | --- | --- | --- |
| B01几何与参考 | 核对机身原点、x前y左、球框下缘代表什么；固定相机、姿态、地面、球型、分辨率 | 拍照标注测量轴；球中心/接地点定义与管理器一致；条件签名 | 未执行 |
| B02拟合数据 | 四点为代码下限；教师验证建议采6～9个覆盖边界和内部、远近和左右的点，避免共线及集中一角 | 每点保存[u,v,x,y]、原图/框和源戳，至少重复20个不同源帧了解线索波动；固定规则选代表值 | 未执行 |
| B03拟合检查 | 固定代码/数据版本建H，记录秩、点位分布、拟合残差；开发者另查条件数和异常点 | 不以“函数没报错”判断稳定；记录拟合失败及处理 | 未执行 |
| B04独立覆盖 | 另选至少9个不重复拟合点，覆盖近中远×左中右；每点20个不同源帧 | 每帧x/y误差、每点中位数/P95/最大值、方向偏差、抖动、有效比例；对照冻结门槛 | 未执行 |
| B05范围边界 | 在安全静态条件测区域内、边界附近、区域外和不匹配分辨率 | 正常估计或明确拒用；区分“不检出”和“估计超范围”；不删除检查 | 未执行 |
| B06外观/遮挡 | 原球位下改变正常课堂光照；球边缘被轻度遮挡、画面出现两只球时只做静态观察 | 是否误选、框下缘偏移、误差/可用率；最高评分规则不等于身份跟踪 | 未执行 |
| B07姿态迁移 | 现场保护下由教师按既定流程改变头部/站姿后静态重新采点，不开管理器 | 误差变化、哪些条件使模型失效；`setup_note`不会自动检测变化 | 未执行 |
| B08独立运动核查方案 | 先准备能量出运动中“真实相对球位”的方法，再采运动数据 | 可用经标定外部相机/测量系统，结合实际时刻的机身参考原点和球位；同一估计算法及未验证里程计不可作独立真值 | 未执行 |

## 5. C：教师验证管理器与控制链

进入C前：球位来源、参考系、精度、时效有依据；当前姿态/步态适用性已核查或已有可验证的动态采集计划。C01产品启停说明应在B09之前确认；任何运动测试均需现场批准。本计划不提供把假定`(0.6,0)`直接发给真机的快捷演示。

| ID | 操作 | 应核对的结果/失败后处理 | 初始状态 |
| --- | --- | --- | --- |
| C01管理器契约 | 先查产品说明并审阅教师测试程序：start模式、未收到球位、更新率、过期、stop、阻塞与外部停止 | 缺少的行为写待核；未明确前不故意用无球/旧坐标启动做试验 | 未执行 |
| C02启停与首帧 | 在明确契约和现场保护条件下，用已核实球位来源，观察启动模式、首帧前行为及启动后坐标变化 | 不沿用start前旧球位；记录start/首次update/stop调用时刻与现场录像；必要时暂停 | 未执行 |
| C03一次受控尝试 | 先以经产品确认的低力度、短窗口单次试踢；记录每次新球位、处理时间与状态，再stop | 调用结果、管理器退出、现场停稳、是否踢出、目标区结果分开；满足预填要求再重复 | 未执行 |
| C04拒用分支 | 先用离线替身/录制数据核查无球、超范围、重复源帧、处理过慢、异常、start失败与stop失败 | 不继续下发旧球位；finally尝试停止，stop失败保留原对象与活动标记 | 未执行 |
| C05真实失效 | 教师在已明确系统失效处理和保护下，记录自然出现的丢球/超范围/慢处理；其余填未测 | 不让人入运动路径取球，不故意断网/推倒；离线通过不填作本项真机通过 | 未执行 |
| C06释放和重复 | stop成功返回且现场停稳，原session/管理器保留；人工复位后至少3轮独立运行 | 旧控制不占用、句柄和资源状态一致；保留每轮条件、日志、效果；不能只保留最好一轮 | 未执行 |

L2现稿是先start再开始取图，L4附件是先静态观察后start，再重新检测。两者的首帧行为应分别核查。六秒循环与`finally`不能在SDK调用阻塞时保证立即执行，外部停止与现场保护不由程序计时替代。
