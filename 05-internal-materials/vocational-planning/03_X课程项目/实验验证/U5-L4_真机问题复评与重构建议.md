# U5-L4 真机问题复评与重构建议

初评日期：2026-10-22；进展更新：2026-10-23。用户认可持续会话管理方向，学生Notebook和生成器已重写；新稿待设计确认①、真机确认②。本记录保留原问题依据，不代表新代码已验证。

依据：用户本轮真机反馈；已验证的 U5-L1、L2、L3 Notebook；[SDK 语音接口](../../../../01-booster-kb/07-tech-platform/booster-sdk.md)。L1～L3 的确认②已完成，本记录不代替这三课的 P2 审定，也不表示 L4 通过真机验证。

## 1. 结论

U5-L4 需要重构学习目标和实验主线。原稿将持续任务的存续时间、人工设置的监听窗口和一轮问答的响应时间混用，导致目标、实验和记录表都缺少有效的测量依据。仅修改 `print()` 或调短 `sleep()` 无法解决。

建议保留「语音问答闭环」课名，以**持续对话的启动、使用、停止和再次启动**为实践主线，用能观察到的会话状态学习状态机。ASR、LLM、TTS 继续用于解释功能链路；程序控制到哪一层、接口能提供哪些信号，也成为本课需要辨明的内容。

## 2. 原稿的问题及影响

以下单元格按2026-10-22重构前稿从1开始计数，新稿不沿用这些格号。

| 位置 | 具体问题 | 对学生学习的影响 | 建议处理 |
|---|---|---|---|
| 第1格目标3；4.2、第17格 | `chat()` 启动持续语音会话，18秒后主动取消。计时包含人为保留会话的时间，与一次回答何时开始、结束没有对应关系 | 学生会把窗口长度当成模型响应速度 | 删除测量单轮耗时的目标和代码 |

| 3.1～3.2 | 把「说的时候不听」当成 `chat()` 的固定行为；L3 已实际练习会话中打断 | 同一单元给出互相冲突的解释 | 区分具体应用可制定的轮次规则与 SDK 已支持的打断行为 |

| 2.3～2.4 | 把响应时间机械拆为三个可测部分，又给出缺少来源的1秒、两三秒、5秒容忍线及三四秒总时长要求 | 学生既拿不到分段数据，也不能据此作合格判断 | 删除硬阈值与分段计时要求；等待感受可讨论，不作本课测量主线 |
| 第24格 | 要求填写 ASR、LLM、TTS 分段用时，接口没有提供相应边界信号 | 表格无法由实验结果填写 | 改为指令、会话状态、任务状态、实际现象及停止结果的记录 |

L1 已有的6秒监听实验可以保留其原有意义：观察窗口内收到的识别文字。L1 的实测输出还包含「人工→人工智能→人工智能」这样的多次回调，因此收到一条文字既不等于整句话已经说完，也不保证是一条最终结果。当前回调只有 `text`，不能自行添加 `is_final` 来修补 L4。

## 3. 为什么建议学习会话管理

L1 已让学生认识录音、流和识别输出；L2 已验证合成结果与播放任务的等待；L3 已能使用人设启动对话，并通过中止运行退出。L4 可以在这些经验上增加一个明确的问题：**应用如何保证同一时间只保留一个语音会话，并在停止后允许重新启动？**

这与 L3 的分工是：L3 调整「回答的内容与风格」；L4 管理「会话何时启动、当前能做什么、何时允许再次启动」。复用 `chat()`，新增的是状态、转换条件和任务管理，不再重复做三种人设对比。

若只把 L3 的启动与 Ctrl+C 操作再做一遍，L4 内容会偏薄。因此实验须包含重复启动拦截、停止请求与实际终止的区别、再次启动三类操作，并要求学生根据记录解释转换条件。

## 4. 建议的学习目标与环节

建议学习目标：

1. 能说明采音、语音转写、回复生成、语音合成与播放各自的输入输出，区分持续会话和一轮问答。
2. 能根据应用操作和任务状态，画出会话状态与转换条件，解释为什么不能从任务句柄推断内部正在聆听、生成还是播放。
3. 能运行并调整一个简单的会话管理程序，完成启动、阻止重复启动、停止和再次启动，并记录实际结果。

| 环节 | 建议用时 | 学生完成的活动 | 能留下的学习证据 |
|---|---:|---|---|
| 一、同一个会话里可以问几次 | 5分钟 | 在已验证的 L3 用法中连续问两个问题，观察回答结束后任务是否仍在运行 | 区分「回答完」和「会话退出」 |
| 二、功能链路与程序可见信号 | 8分钟 | 对照 L1～L3 的输入输出，标出本课能获取的文字、任务状态和人工观察结果 | 一张链路与可见信号对照表 |
| 三、给会话规定状态与转换 | 8分钟 | 按开始、查看、停止三种操作填写状态转换表；说明重复开始时该怎么处理 | 有条件、有操作结果的状态图 |
| 四、实践会话管理 | 17分钟 | 分别运行开始、重复开始、查看、停止、再次查看、重新开始；先运行已给程序，再补写一个状态判断 | 代码、操作记录与实际状态 |
| 五、解释与评价 | 7分钟 | 依据记录解释为什么回答完不能自动回待机、为什么发出取消不一定已经退出 | 检查点、判断题及短答 |

45分钟为内容安排建议，后续教学设计再按真机操作耗时调整。本次不提前编写 P3 教学设计。

## 5. 状态机如何落地

将应用状态暂定为「待机」「会话已发起」「停止请求已发出」。它们描述自己的管理程序，不冒充 SDK 的内部问答阶段。

| 当前情况 | 学生操作或实际条件 | 程序动作与下一步 |
|---|---|---|
| 待机，旧任务不存在或已终止 | 开始 | 创建一个 `chat()` 任务，保存句柄，记为「会话已发起」；句柄返回不代表已经可以收音 |
| 已有任务且 `done()` 为假 | 再次开始 | 提示已有会话，保留原句柄，不重复创建 |
| 会话已发起 | 查看 | 打印当前 `status`；学生通过回答和字幕观察交互，不把 `RUNNING` 解释为某个内部阶段 |
| 已有任务且未终止 | 停止 | 调用 `cancel()` 并查看返回值和当前状态；请求成功发出后，记为「停止请求已发出」 |
| 停止请求已发出，任务仍未终止 | 再次开始或查看 | 阻止再次启动，继续保留原句柄；学生再次运行查看格 |
| 任务 `done()` 为真 | 查看 | 记录 `SUCCEEDED`、`CANCELLED` 或 `FAILED`；失败时显示 `error` 并先检查原因，再决定重试 |
| 已确认正常终止或取消完成 | 再次开始 | 允许创建新会话，验证可以再次问答 |

`PENDING`、`RUNNING`、`CANCELLING` 是非终态；`SUCCEEDED`、`FAILED`、`CANCELLED` 是终态。SDK 任务状态和应用状态分别列出，不能用几个 `print("聆听/处理/回答")` 代替真实控制条件。

代码可分为连接与初始化、会话操作函数、操作练习三部分。操作函数只用已学的字符串、`if/elif`、函数与 `TaskHandle`；每次设置 `command = "开始"`、`"查看"` 或 `"停止"` 后运行一格，模拟应用操作。不需要另开线程、后台轮询或同步视觉运动，也不需要一个永不退出的主循环。已知任务尚未停止时保留句柄，不能先清空变量再重开。

原来的「待机→聆听→处理→回答」可以作为功能过程讨论；当前接口没有提供这些阶段的转换信号，不将它作为程序已实现的状态机。

## 6. 与后续单元的边界

- 本课机器人静止，只使用语音能力；不加入迎宾检测、接近、运动打断或动作编排。
- 不使用 U7 的 `Thread`、`Lock`、多传感器协同或综合任务调度。SDK 内部异步执行的实现不在本课展开。
- 不新增未经 L1～L3 真机验证的整段录音识别接口或独立文本 LLM 接口。不会用虚构的单轮完成回调补齐状态。
- 回复是否说完由学生听到、字幕等现象辅助观察；这些人工观察不作为程序已获得的自动转换信号。

若希望学生亲自串联「识别文字→选回复→合成播放」，另一条可行路线是限定关键词问答。它能复用 L1、L2，但中间环节应明确称为规则选答；它会改变原课 LLM 问答的定位。本次优先建议保留持续 LLM 会话，以会话管理落实状态机。

## 7. 重写后需要补做的真机验证

1. 单次启动可连续完成至少两次问答，回答结束后任务仍可继续交互。
2. 旧任务未终止时重复开始，不新建第二个任务，不覆盖旧句柄。
3. 查看时打印的任务状态真实可读；不要求必须观察到短暂的 `PENDING` 或 `CANCELLING`。
4. 记录 `cancel()` 返回值、请求后的状态及最终状态；若未及时终止，保留句柄、停止重开，不伪造失败场景来凑记录。
5. 在确认旧任务终止后，能够再次启动、完成问答并再次停止。
6. 课堂中断 Notebook 时，检查旧任务是否仍存在；沿用 L3 已验证的取消与有限等待用法收尾，不以停止代码格等同于停止会话。
7. 记录表能由上述操作逐项填写；评价题只要求判断已有证据，不要求估算 ASR/LLM/TTS 内部分段用时。
