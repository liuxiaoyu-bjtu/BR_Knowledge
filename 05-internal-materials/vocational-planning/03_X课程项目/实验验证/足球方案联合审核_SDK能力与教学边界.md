## 1. 审核结论

现阶段应先做教师侧SDK能力探查，再确定足球定位方案。`ball_position.py`是课程自编的候选定位辅助代码，不能因其离线计算通过、教材已解释调用方法，就认定它是课程必须使用或已经可用于踢球的方案。

此前设计从“检测返回二维框、踢球接口需要米制坐标”推到了“自己建立像素—米换算”。这个推断提供了一条候选实现，却没有充分核实本机是否已有更直接的球位来源，也没有以实机数据证明固定映射在步态中的有效性。把这些待验证条件放进学生主线，确实增加了课时和理解负担。这一步应先补教师预验证。

当前建议的教学深度：学生理解球在图像、相机、当前机身坐标中的含义，能筛选目标、读取经过核实的位置、提供给管理器并管理退出。若最终需要课程辅助定位，学生还需理解其输入输出、条件和核对方法；不要求从零编写矩阵求解、凸包和投影算法。

本轮保留学生Notebook、生成器与控制实现，先提交审核依据及可逐项记录的测试计划。选择哪条定位路线，取决于后续本机证据。

## 2. `ball_position.py`基于什么建立

### 2.1 它实现了哪些功能

| 函数 | 具体实现 | 性质 |
| --- | --- | --- |
| `select_ball` | 按类别筛选，选该类别中评分最高的一条 | 可由学生阅读、复现的基础循环 |
| `ball_pixel` | 取框中心x、框中心y加半个框高，作为下缘中点 | 简单几何线索，不能自动称为球的地面接触点 |
| `build_calibration` | 用`[u,v,x,y]`实测点构造线性方程，`np.linalg.lstsq`拟合3×3投影矩阵 | 课程自编近似模型，非SDK定位接口 |
| `pixel_to_robot` | 检查分辨率、像素范围，计算投影并除以齐次分量，再检查米制范围 | 使用固定矩阵进行位置估计 |
| `verify_calibration` | 用至少三个独立点计算平面位置误差，全部小于容许误差才记`verified=True` | 本文件中的静态核对标记 |
| `_hull`、`_inside` | 计算凸包，检查点是否位于样本覆盖区域 | 限制外推的内部辅助代码 |

这是一组普通Python函数，“接口”只表示函数调用约定，不代表另一个经过官方验证的定位产品。其数学形式可以由源码直接核查；当时没有依据本机相机标定报告、真实训练数据或实际足球测试建立它。

### 2.2 换算的数学假设

代码先把`u/v`分别除以图像宽高，得到`u′/v′`，再拟合：

\[
\begin{bmatrix}\tilde{x}\\\tilde{y}\\w\end{bmatrix}
= H\begin{bmatrix}u'\\v'\\1\end{bmatrix},
\qquad x=\tilde{x}/w,\quad y=\tilde{y}/w.
\]

`H`固定最后一个元素为1，求其余8个参数。每对点提供两条方程，因此四对分布合适的点是代数最低数量；代码还检查方程秩。更多、分布更广的实测点和独立核对，才有助于判断现实误差。它不是“一个像素固定等于几厘米”的比例尺。

平面单应关系有明确适用条件：空间点位于同一平面，成像关系相对固定，畸变已处理或影响可接受。现实现还有一个近似：用球框下缘中点代替地面点。球的轮廓、遮挡、检测框波动、球半径和观察角度会影响该线索，不能把理想平面几何自动推广到真实球框。

机器人平移或绕竖直轴转向，**本身不必然使机身相对坐标映射失效**：若相机相对机身的位置、朝向、离地高度及局部地面关系保持一致，映射有继续成立的可能。实际足球步态的起伏、俯仰、侧倾、头部调整会破坏这些条件，本附件没有动态补偿。

### 2.3 现有检查不足以证明什么

- `rank=8`只说明可解，不保证点位分布良好、数值稳定或对检测噪声不敏感。代码没有条件数、稳健拟合或畸变处理。
- 三个静态核对点满足误差限，只能说明那几个点、当时姿态与采样达到要求，不能证明整个区域或步态全程都可用。
- `setup_note`是文字，代码不会读取当前头部/机身姿态与它比较。`verified`没有绑定机器人编号、当前姿态、模型版本或动态测试证据。
- 两个凸包限制的是标定样本覆盖范围，不能叫作整个区域都“已经核对”；独立点只检查了其中有限位置。
- 固定姿态下得到的新图像，也可能带来不适用的球位。时间戳更新与位置准确是两项不同检查。

本轮用人工构造的投影验证，代码可重建该理想模型，独立点误差约`10^-15 m`。这只是数值一致性，不是真机精度。另验证了更改姿态说明不会使`verified`自动失效，说明该字段不能承担动态适用性判断。

## 3. SDK是否已经提供足球世界坐标

### 3.1 需要区分坐标与数据来源

| 对象 | 含义 | 能否直接填`update_ball` |
| --- | --- | --- |
| 图像像素 | 球框在画面的位置 | 不能，单位和坐标不同 |
| 相机三维坐标 | 球相对相机的位置，须明确深度含义、轴向和原点 | 不能直接套用，须确认或变到管理器要求的机身参考系 |
| 当前机器人二维坐标 | 当前机身参考下前向x、左向y，单位米 | 经来源、参考原点、方向与时效核实后可用 |
| 世界/场地坐标 | 球相对固定场地原点的位置 | 仍需机器人当前位姿转换，本任务本身不要求先得到世界坐标 |
| 坐标系变换 | 两个参考系之间的位置与朝向关系 | 只转换已有位置，不会凭空找出球 |

官方`SoccerKickManager.update_ball(x,y)`明确要求**当前机器人坐标系**，并接收外部球位；它不是查询球位置的函数。所谓“自动踢球”不能据此理解为这个类已包办图像识别和定位。其概览要求持续提供球位。

### 3.2 本次能从公开文档确认的能力

| 公开能力 | 文档明确了什么 | 仍需本机核实什么 |
| --- | --- | --- |
| `Detection(model="soccer").detect(...)` | 返回`list[DetectionResult]`；示例有Ball类别 | 实际类名、扩展字段及是否有可用三维球位 |
| `DetectionResult` | `bbox`二维框；`distance_m`可为空；`mask/keypoints`为可选扩展 | 距离是否真的填充、测量含义、是否还存在版本特有位置字段 |
| `DetectionResult.to_dict()` | 只保留基础分类和框字段 | 探查不能只打印它就断言没有距离或位置 |
| `get_image(img_type="depth")` | 可以请求最近一帧深度图 | 本机是否实际发布、单位/无效值、RGB配准和时间对应 |
| `get_camera_info()` | 有内参和畸变等信息 | 参数属于哪个流、与分辨率和实际图像是否一致 |
| `list_frames()`、`get_transform()` | 列出可查询坐标系，查询两参考系之间变换 | 有无相关球位帧、相机到管理器机身原点的变换是否存在、方向和时间是否可用 |

在本次查阅的这些公开页面和足球管理器文档中，没有找到承诺直接返回足球场地/世界三维位置的公共查询。这个结论限于公开文档，不能据此否定用户本机版本、额外服务或产品内部已有定位能力。需要运行探查并由产品/SDK同事确认。

深度加内参可提供另一条技术路线，但也不能“读一个距离就直接填x/y”。若取到的是光轴深度Z，才可在合适的去畸变坐标下按内参反投影；若是沿视线距离，则公式不同。之后仍需核对相机到机身的变换。RGB/深度分辨率相同也不等于已配准。框内深度中位数还可能主要落在地面或背景上，足球的小面积更需检查。

历史`probe_depth_distance.py`假设dtype对应单位，并按分辨率比例映射RGB与深度；这些假设不能直接带入本次结论。历史脚本中“distance_m永远为None”等说法也只可视为当时版本的核查记录，当前版本要重新测。

### 3.3 为什么先前会选择自己换算

当时选择是为了把二维检测和管理器输入接起来，并避免在一课中增加深度、内参和三维变换推导；因此采用了固定姿态的实测映射。这个选择降低了代码调用的表面复杂度，却把定位可靠性、标定采集和动态核查移到了教师与学生身上。未先完成本机能力比较，就不能认定它比SDK已有能力更适合课堂。

本地开发电脑安装包显示`boosteros 0.1.0`，可见的导出文件为旧`BoosterK1/BoosterBase`命名，未在所读导出文件中列出当前文档的`BoosterRobot/SoccerKickManager`。本轮只读安装文件，未尝试连接。这不是对用户教学机器人所用环境的判断，更说明需要以实际运行环境记录版本，不能把本地安装包当成目标版本。

## 4. 学生应理解到哪一层

| 层次 | 建议要求 | 当前学材与所需调整 |
| --- | --- | --- |
| 必修理解 | 图像/机身坐标、单位与正负号、检测和定位的差别、有效球位、更新与停止 | 保留，结合具体返回值讲清 |
| 能阅读/复现 | 类别筛选、选球规则、读已核实的x/y、循环更新管理器、退出 | 可用基础Python，代码应展开 |
| 条件性实践 | 若确需标定，观察一个已知点的对应关系，核对几处独立误差，判断条件变化后不能盲用 | 由教师提供已验证方案与标定，学生做有限核对；课内时间不足须缩减其他活动 |
| 教师辅助实现 | 矩阵拟合、凸包、齐次坐标除法、数值稳定性、畸变和动态补偿 | 不列为本课程学生从零编写或算法推导要求 |

上一轮说明实际采用“理解输入输出、可以打开阅读、不要求推导”的口径，没有要求学生完整复现算法。但当前L2仍让学生完成至少4个拟合点、3个核对点，加检测、坐标讲解、管理器与试踢；对45分钟课时负担偏重。若学生被要求读懂全文件，又缺少上述数学前置，就会形成学材无法自行完成的问题。

## 5. 像素到米是否要课堂自己定

**按当前现稿，确实如此。** U7-L2 STEP 03填写实测`[u,v,x,y]`，STEP 04填写独立点与容许误差，由程序拟合并保存`ball_calibration.json`；教师可以课前采拟合点，学生至少核对3点。U7-L4与U8读取这份文件，所以负担还会延伸到后课。

这里确定的是本机、本姿态、本分辨率、本球与地面条件下的近似参数，不能叫通用“换算标准”。容许误差要在测试前按踢球需求确定，不能测完后调大阈值使其通过。

建议先比较SDK能力。若已有可靠球位，取消课内标定；若SDK组合定位可由教师稳定准备，提供有说明的辅助读取，学生理解与核对结果；只有固定映射在实际任务条件中通过测试且没有更合适方案时，才保留为明确条件下的辅助方案。即便保留，也不同时要求学生在一课中从零标定、理解全部算法并完成试踢。

## 6. 现在怎样逐步测试

原测试指导列出了标定、误差、丢球和退出等方向，但一次展开30项任务和多种路线，不便现场按步骤完成。按用户反馈，改为每次只交付当前一轮的操作、记录表及配套代码。

第1轮只做静止足球检测：版本与取图、单帧字段、有球和无球各20张新图。代码按表中默认18/20、0/20数量标准自动统计；这些是调查用初步标准，不是运动性能承诺。用户记录画面与标框是否符合实际，把结果目录填回表格，助手据此安排距离字段、深度或检测问题的下一轮。本轮不要求用户填写尚无依据的米制误差阈值。

[第1轮操作与记录](足球测试_第1轮_操作与记录.md)、[配套测试Notebook](足球测试_第1轮_静止检测.ipynb)。旧分级计划和旧探查Notebook已移除，SDK证据及本报告保留。

## 7. 对后续课程的影响

| 课程/附件 | 当前依赖 | 审核后的处理建议 |
| --- | --- | --- |
| U7-L2 | 自编换算与独立核对后接管理器 | 先确定球位来源，再重排课堂采点和试踢；世界坐标不设为基础要求 |
| U7-L3 | 只用`select_ball`取得像素目标，比较并发记录 | 不依赖拟合矩阵，可继续做静止检测/播报实验；不因球位方案待测而重教算法 |
| U7-L4足球片段 | `observe_ball`、标定文件、有限管理器窗口 | 统一改用最终验证的球位来源；保留新观测与交接原则 |
| `flows.py` | `observe_ball`和`kick_window`依赖当前标定 | 定位来源应与任务控制分开核对，最终方案确定后再改，不能混用两套坐标 |
| U8足球主题 | 需求/场地/管理器与标定前提、跨课文件 | 只整合教师预验证能力；取消重复从零建定位算法的任务，不让综合课替基础能力排险 |

教师控制验证还须单独检查：L2原函数先start再取首帧，L4附件有启动前观测但启动后重新取帧；两者不是同一启动保护。无球时管理器会怎样、旧球位多久失效、stop后实际停稳和重启行为，都需要文档依据或现场测试。有限循环秒数不能中断阻塞中的SDK调用，且现有“取图到处理耗时”不是完整数据图龄；这些条件不能靠固定映射的`verified`字段保证。
