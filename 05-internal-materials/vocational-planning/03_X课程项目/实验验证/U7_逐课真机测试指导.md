## 3. L2：足球定位与自动踢球

### 3.1 先验证静态定位

| 操作 | 核对方法与预期 | 记录要求 |
| --- | --- | --- |
| STEP 01，第 4 格 | 首次连接，导入 `SoccerKickManager`，创建对象但不调用 `start()` | 本机是否支持、创建对象时有无意外模式变化；本格不用于重置正在活动的管理器 |
| STEP 02，第 6 格 | 放一只球，检查实际 `class_name`、评分、分辨率及下缘中点 u/v | 官方示例为 `Ball`，以本机输出为准；类别不同须同时修改后续使用处，不能只改一格 |
| 重跑 STEP 02，球分别放在前方偏左/偏右及远/近 | 检出结果合理；图像 u 向右增大，与机身 y 向左为正的含义不同 | 位置与照片对应；未检出不补成中心坐标 |
| STEP 03，第 8 格 | 至少四个不共线、覆盖远近和左右的实测点；填写 `SETUP_NOTE` 后生成映射 | 每行是 `[u,v,x米,y米]`，机身测量原点由教师确认；少点或资料未齐时应停留在等待填写 |
| STEP 04，第 10 格 | 另取至少三个不同的、未参与拟合的内部点；填写教师确定的正数误差限 | 比较独立平面误差；只有全部达标才 `verified=True`；核对保存的 `ball_calibration.json` |

注意：`calibration is None`、核对资料不足或抛出异常时，不能把旧的 `ball_calibration.json` 当成本轮新结果。验证失败但已保存的文件也可能存在，需同时核对文件内容、`verified`、姿态说明和版本。

静态拒用检查可以在**不启动管理器**的条件下完成：用标定区域外的真实球位检查 `pixel_to_robot()` 是否报范围错误；向该函数传入与标定不同的分辨率，检查是否拒用。传入不同分辨率仅用于验证检查分支，不表示已完成另一分辨率的标定。没有足够场地覆盖有效区域时，应重新布点或缩小任务范围。

标定是课程附件提供的近似换算，不是 SDK 直接返回的球位置。检测框下缘并非精确地面接触点，误差会受球型、检测波动、姿态和光照影响。

### 3.2 教师先核查运动条件

**静止核对通过不能直接批准试踢。** 足球步态可能改变机身俯仰、头部和相机位置，使同一映射失效。教师需先按现场保护安排，用可核对的球位或录像，检查准备启动及实际步态中的坐标方向、误差与有效范围，并记录采用的核对方式。没有可执行的动态核对方法，或误差超出本次要求时，本课先停留在静态定位，反馈后再调整方案。

| 核查项 | 实际结果 |
| --- | --- |
| 标定时 / 启动前 / 足球步态时的头部和机身姿态 | |
| 坐标原点、x 前正与 y 左正是否一致 | |
| 动态核对方式、球位依据和误差范围 | |
| 哪些姿态或区域不能使用当前映射 | |
| 是否批准本轮运动及批准条件 | |

### 3.3 有限试踢与退出

| 操作 | 重点观察与预期 | 问题如何记录 |
| --- | --- | --- |
| STEP 05，第 12 格 | 仅定义函数，不运动；阅读 `start → update_command → 更新球位 → finally stop` | 核对本机四接口与参数支持情况；不要给返回 None 的接口加 `wait()` |
| STEP 06，第 14 格，先保持批准变量 False | 输出尚未满足运动条件，不启动 | 这只能证明批准分支，不能算试踢已通过 |
| 教师批准后，按已验证流程站稳并进入要求模式，再输入“试踢” | 低力度、单次有限窗口；观察真实模式变化、机身运动、坐标更新、停止原因和球的去向 | `direction=0`是相对当前机身向前；记录实际方向，不能当作固定场地方向 |
| 正常达到窗口，或自然出现丢球/超范围/处理慢/源时间戳未更新 | 结束循环并调用 stop；不继续使用旧坐标 | 保存停止原因、更新次数和录像；未自然出现的分支填“未测”，不要在运行路线内人工拿球诱发 |
| STEP 07，第 16 格 | 调用原管理器 stop，成功返回后清除 `kick_active`；现场确认停稳 | stop 异常时保留原对象及活动标记，先处理停止，不重跑连接格覆盖对象 |
| 停稳、复位并核对模式后再测一轮 | 没有旧控制争用，可按本轮条件启动 | 第二轮批准、站位和版本另记，不能直接连续点击运动格 |

现稿 `try_soccer()`先调用 `start()`和设置踢球指令，再进入取图循环，**没有启动前的首次球位检查**。测试前应静态确认当前球位可用，但这不能消除启动后首帧失败的可能。教师必须观察这一段在本机上的实际运动和停止表现；若启动即出现无法接受的运动，应暂停运动验证，先补启动前检查或调整方案。L4 的附件片段另有启动前检查，不能把其结果当作 L2 已具备相同保护。

六秒只限制循环检查窗口，SDK 某次调用阻塞时，不保证程序能在六秒立即返回。0.8 秒是取图前本地计时到处理完成的练习参数，不能测得完整图像年龄。若反复超时或源时间戳未更新，先定位数据问题，不为让机器人动起来删除检查或任意放宽阈值。

**本课分开记录**：接口调用/停止原因、管理器 stop 是否返回、机身是否停稳、球是否踢出、是否进入目标区。球未踢出不自动表示程序失败，程序正常退出也不表示已经射门成功。

## 4. L3：多线程协作

本课保持机器人固定，只缓慢移动检测目标。先确认 L2 管理器已停止，语音服务及适中音量可用。

| 操作 | 重点观察与预期 | 保存什么 |
| --- | --- | --- |
| STEP 01，第 4 格 | 首次连接与初始化；默认 soccer/Ball，也可成对修改模型和类别 | 实际类别、语音服务配置；重复测试不重跑此格清空旧对象 |
| STEP 02，第 6 格 | 旧线程存活或音频未结束时拒绝初始化；条件满足后创建同一把锁、STOP和共享记录 | 若拒绝，转 STEP 07 收尾，不能绕过检查重新绑定 STOP |
| STEP 03，第 8 格 | 只定义线程函数；每轮将编号、检出、位置、时间写入完整记录 | 若检测异常，记录 error、STOP与线程退出情况 |
| STEP 04，第 10 格 | 启动检测，主线程调用有限播报；缓慢移动球，保存播报前后两份记录 | 播报是否真实成功、编号差、坐标变化、source、error，以及末尾 is_alive |
| STEP 05，第 12 格 | 显示编号增量、取图和处理时长、处理后存放时长及可用判断 | 运行此格前的人工停留也会增加存放时长，不能解释成 SDK 变慢 |
| STEP 06，第 13 格 | 停留约两秒，再运行第 12 格 | 编号、坐标仍是同一份 after，存放时长增长，可用判断可能变 False；不是重新取图 |
| STEP 07，第 14 格 | STOP置位、join后检查 is_alive，另清理并检查音频 | `线程仍在运行=False`、`音频任务均已结束=True`；待处理项和检测错误原文 |

只有播报真实完成、检测编号在播报期间增长且目标记录合理，才能支持本课的并发观察结论。若语音立即失败，前后编号相同不能据此断定线程无效；若球没有移动，编号增长但坐标不变也可能正常。

STEP 04 的 finally 已请求停止线程，所以 STEP 05 并不读取实时更新中的记录。需要第二轮时：先 STEP 07 确认全部结束，再从 STEP 02 初始化，依次运行 STEP 03～05。不要仅重跑 STEP 04，因为上一轮 STOP 已置位。

如果 join 超时而线程仍存活，保留 `vision_thread`、STOP和原连接，等待调用结束后再次检查。只有原线程结束后才创建新 Event 和线程。不要故意断网制造无法回收的线程；实际遇到阻塞时保存调用位置和等待情况。本机是否支持当前取图/推理与语音任务并发，需要这次实测确认。

## 5. L4：多模态流程衔接

### 5.1 准备与首轮验证

| 操作 | 重点观察与预期 | 保存什么 |
| --- | --- | --- |
| STEP 01，第 4 格 | 首次创建 session，列出实际动作；加载的是本轮有效标定文件 | 动作 ID 的实际类型、模式/时长/范围；导览可先测，足球资料未齐不得批准 |
| STEP 02，第 6 格 | 将 `GREET_ID` 填成动作列表中的真实值，保持类型一致；只定义导览函数 | 现稿空字符串是占位符，未填不能执行；无效 ID 应返回具体原因 |
| STEP 03，第 8 格 | 只定义足球函数；未核对标定时返回原因 | 若只定义未运行，不能记作足球接口测试 |
| STEP 04，第 10 格，先保持 APPROVED=False | 不启动片段 | 批准分支输出 |
| 先选导览，现场批准后输入“运行” | 首次来宾可见 → 播报完成 → 新图像仍检出 → 致意 | 程序返回、音频/动作实际状态、现场动作；单名来宾不等于身份跟踪 |
| STEP 05，第 12 格 | cleanup后检查 idle，打印已有任务状态及 kick_active | 没有活动任务才能换场景或重试；未结束保留原 session |
| 再选足球，另核对 L2 动态条件与场地后运行 | 首次球位有效 → 播报完成 → 新图像球位有效 → 有限踢球控制 → stop | 足球坐标更新条数、返回原因、stop及球实际效果；不能沿用导览的批准条件 |

### 5.2 检查“后续步骤有没有被阻断”

| 用例 | 安排 | 预期 |
| --- | --- | --- |
| 首次没有来宾 | 在安全、无致意条件下运行导览；镜头内不安排其他可检出人物 | 返回首次未检出来宾，不播报、不致意 |
| 播报后目标离开 | 导览来宾在场地外侧、播报期间离开画面；不进入机器人活动范围 | 返回播报后未检出来宾，跳过致意 |
| 有新目标位置 | 静态足球观察中改变球位置后再取图；实际试踢时不让人员入场取球 | 新结果对应当前位置；不能拿播报前坐标直接控制 |
| 无效标定 | 静态检查缺文件、verified=False、范围或分辨率不符 | 返回明确原因，不启动足球管理器 |
| 无效动作 ID | 使用确认不在列表中的值，单独验证拒用分支 | 不调用 do_action；不能把拒用记成动作运行通过 |
| 播报失败、处理超时、旧源图像、动作未成功 | 自然出现时保留输出与状态，不强行制造网络或运动故障 | 不进入下一行为；未发生项登记未测 |

当前执行格只打印最终原因，并非每次都显示首次/播报后观测。为核实交接，可在教师测试副本中，在两个函数已有的 `first = ...`、`current = ...` 后分别增加 `print("首次观测：", first)`、`print("播报后观测：", current)`，并在 `say()` 返回后打印 result。每轮按实际执行到的位置保存输出；副本与增加打印后的耗时单列记录。不要为了补打印在正文执行格外单独调用 `guide_segment()`、`soccer_segment()`或 `kick_window()`，那会绕过本课现场批准检查并再次发起行为。

`greet()`当前仅将 `SUCCEEDED`作为“完成”。如果动作肉眼已播完、句柄却一直未成功，最后取消得到 `CANCELLED`，应同时记录这两个事实，片段仍按当前约定结束。U6 某些动作“等待后取消才释放占用”的真机经验不能自动推广为所有动作都可视为成功；需由教师为本动作确认交接条件，再决定是否改附件。

L4 的 `idle(session)`只核对本会话保存的资源，不代表其他 Notebook 或连接没有活动任务。若报告 `Robot is busy executing another action; cannot start action task`，先保留已有对象，运行拥有旧任务的课程收尾格；依据原任务状态及现场表现处理后再试。不要重建 session 或反复启动覆盖旧句柄。
