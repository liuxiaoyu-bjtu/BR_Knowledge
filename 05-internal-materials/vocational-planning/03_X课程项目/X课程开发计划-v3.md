### 11.3 工期评估：10-20 是否够、是否合理

**结论：10-20 完成全量（5 阶段、32 单元）在「AI 生成节奏 + 流水线并行 + 国庆预写」前提下可达，但余量极小（可用 43 工日 vs 需求约 41 工日），属紧平衡，任一环节掉队都会击穿节点。**

**需求测算（AI 生成节奏，区别于人工从零撰写）**：
- Phase 1 实验代码 32 notebook ≈ 11 WD
- Phase 2 大纲嵌入 32 ≈ 6 WD
- Phase 3 手册详写 + PDF + 教学设计 32 ≈ 10 WD
- Phase 4 PPT 内容 32 ≈ 6 WD
- Phase 5 PPTX 32 ≈ 8 WD
- **合计 ≈ 41 WD**，可用 43 WD，**缓冲仅约 2 天**。

**为什么能压进 10-20（关键在流水线，不在总量）**：
- 整阶段串行需 41 WD 且不含门禁冷却；本计划用**跨单元流水线**，把国庆 0 工日变成「确认① 审核 + P3 预写」窗口，使 P3–P5 尾段（约 24 WD 工作量）被并行前置，最终只占用国庆后 10 个工日。

**四大前提（任一不满足则 10-20 不保）**：
1. 确认① 必须在国庆期间（10-01~10-07）审核通过，最迟 10-08 签署——否则 P3 无法假期预写，尾段退回串行、缺约 14 工日。
2. P4/P5 采用统一模板批量生成，不可逐页精雕。
3. 用户验证/确认门禁周转 ≤ 2–3 工日；前序单元掉队时优先保 U1–U4。
4. AI 保持生成节奏（不被长时阻塞）。

**风险与兜底**：
- **最大风险**：P5（32 PPTX）是尾段长杆，若前面任一环节延迟，最先被挤压。
- **兜底方案**：若至 W9 末（10-16）P5 进度 < 50%，则**优先交付 U1–U4 的 PPTX**（前 16 课时教学刚需），U5–U8 的 PPTX 顺延至 10-23 起补完——保证 10-20 至少有「可开课的核心交付」，全量不晚于 10-28。

**对比旧评估（10-15 方案 A）**：原方案把 10-15 设为「核心交付」（仅 P1+P2+确认①+前 16 手册），PPT 顺延 11 月。现因硬性 10-20 全量要求，改为「国庆预写 + 流水线」打法，把 P3–P5 全部拉进 10-20；代价是余量从宽松变为紧平衡，对门禁周转要求更高。

### 11.4 跟踪使用说明

- 每周末核对「本周交付目标」勾选状态（⬜→✅）。
- 两个门禁（确认①、确认②）必须由用户审核通过后才解锁后续 Phase。
- 若某周落后，优先保 U1–U4（前 16 课时）进度，后段单元可顺延。

## 三、各阶段详细说明

### Phase 1：实验代码开发（Jupyter，python cells + 必要说明）

**目标**：为每个课时编写 jupyter notebook，主体为可运行 python cells（BoosterOS SDK 调用），辅以最小必要说明。

**定位**：AI 编写，用户验证运行。notebook 是工程代码包，不是验证报告。

**每个 notebook 包含**：

| 内容 | 说明 |
|---|---|
| 代码 cell | 本课时轻任务的可运行实验（BoosterOS SDK 调用） |
| 说明 cell（markdown，最简） | 标题、目标一句话、运行前置（连接/模式/依赖） |

**设计原则**（沿用 v2 并适配 notebook）：
1. **低耦合**：每课时一个独立 notebook，不依赖其他课时
2. **可渐进**：从 `boosteros` 最简 API 出发，逐步打开 SDK 能力面
3. **有输出**：每个 cell 运行后产生可见结果（print / 保存文件 / 机器人动作）
4. **有注释**：关键 API 调用处标注说明（markdown cell 或代码注释）
5. **安全第一**：涉及运动的 cell 有安全提示和限速
6. **U4 项目化**：U4 四课时以「商业展厅迎宾导览模块」项目组织，单课时 notebook 可独立运行，L4 整合完整行为链
7. **跳过 SDK 占位字段（重要）**：BoosterOS SDK 持续开发中，许多返回值/方法当前为 `None` 占位（如 `list_joints()` 的 `max_torque`/`max_velocity`/`limits` 均为 `None` 或 `0.0` 占位）。**本课程只使用已开放、有真实值的字段，占位字段一律不出现在实验中。** 实验代码与说明中不得访问、打印或要求学生填写这些 `None` 占位字段；若该接口仅占位字段可用，则不在课程中使用该接口。

**交付物**：**32 个 `.ipynb`**（U1–U8 各 4）。其中 **30 个含实验 python cells**；**U8-L1（选题拆解）、U8-L4（展演答辩）为纯教学环节，notebook 仅留骨架/占位，无实验 cell**（详见§五清单）。

**存储位置**：`vocational-planning/notebooks/`

### Phase 2：大纲嵌入 + 确认①

**目标**：在 Phase 1 notebook 基础上补充 markdown cells，将 v4 大纲的"单元目标 / 知识线 / 核心概念 / 轻任务映射"嵌入文档，形成"代码 + 教学设计框架"的草稿，供用户确认大纲映射是否正确。

**前置条件**：Phase 1 对应单元实验代码验证通过
**组织方式**：**按课时**（沿用 32 个 notebook，原地演进）

**补充的 markdown 内容**：
1. 单元定位与边界（如 U4「看见 vs 据所见去行动」）
2. 本课知识线 / 技能线（双主线）
3. 核心概念标注（对照 v4 编号，如 B01 P控制、B02 模仿学习）
4. **轻任务 ↔ 代码 cell 对应表**（关键审核点：每个轻任务是否都有可运行 cell 支撑）
5. 行业/职业认知锚点（U1/U4/U8 的可选了解模块预留位）

**门禁**：⚠️ **确认①** — 用户审核 notebook 内大纲设计后进入 Phase 3。

**交付物**：32 个 `.ipynb`（已嵌入大纲 markdown，仍为草稿态，原地演进）。

**存储位置**：`vocational-planning/notebooks/`（同 Phase 1）

### Phase 3：详细编写（实训手册定稿）+ 导出 PDF + 教学设计

**目标**：确认①后，补全 notebook 详细内容，达到参考书（《计算机视觉实训书书稿》）体例，成为可直接给学生用的实训手册；导出 PDF；之后派生教学设计。

**前置条件**：确认①通过
**组织方式**：**按课时**（32 个 notebook 原地演进至定稿）

**实训手册 notebook 体例**（借鉴参考书章节结构）：
- **实验目的**：本课要解决什么问题、达成什么能力
- **知识原理/背景**：核心概念讲解 + 通俗类比（呼应 v4 知识线/轻量概念）
- **环境与准备**：依赖、连接 K1、运行模式、安全须知
- **实验步骤**：分步（说明 cell + 代码 cell + 预期输出/截图占位）
- **检查点（checkpoint）**：每完成一步自查
- **思考题 / 扩展任务**：拔高与延展
- **评价自检表**：学生自测

**交付物**：
- **A — 实训手册 notebook（定稿，学生用）**：32 个 `.ipynb`（即 Phase 2 草稿演进完成）
- **B — 实训手册 PDF（打印用）**：32 份 `.pdf`（notebook 导出）
- **C — 教学设计（教师用，派生文档）**：32 份 `.md`（由 notebook 派生：环节展开、讲法话术、演示步骤、FAQ、板书/PPT 要点）

**存储位置**：
- `vocational-planning/notebooks/`（定稿源文件）
- `vocational-planning/实训手册PDF/`
- `vocational-planning/教学设计/`

> 注：实训手册（A/B）确认后，**同步生成**教学设计（C），教学设计非独立门禁。

### Phase 4：PPT 内容大纲设计

**目标**：设计每课时 PPT 的页面结构与内容要点，作为 PPT 制作的蓝图。

**前置条件**：Phase 3 对应单元完成
**组织方式**：**按课时**（每课一份，用户明确"每课多少页、每一页大概内容"）

**每课 PPT 内容设计包含**：
1. **页面清单**：预计 15–25 页/课时
2. **每页设计**：页面标题和类型（封面/知识页/代码页/演示页/互动页/总结页）、核心内容要点、视觉建议（图片/图表/动画）
3. **代码展示页**：对应 notebook 中哪些 cell、高亮建议
4. **互动/演示页**：互动设计和演示流程

**交付物**：**32 份 PPT 内容大纲**（`.md`，每课 1 份）

**存储位置**：`vocational-planning/PPT内容设计/`

**门禁**：⚠️ **确认②** — 用户审核 PPT 内容设计后进入 Phase 5

## 十一、备忘：v3 相对 v2 的核心变化

v2 把交付物拆成六类独立文档（实验代码 `.py` + 课时大纲 `.md` + 实训手册 `.md` + 教学设计 `.md` + PPT内容 `.md` + PPTX，共 142 份）。v3 基于新决策**改用 Jupyter Notebook 作为实训手册的单一源文件**，关键变化：

1. **实验代码包 = `.ipynb`**，不再是 `.py + README`；主体为 python cells，辅以必要说明 cell。
2. **原 Phase 2「课时大纲」与原 Phase 3「实训手册」合并进同一个 notebook 的演进**：
   - Phase 1 写代码（python cells + 最小说明）
   - Phase 2 在 notebook 内补 markdown，嵌入大纲设计 → 确认①
   - Phase 3 补全成完整实训手册（参照参考书体例）
3. **实训手册 = 最终 `.ipynb` 直接导出 PDF**（可打印），学生端打开 notebook 学习、教师端导出 PDF 印发。
4. **教学设计（教师用）作为 notebook 确认后的派生文档**单独生成，不进 notebook。

> 净效果：大纲设计不再是一份游离的 `.md`，而是"长"在代码旁边的 markdown，代码↔大纲映射在 Phase 2 即可被审核，避免 v2 中"代码和大纲各写各的、最后才发现对不上"的风险。
