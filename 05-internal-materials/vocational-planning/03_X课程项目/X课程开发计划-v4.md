## 一、v4 相对 v3 的核心变化（历史调整记录）

> 本节保留当时的阶段编号与定义；现行 P1–P6 及旧、新编号对照见 §三。

v3 开发计划（2026-08-17）按「Phase 1 代码骨架 → Phase 2 大纲嵌入 → 确认① → Phase 3 手册 → Phase 4 PPT 内容 → 确认② → Phase 5 PPTX」五阶段建模。但 U1 实际开发（记录于 `notebook开发规则.md` §1/§6/§7）走通的是另一条、并被证明更合理的路径。本 v4 据此重排：

1. **相位模型重构（关键）**：v3 把「代码 → 大纲嵌入 → 详写手册」拆成三段独立 Phase，假设先写代码骨架、再嵌大纲、最后补写成手册。U1 实测证明：notebook 从一开始就是**实训手册单一源文件**，由 `_gen_Lx.py` 一次性生成（含课头/实验头分层、课程大纲映射审核块），所谓「大纲嵌入」只是生成器里的一个 markdown 块，所谓「详写」是迭代同一文件。因此 v3 的 P1/P2/P3 在实操中**合并为「notebook 实训手册开发」一个活动**，v4 首版据此不再虚拆；但 2026-08-27 二次修订已恢复 v3 式 P1/P2/P3 拆分（见 §一.6），单源演进事实不变，只是三段各自独立成 stage、独立卡门禁。
2. **门禁体系澄清**：开发记录里出现过两套叫法（v3 的「确认①/确认②」与规则文件的「确认①③/④/⑤」）。v4 统一为 **四道用户确认闸门**，并固定其真实位置（见 §三）。
3. **单源生成法固化**：确立「改 `_gen_Lx.py` → 重跑 → 覆盖生成 notebook」的迭代闭环，并用 `splitlines(keepends=True)` 保证重跑后 notebook **逐字节一致（RAW EQUAL）**。这是 U1 后期（L4 反复重构）沉淀出的可靠工作法。
4. **内容纪律写入计划**：安全提示分级呈现、真实 SDK 字段仅用、不写虚构动作名、收尾走 `prepare`+手动趴姿严禁程序直进 `damping`、`TaskHandle`/`ActionInfo` 以真返回值探究——这些在 U1 中反复修正得出的硬规则，提升至计划级约束（见 §五）。
5. **重定基线**：v3 进度表以 2026-08-17 起算、目标 10-20 全量；现已过 08-27，且 U1 已实质完成，v4 以「U1 为验证切片、U2–U8 套模板规模化」重新排程（见 §九）。
6. **两阶段宏流程（二次修订）**：U1 验证后，U2–U8 不再按单元内 P1–P6 全链推进，改为「**Phase I 全量 P1（逐课用户手工确认 G1）→ Phase II 逐课 P2–P6**」；P1/P2/P3 恢复 v3 式拆分；P2↔P3 之间增设 G2 确认；P7 仍全课程结束后批量。详见 §三 / §九 / §十。

## 四、各阶段详细说明

### P1 与 P2：Notebook 初稿、验证与定稿

每课维护一个 `.ipynb`，同时作为学生学材与最终实训手册源文件。具体要求以 `../02_共创规则与上下文/notebook开发规则.md` §1、§8 为准。

- **P1**：完成可供学生逐格学习的初稿，包含课程头、目标、必要知识、实验设计与代码、操作和观察提示、结果解释、记录及相应检查评价；附件按需引用。完成后用户审阅设计（确认①），再用 Notebook 做真机验证（确认②）。P1 不是无代码框架阶段。
- **P2**：在确认②后，由助手核查目标覆盖、技术事实、前置知识与承接、文字和代码及实测结果的一致性、附件、评价、安全与表达。按实际缺口判断，不统一重写课头、知识讲解或练习，也不强制向学生正文添加大纲审核块。
- **有问题**：先报所在课节或单元格、问题、影响、建议改法与是否补验；用户批准后修改、复核。改变实验行为或操作安全的部分由用户重验受影响单元格。
- **无问题或修订后通过**：记录审定依据，提示「可以进入 P3」，审定结束时不自动编写教学设计。尚有待解决或待补验的问题时不标记通过。

**关键纪律（源自 U1 开发记录，硬性）**：
- **单一源文件与生成器同步**：以当前 Notebook 为准，同步生成器并核对逐格内容；保留用户手改、真机输出与执行记录，不运行过期生成器覆盖现稿。
- **课头/实验头分层**（§8）：首 cell = 课程级（课程名 + 课程目标，不写安全/前置）；首个动手实验环节头 = 实验级（实验名称/目标/⚠️安全/📌前置）。
- **安全提示分级呈现**（§3.5）：**仅「第一次 code 实验」前给完整 ⚠️ 安全**（含 `walk → prepare`、严禁 `walk → damping`）；后续独立实验开头只写红字关键说明（`<font color="red">执行下面任务前，确保机器人处于 X 模式，并且……</font>`）。
- **真实 SDK 仅用**（§3.7）：只访问有真实值的字段，不打印/不要求学生填 SDK 占位 `None` 字段；不写虚构动作名（如「挥手/鞠躬」），以 `list_actions()` 读到的 `id`/`type` 为准。
- **收尾安全**：任何运动实验收尾不得程序直进 `damping`；先 `set_mode("prepare")` 回站立，再红字提示「手动放趴姿 → 按约定 `damping` → 关机」。
- **前向引用纪律**（§8.7）：除 U1-L1 外，各课不得出现「后面单元将…」字样。
- **人工窗口拆分**（§3.8）：凡「发准备指令 → 人工拉起/确认 → 发执行指令」，须拆独立 cell + 红色人工确认提示 cell（源自 L2 真机测试）。

**交付物**：32 个 `.ipynb`（P1→P2 原地演进，单一源）。其中 U8-L1（选题拆解）、U8-L4（展演答辩）以非代码学习活动为主，仍需完整呈现学生任务与记录要求，不以无代码为由只交框架。

### 9.2 工期评估：10-20 是否够、是否合理（周期固定，不评估改期）

**结论：10-20 全量交付是 v3 锁定的硬性周期，本计划不评估、不提议改期。在「AI 生成节奏 + 五道闸门按单元集中周转 + 套用 U1 模板 + 国庆预写」前提下，10-20 可达；但余量极小、属紧平衡，且真正瓶颈是门禁周转（尤其 G1 逐课真机验证），任何环节掉队都须靠窗内重排吸收，而非顺延日期。**

**需求测算（AI 生成节奏，区别于人工从零撰写）**：
- P1 实验代码骨架 32 notebook ≈ 8 WD（仅代码 cell + 极简脚手架，低于 v3 的 11 WD，因不写正文）
- P2 大纲嵌入 32 ≈ 6 WD
- P3 实训手册详写 32 ≈ 9 WD
- P4 教学设计 32 ≈ 4 WD（从 v3 的「Phase3 捆绑包」中拆出）
- P5 PPT 内容 32 ≈ 6 WD
- P6 PPTX 32 ≈ 8 WD
- P7 PDF 批量 32 ≈ 2 WD（自动化导出为主）
- **合计 ≈ 43 WD**，v3 固定窗口可用约 43 WD（含门禁冷却），**余量紧张（≈0~2 WD）**——与 v3 同属紧平衡。

**为什么必须窗内重排、不能改期（关键在周转，不在总量）**：
- 全课程共有 **G1×32 + G2×28 + G3×28 + G4×28 + G5×28 ≈ 144 次用户确认**。即便每次仅 0.5 工日冷却，也占约 72 工日，远超生成产能——因此排程的真正变量是确认闸门周转节律，而非 AI 写得多快。
- Phase I 的 **G1 逐课真机验证**最依赖用户真机时间，是 Phase I 长杆；Phase II 的 G2–G5 须随单元批量处理以压进固定窗口。

**四大前提（任一不满足则 10-20 不保，但只能窗内补救）**：
1. **G1 须按单元节奏集中验证**（每周一个单元 4 课），门禁周转 ≤ 1 工日/单元；否则 Phase I 滞后只能靠压缩 Phase II 吸收。
2. **P4/P5/P6 套用 U1 验证模板批量生成**，不可逐页精雕。
3. **G2–G5 用户审核周转 ≤ 2–3 工日/课**；前序单元掉队时优先保 U1–U4。
4. AI 保持生成节奏（不被长时阻塞）。

**风险与兜底（均在 10-20 窗口内）**：
- **最大风险**：G1 真机验证节律（依赖用户真机排期）是 Phase I 长杆；若某单元验证滞后，只能压缩 Phase II 周次或启用国庆预写兜底，不得顺延至 10-20 之后。
