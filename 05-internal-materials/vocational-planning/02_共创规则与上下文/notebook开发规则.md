## 1. 文件与工作流

- 单一源文件 = `.ipynb`（Jupyter Notebook），由 `python cells` + 必要的 `markdown` 说明组成。
- 该 ipynb **同时作为「实训手册（学生版）」源文件**：学生端直接打开 notebook 学习；教师端在**全部课程开发结束后统一导出 PDF** 印发（见 P6），不在单课开发中途导出。
- 命名规范：`03_X课程项目/notebooks/U{单元}-L{课时}_{关键名}.ipynb`，例：`U1-L1_具身智能概览与连接K1.ipynb`。
- **现行六阶段工作流（2026-10-20）**：连续执行 P1–P6；Phase 与确认节点独立编号，保留①～⑥的节点编号，其中③为助手审定节点，有问题时才需用户确认修改方案。
  - **P1 学生 Notebook 初稿与实验设计**：一次完成课程头、课程目标、知识讲解、实验设计与代码，以及相应的观察记录、结果解释、检查与评价任务；附件按实际需要引用。知识课与实训课均可包含知识引入和代码练习，按本课目标安排，不机械套用同一节序。初稿应能供学生逐格学习，不能只交无代码框架，也不将必要知识统一留到 P2 补写。
    - **确认①（设计审阅）**：用户审阅课程结构、知识承接、实验任务与代码是否适合本课目标。此时的代码是待真机验证的初稿，确认①不代表运行通过。
    - **确认②（真机验证）**：用户在机器人上用 Notebook 逐格运行，确认接口、操作顺序、输出与现象；助手根据用户反馈提出修订。只有受影响的代码与操作获得真机确认后，才能进入 P2。一次反馈可同时包含设计审阅和运行结果，但记录时应分清①、②的依据。
    - **合并与重编号记录**：2026-10-10 将旧 P2 的实验设计和代码编写并入 P1，用户真机验证保留为确认②，当时暂停使用 P2 编号。2026-10-20 将旧 P3 调整为复核与定稿，并按实际工作连续重编号：旧 P3–P7 对应现 P2–P6。
    - **真机验证的载体是 Notebook 本身**：必须逐格验证；独立 `.py` 探针只能辅助，不能替代 Notebook 验证。P1 不编造实测数据；已有实测记录保留，新增结果以用户提供的真机记录为据，在 P2 核对。
  - **P2 真机验证后的复核与定稿**：助手依据确认①、②及现稿进行审定。发现问题，先提供问题和修改方案，待用户确认后修改、复核；没有问题，直接提示「可以进入 P3」。具体执行见下文「P2 审定约定」。
  - **P3 教学设计（教师用 .md）**：在 P2 审定通过后编写时间轴、教学环节与学习评价等 → 完成后由用户确认④，再进入 P4。
  - **P4 PPT 内容大纲（每课页设计）** → 完成后由用户确认⑤，再进入 P5。
  - **P5 PPTX 开发**：须在确认⑤后编写 → 完成后由用户确认⑥。
  - **P6（全课程开发结束后统一进行）**：按统一模板导出实训手册 PDF；移除课程大纲映射、课程设计备忘等内部审核文字，并删除学习评价的参考答案，保留学生作答题目。

### P2 审定约定

1. **输入与范围**：以已通过真机确认②的 Notebook、用户运行记录及现行大纲为依据，检查课程目标与内容、练习及评价的对应关系；核对技术事实、前置知识、知识承接、代码与文字、实测结果、操作安全、附件引用和去 AI 化表达。面向已学课程的高职学生审读，不能默认学生学过系统的深度学习或强化学习课程。
2. **按现稿判断缺口**：检查学生是否获得完成学习任务所需的知识、操作、观察与解释。已有内容直接复核，不为满足 P2 名称重复补写；不以缺少某个固定栏目判定缺内容。大纲覆盖关系须核查，可记录在内部审定记录中，无须为了走流程在学生正文中新加审核块。
3. **发现问题**：先列出「所在课节或单元格、具体问题、对学习或运行的影响、建议改法、是否需要补做真机验证」，交用户确认后修改。修改后复核；若涉及代码行为、运行顺序、运动参数或安全操作，须由用户重验受影响的单元格，不能沿用修改前的通过结论。
4. **未发现问题，或批准的修改已完成并通过复核**：给出简要审定结论，提示「可以进入 P3」，记录通过日期与依据；有待修改或待补验的问题时，不标记通过。保留③作为审定节点编号，后续④～⑥不重编号。

## 2. Phase 1 实验代码设计约定

1. **禁用复杂程序结构**：不写 `try/except`、`assert`，不定义 `print_section` 之类辅助函数。课程面向初步程序能力者，目的是探索 BoosterOS SDK，代码越精炼、越直指学习目标越好。
2. **P1 同时完成学生材料与实验设计**：课程导入、必要知识和实验代码在同一初稿中编排，知识与实践按学习任务衔接；P2 在用户真机验证后审定已有内容，发现缺口先提出修改方案。
3. **实验分三类**：
   - **运行类**：md 指示 → 运行提供的 python 单元格 → 观察结果、理解知识/能力。
   - **填空类**：md 给出任务/练习/问题 → 学生删除 python 代码中的下划线占位符、补全程序才能运行 → md 提示「删除下划线并补全」。
   - **自主编写类**：md 描述任务 + 提供空白 python cell → 学生自主编程。不要求每课都有，视整体内容设计而定。
4. **课头精简（必守）**：
   - 不写【单元】【课时】【实验类型】等标题框。
   - 不写「Phase 1 范围说明」之类 meta 注。
   - 实验类型**不**在每课开头描述，由未来统一汇总文档记录。
   - 步骤名称上**不**标注（运行类）等类型标签。

## 3. 内容与表述规则（面向学生文件）

1. **不写交互/日志型话术**：学生文件**不写**「我与你交互形成的决策叙述」，例如「本实验仅读取已开放的…`max_torque` 尚未开放不纳入」「字段说明：SDK 持续更新中…」等。只描述内容本身；设计理由、占位约束等记入内部开发计划/记忆，**不进学生文件**。
2. **不写课程设计前向引用 / 前因后果**：如「IMU、里程计等将在 U2 详细学习」这类设计逻辑**不给学生看**。保留学生向表述（如「机器人有自身状态」）。
3. **仅使用 SDK 已开放、有真实值的字段**：`None` / 占位字段一律不出现在实验代码、说明、或填空/自主编写题中。若某接口仅占位字段可用，则不在课程中使用该接口。
4. **真机实测字段可用性（K1，以真机为准）**：
   - `list_joints()` 每项：`limits`（min/max，单位 rad）**有数据→纳入**；`max_velocity`（rad/s）**有数据→纳入**；`max_torque`（恒 `None`）、`extra`（空）→ **不纳入**。
   - `robot_info`：`manufacturer` / `model` / `name` / `serial_number` / `firmware_version` 均打印（空字符串本身有教学意义）。
   - `get_joint_states()`：仅 `position`（rad）可用，本实验仅观察角度。
5. **涉及真机连接 / 运动的实验**，须加：
   - 「📌 前置准备」注：须先完成 K1 **开机、配网（连同一 WiFi）、查看 IP**，并能用 **BoosterStudio** 成功连接机器人。
   - 「⚠️ 安全提示」注：说明本实验是否涉及运动。**涉及行走 / 运动者，必须写明安全收尾路径——停止须 `walk → prepare`（站立稳定），再经坐下后进入 `damping`；严禁 `walk → damping` 直接切换（站立会瘫倒）。** 详见 §3.6。
   - **分级呈现（避免逐实验重复、稀释重点）**：每节课**仅在「第一次 code 实验」前**给一份**完整**安全提示（含是否涉及运动、收尾路径 `walk → prepare`、严禁 `walk → damping`，见 §3.6）。**后续独立任务（实验）开头不再重复完整安全提示**，只用**红字**给出关键说明，例如：`<font color="red">执行下面任务前，确保机器人处于 walk 模式，并且……（对环境、操作进行安全提示）</font>`——点明本任务所需运行模式 + 环境 / 操作安全要点即可。📌 前置准备（机器人状态 / 已完成的前序实验）仍可在红字外单独保留。

6. **K1 运行模式安全约束（务必准确，禁止误导）**：
   - `damping`：软态，关节有阻尼但**整体无法维持站立**；只能在坐姿（椅子上）或趴姿下进入。开机默认态。**不能**作为“行走后直接兜底”的切换目标。
   - `prepare`：维持站立就绪姿态；须用 **Stand** 把机器人拉起到站立。趴姿下不可直接进入 `walk`。
   - `walk`：**只能由“已 STAND 站立的 prepare”进入**；趴姿进入会关节乱动、腿部乱踢。靠动态平衡维持站立。
   - `custom`：进阶自定义模式，需用户单独编程（SDK 提供 `set_mode("custom")` 与关节指令能力，见 `joint_control_example.py`）才能产生动作；未编程前比 damping 更软，只能在趴姿下进入。**是否纳入某课，须同时满足：① SDK 提供该模式的自定义编程能力；② 该课有对应的 custom 教学设计。** 当前 L2 不满足 ②，故不涉及。
   - **严禁 `walk → damping` 直接切换**（站立瘫倒）。安全停止顺序：`walk → prepare`（站立稳定）→ 坐下 → `damping`（坐姿软态）。
   - 涉及模式切换 / 运动的 notebook，「⚠️ 安全提示」须写清上述约束，不得写“实验结束切回 damping 即安全”之类误导性表述。

7. **「课程设计备忘」标记约定（临时占位，必须删除）**：Phase 1 编写时，若需在 notebook 中临时记录**面向后续 phase（大纲嵌入 / 详细编写等）的设计提示**（如「L2 适合融合 K1 手柄实操」），用「> 📝 课程设计备忘（待后续 phase 细化）」引用块标注。**该标记不是给学生看的内容，是内部临时占位**：在后续对应 phase 把所指内容正式整合进 notebook 后，**必须将这一句整行删除**，不得残留到实训手册 / 学生文件。

8. **真机安全：需人工配合的操作必须拆分 cell（源自 L2 真机测试）**：凡 notebook 中涉及「先发送准备指令 → 必须由人工完成某动作（手动拉起机器人到 STAND 直立站立、确认周围安全）→ 再发送执行指令」的环节，必须把准备指令、人工窗口提示、执行指令分别放在**独立 cell**，cell 之间留出人工操作时间。
   - 严禁将 `set_mode("prepare")` 与紧随其后的 `set_mode("walk")`（或任何进入 walk 的指令）放在同一 cell 瞬间连续执行——否则程序会在机器人尚未被拉起站立时直接进入 walk，导致关节乱动、腿部乱踢。
   - 在两个需要人工配合的指令之间，插入一个明显的 markdown 提示 cell（如红色文字「确定已手动拉起、处于直立站立、周围空旷、教师监督下，再运行下一格」），由人工确认后再运行下一 cell。
   - 该原则源自 U1-L2 真机测试：将行走安全路径从「单 cell 连续执行」拆为「多 cell + 人工窗口」，消除了未拉起即进 walk 乱踢的风险；后续 L3/L4 等涉及 walk 的 notebook 均须沿用（见 §7 变更与下方 L3/L4 交付说明）。
   - **经 L1–L4 实践修订（轻量化）**：`prepare → 人工窗口 → walk` 的"多 cell + 人工窗口"拆分，**仅保留在 notebook 中「首次进入 walk」那一次**（即必须手动拉起 STAND 的真实物理危险点）；其余步骤**不重复拆分**，只在必要代码格前用一句话标注该格所需的运行模式（如「机器人处于 `walk` 模式」「当前在 `prepare` 直立」）即可，避免逐格重复、稀释真正的安全闸门。无特定教学设计意图时，不要求每个 python cell 都说明模式。

9. **去 AI 化表达（所有输出类文档强制）**：
   - **依据文档**：`05-internal-materials/去AI化表达记录.md`（源副本 `D:/A_Project/去AI化表达记录.md`），两处须保持一致。
   - **适用范围**：notebook 实训手册、教学设计、PPT 内容大纲、PPTX、计划与规则文档等**一切对外输出**。写成后须对照该记录逐条自查，再提交用户审阅。
   - **闭环要求（此前遗漏，务必执行）**：用户新指出的 AI 味表述，除改当前文档外，**必须同步沉淀为该记录的新条目**——记录具体句式、典型例子、风险、替代表达、改写原则。**只改文档、不沉淀规则，视为未完成。**
   - **高频雷区**（详见该记录 §8–§15）：「把……拆开来看」「只干一件事」「一句话记 / 记住这几个」「给出 X 样东西 / 解读 X 条规律」「后面会讲 / 后面所有课都……」、解释「我们为什么这么写」的元话术、用抽象概念解释抽象概念、提前引入后续术语。

## 4. cell 结构规则

1. **用户刻意的多 cell 拆分不可合并**：cell 的拆分方式本身是有意义的教学设计。重做 / 修改已存在的 notebook 时，**只改格内内容，不动 cell 边界**（含 cell 顺序）。
2. **新建 notebook** 应做合理拆分：一个步骤可用「多个 md cell + 多个 python cell」组合，便于讲解与观察。
3. **每课末尾新增「学习评价」markdown 单元**：
   - 含 **2~3 题**混合（判断 / 填空 / 选择），留空供学生作答。
   - 参考答案用 `> 参考答案（教师留存，勿印发给学生）` 引用块，置于同一 cell 内。
   - 格式示例见 `03_X课程项目/notebooks/U1-L1_具身智能概览与连接K1.ipynb` 末尾 cell。

## 5. BoosterOS SDK 技术约束

- **导入路径**：
  - `from boosteros.robots.booster import BoosterRobot` ✅
  - `from boosteros.brain import Detection` ✅
  - `from boosteros import BoosterRobot` ❌（顶层 `__init__` 为空）
- **真实可用的接口 / 字段**：
  - 连接：`BoosterRobot()`
  - 信息：`robot_info`（manufacturer/model/name/serial_number/firmware_version）、`list_joints()`（name/limits/max_velocity）、`list_actions()`（id/type/duration/interruptible）
  - 状态：`get_mode()`、`get_battery()`、`get_joint_states()`（仅 position）
  - 模式：`set_mode("damping" | "prepare" | "walk" | "custom")`（`get_mode()` 返回同名字符串；prepare 为行走前置且须已站立、walk 接收速度指令、damping/custom 为软态仅可在坐姿/趴姿进入；安全约束见 §3.6）
  - 运动：`set_velocity(vx, vy, vyaw)`、`set_head_angle(pitch, yaw)`（walk 模式下）、`set_gait("default" | "soccer")`、`do_action(action_id)`
  - 感知：`get_odom()` / `reset_odom()`（`pose_2d = [x, y, yaw]`）、`get_imu()`（`angular_velocity` / `linear_acceleration`；**航向用 `odom.pose_2d[2]`，不取可能 `None` 的 `imu.orientation`**）、`detect()`（bbox.center / bbox.area）

1. **二级标题 = 本课的学习阶段/环节**：用 `## 一、… / ## 二、… / ## 三、…` 对应本课主要阶段（例：`## 一、具身智能与人形机器人认知`、`## 二、连接 K1 并读取身份与身体清单`、`## 三、检查点、思考题与学习评价`）。三级标题（`###`）用于阶段内小节（如 `### 1.1 什么是具身智能`）。
2. **每个阶段都要有"值得记录呈现的必要信息"；非代码运行的活动必须在 md cell 中呈现（学案要求）**：
   - **总原则（本 ipynb = 学生实训手册 / 学案）**：凡是课程中**不属于代码运行**的活动（观察记录、手动操作、手柄 / APP 实操、配网、人工安全确认、拓展阅读等），都**必须在 notebook 中以 markdown cell 呈现**，不能只停留在教学设计或教师脑中。原因：学生需对照本文件完成全部学习动作。
   - **两类非代码活动的呈现方式**：
     - **情景 1（纯文字即可完成记录）**：直接用 md cell 以合理形式记录——如观察记录表（学生填写）、操作步骤清单、安全自查清单、思考题等。
     - **情景 2（需配合较多图片、预估篇幅较长）**：在 md cell 中用文字记录必要信息（操作目标、关键步骤、安全要点），并加【附件提示】指向另行发放的图文附件，例如：
       > 【附件提示：手柄按键布局与逐步操作图示较多，详见附件《K1 手柄遥控操作图示》，请结合图文完成学习。】
       此类附件由人工单独制作，notebook 中只做文字概括 + 附件提示，不堆截图。
   - 知识/概念类阶段：除名词解释外，应补充**表格或流程图**形式的归纳——例如发展脉络表（时期 / 代表进展 / 对本课学习者的意义）、系统组成表、字段说明表等；必要时可加"对学习者的意义 / 为什么值得记录"的通俗说明（这是知识讲解，不是课程设计理由）。
   - 实操/软件类阶段：若涉及 K1 实物图、BoosterStudio 界面、逐步点击操作等**不便放入 jupyter 的内容**，用**文字概括软件功能与操作目标**，并提示阅读**另行发放的附件**（如「见附件《K1 连接与 BoosterStudio 操作图示》」）。此类附件由人工单独制作，notebook 中只做文字概括 + 附件提示，不堆截图。
3. **禁写"课程设计理由"类话术（学生手册）**：凡解释"我们为什么这样设计本课/本节"的话术，不进学生版实训手册。典型须删除样例：
   - "本课先用'只读'方式认识它的身份与身体清单，正是从'计算入口 + 运动清单'两端切入。"
   - "为什么本课只读不写"（及其展开的安全/认知/衔接三点理由）。
   这类内容若有保留价值，放到对应的**教学设计（教师用 .md）**对应环节，不在学生手册出现。
4. **「后面单元逐一展开」类前向引用仅限第一课**：U1-L1（全课程第一课）可写"后面单元会逐一展开"；**其余各课（L2/L3/L4…）的实训手册不得出现**"后面单元 / 后续单元将…"等字样——当课不在文档中呈现这类信息。其他前向引用仍遵守 §3.2。
5. **markdown 换行纪律（防格式错乱）**：每个 markdown cell 的 `source` 必须是"每行一条、行尾带 `\n`"的列表（Jupyter 标准存储）。**严禁把整段内容塞进单个字符串导致换行消失、文字连载**。批量生成/重建 notebook 时须用辅助函数逐行拆分，并校验「无 markdown cell 的 source 是单条无换行字符串」。
6. **P2 按审定结果处理**：见 §1「P2 审定约定」。有问题先交用户确认修改方案；无问题或修订后复核通过，直接提示「可以进入 P3」，不再重复确认整份材料，也不自动编写 P3。
7. **课头 / 实验头分层（首 cell 与实验环节）**：
   - **首 cell（课头）** = **课程级**：第一行 ` # U1-L1：课程名称 `（冒号分隔，不用"实验："），其后紧跟 ` **课程目标** `（覆盖整课：认知 + 实操 + 范式等）。**课程级不写「安全提示 / 前置准备 / 实验目标」**。
   - **实验环节头**（在本课实际动手操作的那个二级阶段开头）= **实验级**：在该阶段标题下依次给出 ` **实验名称** `、` **实验目标** `、` 📌 前置准备 `。**安全提示分级**：本课「第一次 code 实验」须给完整 ` ⚠️ 安全提示 `（含运动 / 停止路径，见 §3.6）；**之后的独立实验开头不再重复完整安全提示，只用红字关键说明**（见 §3.5 分级呈现）。
   - **判定原则**：`安全提示 / 前置准备 / 实验名称 / 实验目标` 是**针对实验实操**的，就放在实验环节开头；若某课它们针对整课（极少见），才放课头。L1 中四者均针对实验，已下沉到「二、连接 K1」环节。
8. **扩展阅读模块（可选，置于「学习评价」之后）**：
   - 在「三、检查点、思考题与学习评价」之后，可增设二级标题 ` ## 四、扩展阅读：… `（命名随内容），用于放置**行业 / 职业认知、前沿拓展**等有价值的延伸内容。
   - **判定**：仅当某课有合适且有价值的内容时才设计此模块；内容为**面向学生的阅读资料**，不写课程设计理由。
   - **来源约定**：原先写在「课程大纲映射」审核块里的「行业/职业认知锚点（可选了解模块）」，应**迁移为正式的扩展阅读模块**进入学生版，审核块内对应条目删除，避免重复（U1-L1 已示范：行业/职业认知锚点 → 四、扩展阅读）。
9. **术语校准（Booster 体系，务必准确）**：
   - **Booster Robot** = 公司名称（机器人厂商）。
   - **K1** = Booster Robot 公司的一款人形机器人（本课程的实体对象）。
   - **BoosterOS** = SDK 名称（Python 包 `boosteros`，安装 `pip install boosteros`）；`BoosterRobot` 是其中的连接入口类。
   - **BoosterStudio** = 类似 VSCode 的机器人开发工具（用于连接 K1、查看状态、切换模式、发送指令等），不是单纯的"调试软件"。
   - 学生文件中提及"厂家 / 厂商"时，落地为 **Booster Robot 公司**；提及开发工具落地为 **BoosterStudio**，提及 SDK 落地为 **BoosterOS**。

10. **教学设计文档（教师用 .md，P3 派生）体例规范**：
   - **禁写项目说明性话术**：`（对应源文件 / 对应大纲 / 对齐 notebook 首 cell「课程目标」 / 派生文档 / P2 重构稿）` 等是**生成与审查用的项目规则**，不显示在教学设计文档上。文档只呈现教师可直接使用的内容。
   - **标准章节顺序（须与 U1-L1 对齐，不可调换）**：教学设计固定为以下六段；从第七段起每节课可不同。
     1. `## 一、课时目标`：纯编号列表（1. 2. 3.），**不写"认知 / 实操 / 素养"等方向标签**（难以保证每课都有三方向）；可加 `> 教学提示：` 块引用补充教学思路。
     2. `## 二、重难点`：表格，列 = `类型 | 内容 | 教学建议`（列名用「教学建议」）。
     3. `## 三、环节时间轴`：表格，列 = `时间 | 环节 | 形式 | 内容`；内容列引用实训手册 §x.x。
     4. `## 四、教学环节详解`：`### 环节 N·名称（X-Xmin）` 子标题，配 `- **话术**：` / `- **演示**：` / `- **投影（见实训手册 §x.x）**：` 等要点。
     5. `## 五、板书设计`：`**板书N · 标题**` + 表格 / Mermaid。
     6. `## 六、学习评价`：`> 题目与实训手册「…」一致` 说明 + 题目，**答案内联到每题之后**（如 `**答案：√**`），与 U1-L1 一致。
     7. `## 七、…`（可不一致）：如 常见问题 FAQ / 教学资源与附件；`## 八、安全与设备准备` 等后续段每课按需。
   - **「四、教学环节详解」的话术与语言规范**（L2 已据此修订，L3/L4 直接套用）：
     - **结构**：每个环节按 `**操作**`（教师具体做什么）→ `**话术**`（教师对学生讲的话，**用中文全角引号 `""` 标出**）→ `**注意**`（给教师的提醒，**写在引号外**）组织；教师读后应清晰知道操作流程，不过简也不冗长。
     - **话术不带括号标签**：禁用 `话术（红线）` `话术（状态机）` 之类写法；若某内容属于**安全红线或设计意图**，应放进 `**操作**` 或 `**注意**`（引号外）向教师传达，不要混进话术引号内。
     - **去 AI 化、贴高职学生**：避免拟人/空泛表达（如"让它听话""埋下伏笔"），改用工程化直述（如"按指令切换工作状态"）；话术要直接、口语、可照着念。
     - **中文引号统一全角 `""` / `''`**：文档内所有中文语境引号用全角，禁用半角 `"` `'`（半角仅用于代码 / 英文）。
   - **教师补充文字可写，但不用"教师补充目标"式标签**：可以写面向教师、帮助理解教学思路的补充文字（如"教学提示：研究重心建议双口味…"），但不要写成 `（教师补充目标：…不进 notebook）` 这类项目管理式表述。
   - **重难点表规范**：
     - 列名用 **「教学建议」**（不用"处理建议"）。
     - **重点** = 本课真正的关键目标；**难点** = 学生真实存在的**操作难点或认知难点**；整体来源是「课时目标」的进一步拆分。
     - 高职/中职年龄段学习者已具备基本具身经验，**不要把"关节命名规律与身体结构对应"之类内容列为认知难点**（它不构成认知门槛，可作普通知识点）。
   - **术语校准类内容是给协作 AI 看的，不进文档**：如 `{术语校准：Booster Robot=公司…}` 这类这是写给生成工具看的备注，**不要作为知识呈现给教师或学生**；只需确保文档全程名词使用准确（见 §8.9）即可。
   - **连接概念务必准确（K1）**：K1 是**实体机器人（有芯片、有操作系统）**；我们写程序的电脑**通过网络与 K1 远程连接**，从而可以在电脑端给 K1 编写并下发程序；SDK（BoosterOS）是**操作 K1 的程序接口集合**；电脑与 K1 的通信走网络连接（实际为 **SSH**）。两种连接方式：
     - **无线**：先用 **Booster APP** 给 K1 配网 → 获取 K1 的 **IP 或设备序列号** → 在 **BoosterStudio** 用 IP 或序列号连接、查看运行模式/关节/姿态等状态；编程传文件走 **SSH + IP**。
     - **有线**：用**网线直连**电脑与机器人 → **修改电脑网络配置** → 即可在 BoosterStudio 连接。
   - **板书 / 图示用 Mermaid 或表格**：板书 / PPT 要点优先以**可直接渲染的结构化形式**给出，而非纯文字罗列。推荐：
     - **Mermaid 代码**（```mermaid 围栏）：适合树状 / 流程图（如"四大子系统""电脑—K1 连接""SDK 读写范式"），可粘贴到支持 Mermaid 的编辑器 / 白板自动渲染为框图。
     - **表格**：适合对照类内容（如"离身 vs 具身"的维度对比），比 ASCII 框图更易维持排版。
     - 不强制 ASCII 美术字框图（手绘易出"箭头数≠节点数"之类错位），除非使用真正的图形工具。
   - **学习评价用「先题目后答案」格式**：教学设计文档中呈现学习评价时，先给出完整题目（判断 / 填空 / 选择，与实训手册一致），再在题后附「答案：…」，便于教师直接对照批改；不要只列答案。

11. **PPT 内容大纲（P4 派生）体例规范**：
   - **课件标题体系（三层标识）**：每页采用「章节标签（页眉小字/色块）+ 页面主标题（大字）+ 副标题（主标题下，以「——」引出本页聚焦点）」。**章节标签对应课程大块**（如 `第一部分 · 初识具身智能`），**主标题+副标题呈现本页独立内容**。标题要像"学习类课件"而非内部设计文档。
   - **删除课程设计隐线话术**：不要把内部思考逻辑写进课件标题或正文，如 `双口味` `双口位` `能落地` `与后续课程直接相关` `平衡小结` `研究重心双口味` 等；学生只见学习内容与问题。需要表达"前沿 vs 应用"时，用学生能懂的标题（如 `前沿一 · 视觉语言导航 VLN` / `应用一 · 机器人操作`）。
   - **密集知识点拆多页图文并茂**：发展脉络、研究重心等"一页会拥挤"的内容，**拆成多页、每页聚焦一个时间点和事件/研究内容，左文右图或上图下文**；不要堆在一页。
   - **板块式设计**：同类多条内容（如应用三方向：机器人操作/运动控制/手眼协调）用**统一版式卡片 + 配图**逐页呈现，形成"三板块"视觉节奏。
   - **过渡页用问题/话题/情景衔接**：不同大块之间用**问题式过渡页**抛出"话题/问题/情景"（如"回到我们手边的这台 K1——它到底由什么组成？""看完了身体，怎么用一行代码让它听话？"），避免"突然跳到 SDK"之类断裂。
   - **实物介绍页插在合适位置**：在"系统组成"与"SDK/开发工具"之间，应插入 **1–2 页 K1 机器人实拍/示意图介绍**（外观、硬件参数、能做什么），再自然过渡到"怎么用程序控制它"。
   - **连接概念准确（同 §8.10）**：PPT 中 K1 是实体机器人、通信走 SSH、两种连接方式，不得写成"网络设备 / IP:端口直连"。

## 8.12 课堂学习课件排版设计规范（P5 视觉模板，适用所有 PPTX 生成）

**定位**：课堂学习课件（区别于讲座 / 答辩），以学生"学"为中心——一页一个知识点、字号保证后排可见、留白给思考、图文占比高、带互动锚点、首尾有目标/小结。已确认基调：**清新白底 · 微软雅黑 · 页脚仅页码 · 代码页浅色底深字**。

1. **画布与栅格**
   - 尺寸 16:9（13.333″ × 7.5″）；安全边距左右 0.6″、上下 0.5″。
   - 常用版式参考：左文右图（左 55% / 右 45%）、上图下文（上 50% / 下 50%）、板块卡片（1–3 卡横排）、代码页（上说明 + 下代码块）。U2 起按内容关系选择结构，上述比例不作为固定要求；保留 U1 的标题、配色、字体和页码规则。

2. **配色系统（按教学体例编码，清新白底基调）**
   - 背景：主背景 `#FFFFFF`；分区/卡片浅灰底 `#F4F6F9`。
   - **科技蓝 `#2563EB`：常规知识内容**，用于概念、原理、发展脉络、研究方向、工具说明及知识页的章节标签/标题强调。
   - **青绿 `#0EA5A4`：实践操作内容**，用于 BoosterStudio 演示、连接任务、代码运行、实验步骤和实践结果；配套浅底为 `#CCFBF1`。
   - **橘黄 `#F59E0B`：思考与评价内容**，用于「想一想」、思考题、学习评价、课堂总结和下一步提示；配套浅底为 `#FFF7E6`。
   - **警示红 `#E5484D`：安全警示内容**，仅用于安全提示、风险提醒和停止操作，不承担章节或模块配色。
   - 颜色由教学体例决定，**不按并列应用方向或模块随机更换整页主题色**。同类连续页保持同色，通过编号、图标、关键词和版式变化区分内容。
   - **页面级应用**：常规知识页保持科技蓝页眉；独立实践/代码页切换青绿页眉与关键控件；独立思考/评价/总结页可切换橘黄页眉。知识页中嵌入的小型活动只给活动框着色，不改变整页主色。
   - 文字：正文 `#1F2933`；注释/副标 `#5A6573`；更浅 `#8A94A6`。
   - 代码：代码块底 `#F4F6F9`、边框 `#DDE3EA`、字 `#1F2933`、等宽；高亮行底 `#FFF8E1` + 左侧 3px 琥珀色条。

3. **字体阶梯（微软雅黑 Microsoft YaHei；python-pptx 仅设置字体名，渲染在用户 PowerPoint 完成）**
   - 章节标签 12pt 加粗 主色｜主标题 32pt 加粗｜副标题（——后）18pt 常规 注释色｜正文 18pt（投影可读下限）｜注释/来源 13pt｜代码 15pt 等宽（Consolas / 思源等宽 / Courier New 备选）｜页码 10pt 灰。

4. **页眉（章节标签）+ 页脚（仅页码）**
   - 页眉：每页顶部章节标签小字，如 `第三部分 · 认识 K1 与开发工具`（主色）；封面/过渡页可弱化。
   - 页脚：仅页码（如 `12 / 30`），居中或右下，10pt 灰。**不显示课程名/课时/学段**（用户选择）。

5. **各页型模板（坐标级骨架，供 P5 python-pptx 实现）**
   - 封面：居中大标题（课程名）+ 副标题（课时主题）+ 底部「单元 U1 · 课时 L1 · 主讲」占位。
   - 目标页：主标题「本课目标」+ 3 条要点卡片（编号圆点）。
   - 互动页：大字提问/任务 + 互动提示框（【想一想】）。
   - 知识页（左文右图）：左 55% 文字（主标题+副标+要点），右 45% 图片/图示占位框（框内标注「配图：…」）。
   - 板块卡片页：1–3 卡片横排，每卡【图标位】+ 方向名 + 一句解释 + 图。
   - 过渡页：超大问句居中 + 虚化背景图，弱化页眉。
   - 代码页：上方 1 行说明（对应 notebook 步骤 / cell）+ 下方代码块（高亮关键行）+ 可选右侧输出示例小图。
   - 演示页：步骤编号 + Studio 界面占位标注。
   - 小结评价页：左小结三条 / 右评价题目卡。

6. **图文比例与图片占位**
   - 知识/图文页图片占幅 ≥ 40%（宽或高）为原图文模板参考；U2 起以图示是否清晰、信息是否完整及投影是否可读判断，不为满足占比加入无关图片。
   - 审查稿缺素材时，可用带标注的占位框（浅灰底 + 虚线边 + 说明文字），注明缺什么素材及来源状态。U2 起申请确认⑥前必须替换并核验关键实拍、截图和图示，素材待补稿不得作为可授课成品。图片素材与实训手册附件《K1 连接与 BoosterStudio 操作图示》协同准备；U1 已验收成品不要求回改。

7. **代码页样式（浅色底深字）**
   - 浅灰底 `#F4F6F9` + 细边框 `#DDE3EA`，等宽 15pt 深字 `#1F2933`。
   - 关键行高亮：实践代码页使用浅青绿底 `#CCFBF1` + 左侧 3px 青绿色条；若代码仅作为知识示例而不执行，可使用科技蓝弱强调，不使用橘黄伪装成评价页。
   - 顶部注明 `对应 notebook 步骤 N（cell-X）`，确保与实训手册一致、学生可对照抄写。不使用深色满版背景（与整体清新白底统一）。

8. **互动 / 提示框统一样式（文字标签优先于 emoji，避免渲染依赖）**
   - 【想一想】琥珀底卡 + 左色条，启发提问。
   - 【动手试试】青绿底卡，实操任务。
   - 【⚠ 安全提示】红字/红条卡，仅实验相关页（L1 极简因只读；L2+ 重要）。

9. **可读性纪律（投影优先）**
   - 单页正文不超过 6 行要点；一行不超过 28 中文字。
   - 对比度文字/背景 ≥ 4.5:1。禁满屏文字、禁小字号堆砌；图文并茂页优先。

10. **与 §8.11 的关系**：§8.11 = 内容组织规范（标题体系/拆页/过渡/板块）；§8.12 = 视觉排版规范（配色/字体/栅格/页型模板）。P5 生成 PPTX 时二者同时遵守。

   - U2 起的版式选择、图示和素材来源、P5 成品验收按 [`03_X课程项目/PPT制作与图示验收规范.md`](../03_X课程项目/PPT制作与图示验收规范.md) 执行；含经官方资料核对的 PPT Master 方法借鉴、固定视觉规则与灵活构图、关键图示规格和检查记录。该补充规范保留 U1 已验收成品，不增加确认闸门，也不要求改用其他生成工具。

## 8.13 教学环节详解小体例（P3 内部模块标准）

**定位**：「四、教学环节详解」是教师照着上课的操作脚本。每个 `### 环节 N·名称（X-Xmin）` 由下列**标准模块**按需组合，全课程统一使用，不得自造标签（L1/L2 已据此回改一致）。

**标准模块清单（11 个）**

| 标签 | 含义 | 写给谁 | 引号规则 |
|---|---|---|---|
| 【演示】 | 教师演示（实物 / 软件 / 代码 / 现象） | 教师操作指引 | 无 |
| 【步骤】 | 学生按序执行的操作（含 notebook、配网） | 教师引导学生 | 无 |
| 【活动】 | 学生非代码参与（观察记录 / 讨论 / 填写 / 手柄实操） | 教师组织 | 无 |
| 【投影】 | 投屏素材（PPT 页 / 图片 / 手册表格），标注来源 | 教师 | 无 |
| 【板书】 | 黑/白板逐步写出的结构，呼应 `## 五、板书设计` | 教师 | 无 |
| 【核心概念】 | 本环节关键定义 / 原理 / 补充讲授要点 | 教师讲解要点 | 无 |
| 【话术】 | 教师对学生讲的话 | 教师→学生 | 中文全角引号 `""` 内 |
| 【提问】 | 抛给学生的问题（从话术中拆出） | 教师→学生 | 中文全角引号 `""` 内 |
| 【FAQ】 | 学生易问问题 + 标准答法 | 教师 | 答可用引号 |
| 【注意】 | 一般教学提醒 | 教师 | 无（引号外） |
| 【安全红线】 | 安全强约束（醒目特例） | 教师 | 无（引号外） |

**归并映射（历史 ad-hoc 标签 → 标准）**
- `板书/投影`（L1 合写）→ 拆为 **【板书】+【投影】**
- `研究重心（双口味，补充讲授）` / `两种连接方式` → 归入 **【核心概念】**
- `强调` → **【注意】**
- `操作`（L2 笼统）→ 按性质拆为 **【演示】/【步骤】/【活动】**
- `注意（安全红线）` → 拆为 **【注意】+【安全红线】**
- 话术内夹带的问题 → 拆出 **【提问】**
- 环节内散文（无标签）→ 规范为 **【步骤】+【注意】** 等

**每个环节建议排列顺序**
> 〔环节目标·可选〕→ 操作层【演示 / 步骤 / 活动】→ 内容层【投影 / 板书 / 核心概念 / FAQ】→ 语言层【提问 / 话术】→ 提醒层【注意 / 安全红线】

**呼应关系**
- 【板书】写出的结构须与 `## 五、板书设计` 一致；【投影】标注的素材来源（PPT 页 / 手册 §x.x）须真实存在。
- 【话术】【提问】引号内为教师对学生原话；【注意】【安全红线】为给教师的提醒，写在引号外（沿用 §8.10 话术规范：去 AI 化、全角引号、不带括号标签）。

## 8.14 P1 阶段知识与实践的组织方式（2026-09-03 用户澄清）

**课程侧重（2026-10-20 用户澄清）**：概述课可以包含代码练习，实训课也可以引入知识。按每课目标决定知识与操作怎样组织。U6-L1 面向只学过人形机器人基础课与 U1–U5 的高职学生，不能预设其修过深度学习或强化学习；首次出现的术语应结合具体输入、操作与结果解释。
