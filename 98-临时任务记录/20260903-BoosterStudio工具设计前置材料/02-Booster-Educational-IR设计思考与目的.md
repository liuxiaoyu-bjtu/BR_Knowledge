# Booster Educational IR：设计思考与目的

> 本文解释 BoosterStudio 前置方案中提出的 **Booster Educational IR**。它是本次产品设计提出的工作性概念，不是 Booster 当前已经发布的正式模块、协议或产品名称。本文的目的不是直接冻结技术实现，而是把产品、教研和技术团队需要共同理解的问题先说清楚。

## 一、先给出结论

Booster Educational IR 可以理解为：

> **面向 K1 具身智能教育项目的统一语义模型和执行契约。**

它位于图形化积木、Python/ROS2 代码、教育运行时、虚拟 K1、真实 K1、日志评价之间，负责描述一个学生程序“要做什么、需要什么、怎样运行、怎样失败、怎样被安全地执行和观察”。

建议的整体关系如下：

```text
Blockly 积木 / Python / 状态图
              ↓
      Booster Educational IR
              ↓
     类型检查 · 程序验证 · 安全检查
              ↓
       Booster 教育运行时
          ↓            ↓
 Virtual K1 Adapter  BoosterOS Adapter
          ↓            ↓
       虚拟仿真       真机 K1
              ↓
      运行高亮 · 日志 · 评价数据
```

这里的关键不在于增加一个技术名词，而在于改变连接方式：**积木和代码描述同一份程序语义，仿真和真机执行同一份教育项目语义，教师评价和运行过程引用同一份可追踪结构。**

## 二、为什么需要它

### 1. “积木直接生成 Python”很快会碰到边界

最初的图形化工具常见做法是：每个积木对应一段 Python 字符串，连接积木时把字符串拼接起来，点击运行后执行生成的代码。这种方式适合简单、同步的控制，例如：

```text
向前走 1 秒 → 停止 → 说一句话
```

但 K1 的实际程序很快会包含以下情况：

- 动作是一个持续过程，可能需要等待完成、被取消或超时；
- 相机、IMU 和麦克风是持续产生数据的传感器流；
- 视觉识别结果带有置信度、时间戳和目标位置；
- 程序要同时处理感知、动作、语音和用户事件；
- 机器人可能摔倒、电量不足、网络断开或进入保护状态；
- 仿真和真机的速度、延迟、可用能力和失败方式并不完全相同；
- 教师需要知道学生的哪一个积木触发了哪次动作和哪条错误。

如果只有字符串拼接，编辑器、代码生成器、仿真器、真机 SDK 和评价系统会各自解释程序。随着课程升到 L3、L4，这些解释很容易不一致，导致同一程序在仿真、代码视图和真机上的行为难以对齐。

### 2. Blockly 只解决“编辑”，不解决“运行”

Blockly 的职责主要是：

- 积木的渲染、拖拽和连接；
- 输入框、下拉框和类型连接；
- 积木工作区的序列化；
- 自定义积木扩展；
- 面向某种目标语言的代码生成接口。

它并不天然提供 K1 所需的教育运行时、动作生命周期、仿真、设备连接、安全策略、课程任务和过程评价。因此，BoosterStudio 真正要建设的核心资产不能只停留在积木外观，而应包含一套稳定的 K1 教育语义。

### 3. K1 是“具身”系统，程序需要表达身体和环境的关系

普通编程工具主要描述数据和计算；机器人教育工具还需要描述：

```text
机器人看到了什么
→ 机器人如何判断
→ 机器人如何行动
→ 行动后环境发生了什么
→ 机器人如何继续感知和调整
```

这意味着程序中不仅有“调用函数”，还有事件、持续状态、动作完成、目标丢失、异常恢复和安全停止。Educational IR 的价值，就是把这些具身智能学习中真正重要的关系明确地记录下来。

## 三、它究竟是什么

### 1. 是统一语义模型

Blockly 记录的是“有哪些积木、积木怎样嵌套和连接”；IR 记录的是这些积木组成的程序具有什么含义。

例如，下面的积木表面上只是三个步骤：

```text
当程序开始
→ 挥手
→ 等待 1 秒
→ 说“欢迎”
```

IR 应该进一步表达为：

```text
收到 program_started 事件
→ 调用 K1 的预定义挥手能力
→ 等待该动作完成或达到超时时间
→ 等待 1 秒
→ 执行语音输出
```

这样，仿真器知道要模拟一个“动作过程”，真机适配器知道要调用什么能力，运行高亮知道当前正在执行哪个节点，评价系统也能判断学生是否完成了“事件触发、动作衔接和语音反馈”。

### 2. 是执行契约

一个积木或程序节点不能只定义“调用哪个接口”，还应该约定：

- 输入是什么类型，单位是什么；
- 输出是什么类型，是否可能为空；
- 是立即返回还是需要等待；
- 是否可以被取消；
- 失败、超时和设备异常如何处理；
- 仿真是否支持，仿真与真机有什么差异；
- 是否产生运动或其他副作用；
- 需要什么安全权限；
- 如何映射到 BoosterOS SDK、仿真引擎或 ROS2；
- 如何与积木、代码、日志和课程目标建立来源关系。

因此，IR 更像一份“可执行的项目协议”，而不是一个把积木内容换一种格式保存的 JSON 文件。

### 3. 不是新的学生编程语言

学生不一定需要直接看到 IR。对学生来说，它可以表现为：

- L1 的动作和语音积木；
- L2 的感知、条件和任务流程积木；
- L3 的状态图、数据流和 Python 代码视图；
- L4 的 Python/ROS2 工程、状态监控和日志面板。

不同界面可以面向不同年龄和能力层级，但底层都落到同一套可验证的语义上。IR 的存在是为了让产品内部保持一致，而不是要求学生再学习一门隐藏的语言。

## 四、IR 要统一哪些信息

建议将 IR 的内容理解为八类信息。正式设计时可以拆成不同的数据结构，但不应只关注动作调用本身。

### 1. 程序结构

描述程序由哪些事件、顺序、分支、循环、并行任务、状态节点和自定义模块组成。

```text
事件 → 顺序 → 条件分支 → 循环 → 行为模块
```

### 2. 操作语义

描述“执行动作”到底意味着什么。例如“挥手”是一个预定义动作能力，可能需要：

- 启动动作；
- 等待动作完成；
- 检查动作是否成功；
- 在超时或异常时停止并返回原因。

### 3. 数据、类型和单位

描述数字、文字、布尔值、图像、目标、目标列表、位姿、距离、速度、角度和时间等数据。

尤其要避免把有单位的量都当作普通数字。例如：

```text
距离：1.2 m
速度：0.3 m/s
转角：30 deg
等待：1 s
```

如果后续把角度误接到时间输入，编辑器就应该在设计阶段给出提示，而不是等到真机运行才暴露问题。

### 4. 事件、流和异步行为

IR 需要区分几种不同的程序关系：

| 类型 | 例子 | 需要表达的重点 |
|---|---|---|
| 一次性调用 | 播放一个声音 | 调用、返回和失败 |
| 持续动作 | 行走、转身、追踪 | 开始、持续、完成、取消和超时 |
| 事件 | 识别到人、检测到二维码 | 触发条件、事件数据和触发时机 |
| 数据流 | 相机帧、IMU 数据 | 采样、时间戳、频率和订阅关系 |
| 状态 | 行走中、摔倒、保护状态 | 当前值、变化事件和优先级 |

这是 IR 与普通“命令列表”最重要的差异之一。

### 5. 设备能力与适配关系

IR 应引用稳定的教育能力名称，例如：

```text
motion.play_preset
speech.say
vision.detect_person
vision.read_qrcode
robot.get_fall_state
```

再由不同适配器将这些能力映射到：

- Virtual K1 Simulator；
- BoosterOS SDK；
- Booster Agent Framework；
- ROS2 节点、Topic、Service 或 Action；
- 某个具体硬件版本的实现。

这样，课程积木不需要直接绑定某个底层函数名，硬件升级时也不会迫使教研内容全部重写。

### 6. 安全和权限

安全信息应是 IR 的一等属性，而不是运行按钮旁边的一句提醒。可包括：

- 节点安全等级；
- 是否产生运动；
- 允许的最大速度、角度或持续时间；
- 可运行模式：仿真、真机、仅教师批准；
- 动作白名单；
- 网络断开、摔倒、电量低时的保护动作；
- 任务取消和全局停止策略。

同一个“向前走”节点，在仿真中可以直接运行，在真机中则可能需要速度上限、地面检查、教师许可和自动超时。把这些要求纳入 IR，才能在运行前和运行时统一执行。

### 7. 可观察性和来源映射

IR 应保留积木、代码、状态图和运行日志之间的映射：

```text
积木 id
  ↔ IR 节点 id
  ↔ Python/ROS2 代码行或模块
  ↔ 运行时事件
  ↔ 教师评价指标
```

当机器人没有按预期挥手时，系统应该尽可能回答：

- 是哪个积木或代码节点触发的；
- 实际调用了哪个能力；
- 输入参数是什么；
- 仿真或真机返回了什么；
- 是否发生了超时、取消或安全拦截。

这会直接影响学生调试体验和教师复盘效率。

### 8. 教学和评价元数据

同一个程序节点，在工程上是一次调用，在课程上可能对应一个具体学习目标。因此可以附加以下元数据：

- 适用等级和先备知识；
- 对应课程任务；
- 教学目标；
- 允许使用的能力范围；
- 任务完成条件；
- 可观察的过程指标；
- 典型错误和提示策略。

需要明确一点：**教学元数据不应改变底层执行语义。** 它用于课程配置、引导和评价，可以与执行核心分层保存，避免把教学规则硬编码进机器人运行时。

## 五、一个示意性的 IR 结构

下面的结构仅用于帮助产品、教研和技术团队对齐思路，不是最终 Schema，也不代表 BoosterOS 当前接口名称：

```yaml
program:
  id: k1-l1-welcome
  target:
    robot_model: K1
    run_mode: simulation
  source:
    editor: blockly
    grade_level: L1

  triggers:
    - id: start_1
      event: program_started

  nodes:
    - id: action_1
      kind: capability_call
      capability: motion.play_preset
      inputs:
        preset: wave
      execution:
        wait: completion
        timeout: 10s
        on_failure: stop
      safety:
        motion: true
        level: supervised

    - id: wait_1
      kind: wait
      duration: 1s

    - id: speech_1
      kind: capability_call
      capability: speech.say
      inputs:
        text: "欢迎"
      execution:
        wait: completion

  edges:
    - from: start_1
      to: action_1
    - from: action_1
      to: wait_1
    - from: wait_1
      to: speech_1

  source_map:
    action_1: block://workspace/block-17
    wait_1: block://workspace/block-18
    speech_1: block://workspace/block-19
```

这个例子体现了几件事：

1. 目标设备和运行模式是程序的一部分；
2. 动作节点不仅有能力名称，还有等待完成、超时和失败策略；
3. 运动动作携带安全属性；
4. 程序结构由节点和边表达，而不是只靠最终字符串；
5. 每个运行节点可以回溯到具体积木。

## 六、三个课程层级的例子

### L1：从“动作串联”变成可解释的行为

学生看到：

```text
当程序开始
→ 挥手
→ 等待 1 秒
→ 说“欢迎来到我们的表演”
```

IR 需要隐藏底层实现，但保留以下语义：

- `program_started` 事件；
- 一个可等待完成的预定义动作；
- 一个有单位的时间等待；
- 一个语音输出能力；
- 顺序关系；
- 动作完成后的继续条件；
- 真机运行前的安全检查。

因此 L1 的 IR 让学生拥有简单的体验，同时让系统从一开始就按机器人真实的动作生命周期运行。

### L2：把“如果看到”变成感知到决策的闭环

学生看到：

```text
当看见一个人
如果置信度大于 0.7
    说“欢迎来到校园”
    挥手
```

IR 需要表达：

- `person_detected` 事件；
- 目标类型为 `person`；
- 置信度是数值，并且范围和比较关系合法；
- 条件分支的真假路径；
- 语音和动作的顺序或并行关系；
- 检测结果的时间戳和有效期；
- 没有识别到目标时程序如何继续。

这为 L2 的“感知、判断、反馈”建立了统一结构，也使后续可以把同一程序替换成仿真视觉或真机视觉，而不改变课程逻辑。

### L3：从长积木程序转向状态和数据流

二维码迷宫这类任务不再适合只用一条很长的积木链表达。学生更适合看到：

```text
SEARCH
  └─识别到二维码→ APPROACH
                      └─距离满足→ TURN
                                      └─动作完成→ SEARCH
```

在 IR 中，这是一组状态、转移条件、感知输入和动作节点：

- `SEARCH` 订阅或读取二维码检测结果；
- 识别到有效目标后转移到 `APPROACH`；
- 距离达到条件后转移到 `TURN`；
- 转身完成后回到 `SEARCH`；
- 目标丢失、超时或摔倒时进入异常处理分支。

此时 IR 可以同时支持状态图视图、积木视图、Python 视图和运行时状态高亮，避免学生从图形化编程突然跳到一份缺少上下文的代码。

### L4：让图形化成为系统理解和调试工具

追球和踢球任务需要表达：

```text
视觉检测
→ 坐标变换
→ 目标筛选
→ 状态机
→ 运动策略
→ 目标丢失处理
→ 动作执行
→ 日志复盘
```

L4 的 IR 不应试图把所有 Python、ROS2 和算法库重新压缩成积木，而应让系统结构可以被看见：

- 哪个 ROS2 节点发布了检测结果；
- 哪个模块完成坐标变换；
- 哪个状态负责运动控制；
- 目标丢失后使用了什么策略；
- 实际速度、延迟和动作完成时间是多少；
- 仿真和真机结果有哪些差异。

这时 Educational IR 的重点从“降低编程门槛”转向“提高系统可理解性和可调试性”。

## 七、它与各层技术的关系

### 1. 与 Blockly 的关系

```text
Blockly = 编辑器表达层
IR      = 程序语义层
```

Blockly 负责让学生搭建程序，IR 负责把搭建结果标准化、验证并交给运行时。未来即使前端从 Blockly 换成状态图或其他编辑器，只要生成的语义保持一致，运行时和课程项目仍可复用。

### 2. 与 Python 的关系

Python 可以是 IR 的一种可读、可编辑视图或一种工程扩展方式，但不应被当作唯一事实来源。

建议分三步：

1. L1-L2：积木生成 Python 只读视图，帮助学生建立对应关系；
2. L3：图形化主流程与可编辑 Python 函数协作；
3. L4：Python/ROS2 作为主要工程入口，IR 保留状态、能力、接口、来源和调试信息。

不建议承诺所有 Python 都能完全反向还原为积木。Python 可以包含任意表达式、第三方库、线程和底层调用，这些内容不可能全部保持图形化可逆。

### 3. 与 BoosterOS SDK 的关系

IR 不应复制 SDK 的每个底层函数，而应建立“教育能力”到“技术接口”的映射。

例如，教研定义的“执行挥手动作”是学生可理解的能力，适配器再决定：

- 仿真器如何播放对应动作；
- BoosterOS SDK 使用哪个动作接口；
- 真机返回哪些状态；
- 何时判定动作完成；
- 超时和取消如何处理。

这样可以降低教研语义与底层 SDK 版本的耦合，也方便未来把一项能力从预定义动作扩展到更复杂的控制器。

### 4. 与 ROS2 的关系

ROS2 是系统通信和工程集成基础，不是面向 L1-L2 学生的全部教学抽象。IR 可以在 L3-L4 将教育能力逐步展开为：

```text
行为能力
→ 模块
→ Topic / Service / Action
→ 节点和参数
```

这种展开关系让学生先理解“机器人要完成什么”，再逐步理解“系统通过什么通信机制完成它”。

## 八、它在产品中的真正目的

### 目的一：保证仿真与真机是同一条学习路径

学生应能在没有真机或不适合真机的情况下完成大部分程序设计、运行和调试，然后把同一项目切换到真机实践。

这并不意味着仿真和真机物理结果完全相同，而是要求二者在教育语义层面可对照：

- 相同的事件名称和能力名称；
- 相同的输入输出类型；
- 相同的完成、失败、超时和取消概念；
- 差异以明确的适配信息和日志呈现。

### 目的二：把安全前置到程序执行之前

安全检查不能只依赖教师经验或运行时人工观察。IR 让系统有机会在运行前知道：

- 程序是否包含运动动作；
- 动作是否超出本课程允许范围；
- 是否配置了超时和失败处理；
- 当前目标模式是否允许执行；
- 是否需要教师审批。

运行时仍然需要急停、保护和硬件级安全，但 IR 可以减少明显的程序级风险。

### 目的三：支持学生从“做出效果”走向“理解系统”

如果产品只关心机器人是否动起来，学生可能会停留在复制积木。IR 通过类型、数据流、状态、事件和日志，逐步把问题变成：

```text
我给了什么输入？
机器人观察到了什么？
程序为什么做出这个判断？
动作何时开始、何时结束？
失败后系统如何恢复？
```

这正是从编程启蒙走向具身智能系统思维的过渡。

### 目的四：让教师能够布置、观察和评价过程

教师不应只能看最终展示效果。通过节点、事件和日志的统一标识，可以进一步支持：

- 查看学生是否完成必要的程序结构；
- 查看事件是否真正触发；
- 查看学生是否处理目标丢失和超时；
- 查看仿真到真机的差异；
- 根据过程记录进行评价和讲评。

### 目的五：降低长期技术耦合

BoosterStudio 未来可能面对不同 K1 固件、仿真版本、SDK 版本和课程版本。若积木直接绑定底层实现，设备变化会不断反向影响前端和课程。IR 提供稳定的中间边界，使以下部分可以相对独立演进：

```text
教学语义 / 积木设计
        ↕
教育 IR
        ↕
仿真适配器 / SDK 适配器 / ROS2 适配器
```

## 九、设计时需要坚持的原则

### 原则一：语义优先，而不是积木优先

先定义学生要理解的行为、感知、状态和数据，再决定积木如何呈现。不能因为底层接口有一个函数，就直接为每个函数制作一个面向学生的积木。

### 原则二：教育抽象与工程抽象分层

L1 的“挥手”可以对应一个完整动作能力；L4 才逐步展开到动作模块、控制参数和 ROS2 通信。底层真实，不等于所有底层细节都应在低龄阶段暴露。

### 原则三：仿真和真机共享语义，允许实现有差异

目标不是制造一个看起来完全一样的仿真器，而是保证学生在两个环境中学习的是同一套概念。差异必须可见、可解释、可记录。

### 原则四：异步、失败和取消必须是正式语义

机器人不会永远成功完成动作。动作超时、目标丢失、网络断开、摔倒和用户取消都应被建模，而不是由各个积木用隐含方式处理。

### 原则五：可观察性从第一天就设计

运行高亮、变量观察、状态变化、事件时间线和错误定位不是后期装饰。它们决定学生能否理解程序，也决定教师能否有效讲评。

### 原则六：允许不可逆的工程扩展

图形化适合学习和结构化表达，但不应限制 L4 的真实工程实践。Python、ROS2 和第三方算法可以成为扩展节点；无法还原为积木时，应明确显示边界，而不是生成一堆看似可编辑但实际不可维护的“伪积木”。

## 十、分期落地建议

### P0：最小可用 Educational IR

先支持：

- 程序开始事件；
- 顺序执行；
- 等待；
- 动作和语音能力；
- 基础循环和条件；
- 基础视觉事件；
- 基础变量和类型；
- 运行前校验；
- 仿真解释执行；
- 最小真机适配；
- 节点到积木的运行高亮。

这一阶段不必建设通用编译器。可以采用“Blockly 生成最小 IR，教育运行时解释执行”的方式，先验证课程闭环和语义模型。

### P1：完善观察、调试和 L3 状态能力

增加：

- 源码映射；
- Python 只读视图；
- 状态机和状态转移；
- 图像流和检测结果查看；
- 任务取消和超时；
- SDK 接口映射；
- 运行日志和事件时间线；
- 教师任务和提交数据关联。

### P2：支持 L4 混合工程

增加：

- 可编辑 Python 模块；
- ROS2 节点、Topic、Service、Action 的工程视图；
- YOLO 检测和坐标变换调试；
- 仿真与真机部署配置；
- 多模块版本管理；
- 性能记录和差异报告；
- 可复用的行为、状态机和算法模块。

## 十一、正式设计前要交付什么

Educational IR 不应由技术团队闭门定义。建议产品、教研和技术共同完成以下材料：

1. **能力注册表**：列出 K1 可被课程使用的动作、感知、状态、数据和系统能力。
2. **积木契约**：每个积木的教学目标、适用等级、输入输出、单位、异步性、失败方式、仿真支持、真机支持和安全等级。
3. **IR Schema 草案**：确定节点、边、事件、数据、能力引用、版本和来源映射的最小结构。
4. **运行语义说明**：明确顺序、并行、等待、取消、超时、异常传播和停止策略。
5. **仿真/真机一致性标准**：规定哪些行为必须一致，哪些差异必须向学生和教师公开。
6. **代表性样例**：至少编写 L1 情景剧、L2 智能导览员、L3 二维码迷宫三份完整样例，并分别生成积木、IR、代码视图和运行日志。
7. **一致性测试**：同一份样例 IR 在仿真和真机适配器上运行，验证事件、能力、状态和错误语义。

## 十二、需要提前澄清的边界

### 不要把 IR 做成“万能格式”

IR 只需要管理教育项目中需要被编辑、检查、仿真、部署、观察和评价的语义。它不必替代完整 Python 语言、ROS2 图计算模型、机器人控制器或物理仿真器。

### 不要追求所有代码的完全双向转换

合理目标是：核心教育语义可从积木映射到代码，并能保留来源和调试关系；工程代码允许超出图形化表达能力。完全双向可逆会显著抬高复杂度，且容易牺牲 L4 的真实开发能力。

### 不要让教学规则污染底层运行时

“本课只允许使用三个动作”是课程配置；“该动作如何启动、完成、超时和停止”是运行语义。二者应通过元数据和策略关联，而不是混成一套无法复用的逻辑。

### 不要把安全只放在 UI 上

按钮禁用、提示文案和教师确认都很重要，但不能替代运行时和硬件级安全。IR 安全属性、教育运行时安全网关、BoosterOS 保护机制和物理急停应形成多层防护。

## 十三、如何判断这个设计是否成功

在立项评审和 MVP 验证时，可以用以下问题判断 Educational IR 是否真正产生价值：

- 同一项目能否从仿真切换到真机，而不需要学生重写核心逻辑？
- 同一个动作或感知能力能否在不同前端视图中保持同一含义？
- 系统能否在运行前发现明显的类型、单位和安全问题？
- 动作超时、目标丢失、摔倒和网络断开是否有可解释的处理结果？
- 学生能否从运行高亮和日志定位到自己的积木或代码？
- 教师能否看到学生的过程性行为，而不只看最终成品？
- K1 SDK 或仿真实现变化时，课程积木和教学任务是否可以基本保持稳定？
- L1 到 L4 是否是逐步开放能力，而不是每个等级都重新学习一套工具？

如果这些问题无法得到肯定回答，说明当前建设的可能只是一个积木编辑器，而不是面向具身智能学习的开发环境。

## 十四、最终定位

Booster Educational IR 的最终目的，是支撑 BoosterStudio 形成下面这条连续的学习与开发路径：

```text
L1  看见动作和反馈
    ↓
L2  理解感知、判断和任务流程
    ↓
L3  理解状态、数据流和模块协作
    ↓
L4  进行 Python/ROS2 工程开发和智能闭环调试
```

从产品角度看，它让 BoosterStudio 不只是“把积木做出来”，而是把课程、仿真、真机、安全、代码过渡、调试和评价连接成一个系统。

从教研角度看，它让每个积木背后的学习目标、能力边界和可观察证据都能落到工具中。

从技术角度看，它在 Blockly 与 BoosterOS/ROS2/仿真引擎之间建立了稳定边界，允许前端交互和底层设备持续演进。

因此，Booster Educational IR 最值得保留的不是某个固定字段或某种文件格式，而是一个设计判断：

> **先定义学生要理解的机器人行为和系统关系，再用统一语义把积木、代码、仿真、真机和评价组织起来。**
