# BoosterStudio 图形化编程工具前置调研与产品设计建议

> 本文是 BoosterStudio 图形化编程工具立项前的临时调研记录，面向产品经理与教研经理，用于支持框架选择、产品定位、课程内容设计和 MVP 范围讨论。

## 摘要结论

BoosterStudio 不应被设计成“Mind+ 的人形机器人版本”，而应定位为“面向 K1 具身智能学习的分层开发环境”。

技术上建议采用 Blockly 类编辑器作为基础，自己建设面向 K1 的中间表示、运行时、安全网关和仿真适配层；产品形态重点借鉴 MakeCode 的“积木—代码—仿真”闭环、VEXcode VR 的仿真任务化，以及 LEGO 的课程一体化设计。

结合现有 K1 L1-L4 课程，BoosterStudio 的图形化能力应形成逐级变化的工具体验：

```text
L1：行为编排器
L2：任务流程设计器
L3：系统与状态机编辑器
L4：代码工程与智能闭环调试器
```

这意味着产品研发的起点不应是“先选一个积木框架”，而应是先明确：不同学段要让学生理解什么、完成什么任务、观察什么反馈，以及哪些复杂性应该被隐藏或逐步开放。

## 一、主流工具的本质差异

| 工具/路线 | 技术框架或运行方式 | 产品形态 | 最值得借鉴的部分 | 对 BoosterStudio 的限制 |
|---|---|---|---|---|
| Scratch | Scratch Blocks + Scratch VM，程序以事件驱动 AST 运行 | 创意编程、动画、游戏、故事 | 低龄友好、事件模型、即时反馈、自由创作 | 面向角色和舞台，不适合直接承载机器人安全、传感器流和复杂异步任务 |
| Blockly | 通用 Web 积木编辑器，本身不负责完整运行时 | 可嵌入各种教育或行业应用 | 自定义积木、类型约束、代码生成、可扩展 | 需要自行建设运行时、仿真、设备连接和课程产品 |
| MakeCode / PXT | Blockly 编辑器 + PXT 语言 + Monaco 代码编辑器 + 编译器/仿真器 | 硬件编程、游戏、Minecraft、机器人 | 积木与 JavaScript/Python 过渡、模拟器、教程地图、硬件部署 | PXT 强依赖其编译和目标设备体系，不宜作为 K1 的完整底座 |
| Mind+ | 底层实现细节未完全公开 | 桌面端创客平台，积木、代码、AI 训练、界面设计、硬件扩展 | 对青少年友好、硬件生态丰富、实时/离线兼容、内容资源完整 | 功能范围很宽，容易形成“什么都有但学习主线不清”的产品 |
| PictoBlox | 底层实现细节未完全公开，具有 Scratch 风格产品特征 | 积木、Python、AI/ML、机器人、AR/VR、Notebook | Junior Blocks、AI 模型工具、Python 调试、项目和课程产品化 | 内容跨度过大，K1 需要重新收敛到人形机器人能力 |
| LEGO SPIKE | 硬件套件、课程、App、积木/Python 一体化 | 课程驱动的套件式机器人教育 | 课程目标、活动卡、实体搭建、教师资源高度绑定 | 强绑定 LEGO 硬件；官方已宣布 SPIKE 产品停止销售，软件支持至 2031 年 |
| VEXcode VR | 专有积木运行时、虚拟机器人、Switch、Python | 仿真优先、任务/挑战/竞赛 | 免安装仿真、Blocks 到 Python、项目分享、学习提交、数据看板 | 产品和硬件体系封闭，无法直接复用技术实现 |
| Open Roberta | Blockly + NEPO + 云端平台 + 多机器人后端 | 多硬件机器人编程实验室 | 多设备抽象、云端项目、模拟器、用户和程序管理 | 后端体系较重，适合参考平台架构，不适合作为 BoosterStudio 的直接底座 |
| MIT App Inventor | Blockly 风格积木 + 组件模型 + 事件驱动 | 手机 App 创作、设计器和积木编辑器 | “组件—事件—属性—行为”模型、项目导向 | 不具备机器人运动控制和仿真能力 |

### 1. Scratch：适合借鉴交互，不适合直接借鉴运行时

Scratch 的重要特点不是“积木长什么样”，而是：

```text
事件触发 → 脚本运行 → 对象状态变化 → 画面即时反馈
```

Scratch Blocks 2.0 已经基于 Blockly，但 Scratch 本身不主要依赖传统的代码生成器，而是通过 Scratch VM 维护和执行程序的抽象语法树。需要注意的是，旧的 `scratch-vm` 仓库已于 2026 年 6 月归档，后续迁移到 Scratch mono-repo。

适合借鉴的部分：

- “当程序开始”“当听到指令”“当检测到目标”等事件积木；
- 程序运行时的高亮反馈；
- 作品导向和故事化任务；
- 低龄阶段对复杂性的隐藏。

不建议直接借鉴的部分：

- 以角色、舞台、造型为核心的数据模型；
- 依赖 Scratch VM 作为机器人运行时；
- 让机器人所有动作都表现为同步、即时的简单命令。

### 2. Blockly：最适合作为 BoosterStudio 的编辑器基础

Blockly 官方对自身的定位非常明确：它是一个可定制的 Web 图形化代码编辑器，不是完整的教育产品。它主要负责：

- 积木渲染；
- 拖拽和连接；
- 输入框、下拉框和类型连接；
- 积木序列化；
- 自定义积木；
- 代码生成接口。

实际应用仍需自行提供：

- 程序运行时；
- 设备连接；
- 仿真系统；
- 项目管理；
- 教学内容；
- 权限和安全策略；
- 代码调试与日志系统。

这正适合 BoosterStudio。K1 的核心问题并不是“如何显示积木”，而是如何将积木映射为：

```text
学生程序
   ↓
K1 教学中间表示
   ↓
虚拟 K1 运行时 / 真机 K1 运行时
   ↓
BoosterOS SDK / ROS2 / 仿真引擎
```

### 3. MakeCode：最值得借鉴的产品组合

MakeCode 的核心产品闭环是：

```text
积木编程 → 文本代码 → 模拟器 → 实体设备 → 教程与挑战
```

PXT 官方仓库显示，其技术体系包含：

- 基于 Blockly 的编辑器；
- Monaco 代码编辑器；
- 面向初学者的 TypeScript 子集；
- 自定义积木扩展；
- 代码转换；
- 编译器和目标硬件适配；
- 模拟器；
- 教程工具；
- 教师工具。

MakeCode 对 BoosterStudio 的最大启发不是 PXT 编译器本身，而是产品结构：

- 学生可以从积木切换到代码；
- 仿真器和编辑器在同一个工作区；
- 每个知识点绑定一个项目或挑战；
- 设备部署不是独立工具，而是学习流程的一部分；
- 教程、项目、代码和评价形成闭环。

BoosterStudio 可以借鉴其产品组织，但不建议直接采用 PXT 作为底层，因为 K1 的运行环境是 BoosterOS SDK、Agent Framework 和 ROS2，不是微控制器固件编译体系。

### 4. Mind+ 与 PictoBlox：适合作为产品竞品，不适合作为技术底座

Mind+ 当前的产品定位是“一站式创意造物平台”，包含：

- 积木和代码双模式；
- 多种主控板和硬件扩展；
- 实时交互和离线执行；
- AI 模型训练；
- 目标检测、图像分类、姿态识别等能力；
- 可视化界面设计；
- 教程、项目和社区。

PictoBlox 的产品范围也很广，包括：

- 普通积木；
- Junior Blocks；
- Python；
- AI/机器学习；
- 机器人；
- IoT；
- AR/VR；
- Python Notebook；
- 调试器和代码可视化。

它们说明了青少年用户希望在一个环境中完成“设计、编程、硬件、AI、展示”。但 BoosterStudio 不能简单复制这种“大而全”，因为 K1 课程已有明确的能力递进：

```text
身体与动作
→ 任务与行为
→ 感知与状态
→ 工程化智能闭环
```

Mind+ 的底层框架和扩展机制没有像 Blockly、PXT 那样充分公开，因此更适合作为产品体验和市场基准，而不是框架选择依据。

### 5. VEXcode VR：仿真产品形态的优先参考

VEXcode VR 的产品设计非常接近 BoosterStudio 未来需要的教育形态：

- 浏览器直接使用；
- 无需安装；
- 虚拟机器人优先；
- Blocks、Switch、Python 多种编程方式；
- 多个任务场景和挑战地图；
- 项目分享；
- 学习提交；
- 数据看板；
- AI 和数据科学扩展。

VEX 的“Switch”模式值得特别借鉴。它不是简单地在旁边显示一份 Python，而是帮助学生理解：

```text
这个积木程序
↓
在文本代码中对应什么结构
↓
怎样逐步修改文本代码
```

BoosterStudio 后续可以采用类似思路，但需要支持 Python、BoosterOS SDK 和 ROS2，而不是 VEX 专有语言。

### 6. LEGO：课程设计和产品包装的参考

LEGO SPIKE 的核心优势不只是 App，而是：

```text
硬件套件
+ 教师课程
+ 学生任务卡
+ 可观察的实体结果
+ 竞赛和展示
```

它体现出一个重要规律：

> 青少年工具的竞争力不只在编辑器，而在“工具是否让教师能上课、学生能完成作品、学校能持续使用”。

不过 LEGO 官方已经宣布 SPIKE 于 2026 年停止销售，软件会继续支持至 2031 年。这也提醒 BoosterStudio：产品架构要避免过度绑定某一代固件或某一种硬件版本。

## 二、K1 L1-L4 的内容设计对工具的约束

知识库中的 K1 课程已经形成了比较清晰的四阶路径：

- L1：身体、感官、动作、语音、情景剧；
- L2：变量、条件、循环、视觉、语音、校园导览员；
- L3：代码控制、图像流、二维码、状态机、迷宫探索；
- L4：ROS2、YOLO、坐标变换、策略、追球和踢球。

对应到工具，不建议四个等级都使用同一种“普通积木”。

| 等级 | 学习重点 | 推荐工具形态 | 不宜暴露的复杂性 |
|---|---|---|---|
| L1 | 顺序、事件、循环、动作、语音表达 | 图标化积木 + 仿真画面 + 情景任务 | 关节角度、线程、回调、ROS2 |
| L2 | 变量、条件、感知、交互、任务流程 | 语义积木 + 任务模板 + 仿真/真机切换 | 图像流、消息类型、底层协议 |
| L3 | 数据流、模块、状态机、代码接口 | 积木/状态图 + Python + SDK 调试 | 过度隐藏程序结构 |
| L4 | 工程化闭环、部署、鲁棒性、系统集成 | Python/ROS2 IDE + 可视化状态图和监控 | 用积木替代真正的工程代码 |

### L1：机器人行为创作工具

L1 当前终端项目是机器人情景剧，因此核心不是让学生学习大量编程语法，而是完成：

```text
开始
→ 动作
→ 等待
→ 说话
→ 再动作
→ 循环或条件响应
```

建议提供：

- “当程序开始”；
- “等待”；
- “执行动作”；
- “播放声音”；
- “说一句话”；
- “重复”；
- “如果听到/看到……”；
- “停止程序”；
- “安全停止”。

动作积木应以“挥手、鞠躬、转身、走一步、跳舞”等语义表达，不要在 L1 直接呈现关节控制。

### L2：机器人任务流程设计工具

L2 的校园智能导览员不是单纯的动作组合，而是：

```text
感知对象
→ 判断条件
→ 选择流程
→ 语音反馈
→ 动作反馈
```

建议增加：

- 变量；
- 数字、文字和布尔值；
- 条件判断；
- 等待直到；
- 重复直到；
- 视觉识别结果；
- 语音识别结果；
- 目标是否存在；
- 识别置信度；
- 自定义行为模块；
- 场景任务模板。

L2 可以开始让学生接触变量，但不要让学生一开始面对完整的图像对象、消息结构和回调线程。

### L3：系统集成和状态机工具

L3 已经涉及：

- 图像流；
- 二维码；
- 识别结果；
- 多目标；
- 状态机；
- 代码控制；
- 模块协同；
- 持续运行。

传统积木在这个阶段容易产生大量“长程序”，从而带来两个问题：

1. 程序面积越来越大，学生难以理解系统结构。
2. 图形化程序和未来 Python 代码之间出现明显断层。

因此 L3 更适合采用：

```text
状态节点
→ 感知模块
→ 条件转移
→ 动作模块
```

同时提供 Python 代码视图，让学生理解积木背后的函数、回调、数据对象、状态、模块和事件循环。

### L4：工程化开发和智能闭环工具

L4 的自主追球与踢球任务，本质上已经不是低代码问题，而是工程问题：

```text
视觉检测
→ 坐标转换
→ 状态机
→ 目标丢失处理
→ 策略决策
→ 动作执行
→ 部署与复盘
```

L4 需要的不是更多彩色积木，而是：

- Python 编辑器；
- BoosterOS SDK 文档和示例；
- ROS2 节点/话题/服务可视化；
- 图像和检测结果查看器；
- 状态机可视化；
- 日志时间线；
- 参数调试面板；
- 仿真与真机对照；
- 一键启动和部署；
- 性能记录和复盘。

BoosterStudio 的图形化能力应在 L3、L4 变成“系统可视化和调试辅助”，而不是坚持使用传统的全量积木编程。

## 三、建议采用的总体技术架构

不建议采用：

```text
积木 → 拼接 Python 字符串 → 直接执行
```

建议采用：

```text
图形化积木
    ↓
类型化中间表示 Booster Educational IR
    ↓
┌─────────────────┬──────────────────┐
│ 虚拟 K1 运行时   │ 真实 K1 运行时     │
│ Simulator Adapter│ BoosterOS Adapter│
└─────────────────┴──────────────────┘
    ↓
安全网关、安全策略、日志、状态反馈
```

同时从同一份中间表示生成不同视图：

```text
Booster Educational IR
    ├── 积木视图
    ├── Python 视图
    ├── 行为流程图
    ├── 状态机视图
    └── 运行日志和评价数据
```

### 为什么必须有中间表示

K1 的动作和感知接口存在明显的异步特征，例如：

- 动作可能需要等待完成；
- 图像和 IMU 是持续数据流；
- 视觉识别可能有置信度；
- 机器人可能摔倒或进入异常状态；
- 真机和仿真存在延迟、失败和环境差异。

如果只生成 Python 字符串，后期会很难统一处理：

- 仿真和真机的行为一致性；
- 程序暂停和单步执行；
- 运行时高亮；
- 错误定位；
- 安全拦截；
- L1-L4 的不同抽象层级。

## 四、BoosterStudio 的积木分类建议

积木分类不建议完全按照传统编程语言划分，而应体现具身智能的基本闭环：

```text
感知 → 决策 → 行动
```

### 1. 事件类

- 程序开始；
- 点击运行；
- 收到语音指令；
- 识别到目标；
- 机器人状态改变；
- 机器人摔倒；
- 定时触发。

### 2. 控制类

- 等待；
- 重复；
- 条件判断；
- 等待直到；
- 停止当前行为；
- 停止全部行为；
- 超时处理。

### 3. 身体行动类

- 执行动作；
- 设置行走速度；
- 向前/向后/横移/转向；
- 控制头部方向；
- 播放示教动作；
- 说话；
- 播放声音；
- 灯光或表情反馈。

### 4. 感知类

- 获取相机画面；
- 识别颜色；
- 识别二维码；
- 识别人脸；
- 识别物体；
- 获取距离；
- 获取姿态；
- 获取电量；
- 获取摔倒状态；
- 获取目标位置；
- 获取目标置信度。

### 5. 决策和数据类

- 变量；
- 数字、文字、布尔值；
- 目标是否存在；
- 识别置信度；
- 目标位置；
- 当前状态；
- 目标列表；
- 自定义函数或行为。

### 6. 系统和工程类

建议在 L3 以后逐步开放：

- 订阅图像流；
- 回调函数；
- 状态机；
- 坐标系；
- ROS2 节点；
- Topic；
- Service；
- Action；
- 日志；
- 参数；
- 任务取消；
- 超时处理。

### 7. 安全类

安全功能不应作为普通积木的附属功能，而应成为工具的一级能力：

- 模拟运行；
- 真机运行许可；
- 速度上限；
- 动作白名单；
- 运行时间上限；
- 自动停止；
- 摔倒检测；
- 网络断开停止；
- 急停提示；
- 教师审批；
- 真机部署前检查。

## 五、推荐的产品形态

BoosterStudio 教育模式建议采用“一体化工作台”，而不是单独打开一个积木编辑器。

```text
┌─────────────────────────────────────────────┐
│ 课程 / 项目 / 设备 / 仿真真机 / 保存 / 发布   │
├──────────────┬─────────────────┬─────────────┤
│ 任务卡与积木  │ 程序编辑区       │ 仿真/真机画面 │
│ 积木分类      │ 代码视图         │ 机器人状态    │
│ 示例程序      │ 行为流程图       │ 传感器画面    │
├──────────────┴─────────────────┴─────────────┤
│ 运行 / 暂停 / 单步 / 日志 / 变量 / 事件时间线 │
└─────────────────────────────────────────────┘
```

建议提供四种工作模式：

1. 学习模式：有任务卡、示例程序、提示和限制。
2. 创作模式：允许自由搭建和分享作品。
3. 工程模式：开放 Python、SDK、状态机和日志。
4. 教师模式：发布任务、查看运行记录、设置真机权限和评价。

## 六、积木到代码的过渡策略

不建议一开始承诺“积木和 Python 完全双向同步”。完整双向同步的难点包括：

- Python 中的自由表达无法完全映射回积木；
- 异步逻辑难以保持一致；
- 自定义函数和第三方库无法全部图形化；
- 学生修改代码后，积木可能失去可逆性。

建议分三个阶段：

### 第一阶段：积木生成代码

```text
积木程序
→ 查看对应 Python
```

学生可以看到积木对应的代码，但暂时不修改代码。

### 第二阶段：积木和代码分区协作

```text
图形化主流程
+ 可编辑 Python 函数
```

例如：

- 积木负责行为流程；
- Python 函数负责数据处理；
- 视觉结果通过接口传回积木。

### 第三阶段：工程代码为主

```text
Python / ROS2 主程序
+ 状态图
+ Topic 图
+ 调试面板
```

这一阶段图形化不再承担全部编程，而是承担系统理解和调试。

## 七、MVP 范围建议

### MVP：先覆盖 L1-L2

建议首期完成：

- Blockly 编辑器；
- K1 专属积木；
- L1/L2 两级积木分层；
- 虚拟 K1；
- 仿真运行、暂停、重置、慢放；
- 动作和语音仿真；
- 基础视觉/语音事件；
- 仿真与真机切换；
- 真机安全限制；
- 项目保存；
- 课程任务模板；
- 示例程序；
- 程序运行高亮；
- 基础日志；
- 学生作品提交；
- 基础教师查看。

MVP 不建议优先开发：

- 自然语言自动生成完整程序；
- 多硬件兼容；
- 全量 AI 模型训练；
- 复杂多人协同编辑；
- L4 全套 ROS2 图形化开发；
- 自定义场景生成平台；
- 通用低代码 Agent 编排器。

这些功能应建立在 L1-L2 的课程闭环被验证之后。

### P1：支持 L3 系统理解

- Python 和积木同步查看；
- 状态机编辑器；
- 图像流和检测结果查看器；
- 视觉、语音、控制模块化；
- SDK 接口积木；
- 回调和事件可视化；
- 更完整的班级、作业和评价功能。

### P2：支持 L4 工程实践

- ROS2 节点/话题/服务可视化；
- YOLO 检测调试；
- 坐标系和轨迹显示；
- 多机器人仿真；
- 足球任务模板；
- 性能打点；
- 真机部署和版本管理；
- 仿真到真机的差异报告。


## 九、正式开发前，教研团队必须先交付的内容

在工程团队开始搭建编辑器之前，建议先完成六份设计成果：

1. L1-L4 能力目标与工具能力矩阵。
2. 每个等级的积木白名单、隐藏能力和开放能力。
3. 每个积木的输入、输出、运行副作用、失败方式和安全等级。
4. 三个代表性项目的完整程序样例：
   - L1 机器人情景剧；
   - L2 校园智能导览员；
   - L3 二维码迷宫探索。
5. 仿真与真机的行为一致性标准。
6. 教师布置、学生完成、提交、评价和复盘的完整流程。

其中最重要的是“积木契约”，每个积木至少应明确：

```text
积木名称
适用等级
教学目标
输入类型
输出类型
是否产生运动
是否异步
仿真是否支持
真机是否支持
失败情况
生成的 Python/SDK 代码
安全等级
评价指标
```

## 十、最终产品定位

BoosterStudio 教育模式可以定义为：

> 面向 K-12 学生、教师和机器人教育机构的 K1 具身智能学习与开发环境。学生通过积木、代码、仿真和真机实践，逐步完成从机器人行为创作、任务流程设计，到感知决策系统和工程化智能闭环的学习。

它的核心差异不应是“积木更漂亮”，而应是：

```text
课程目标清晰
+ 人形机器人语义积木
+ 仿真优先
+ 安全真机实践
+ 积木到 Python 的自然过渡
+ 感知—决策—行动闭环
+ 教师可管理、学生可复盘
```

产品最终应形成三种逐级变化的工具体验：

```text
L1：行为编排器
L2：任务流程设计器
L3：系统与状态机编辑器
L4：代码工程与智能闭环调试器
```
